# ATLAS PROOF — Архитектура, фазы, безопасность

---

# ЧАСТЬ 1 — ПРИНЦИПЫ

Пять правил, через которые проходит любое решение:

1. **Ничего не добавлять без необходимости.** Если функция не усиливает Proof, Research Intelligence, контроль или монетизацию — откладываем.
2. **Снаружи максимально просто.** Пользователь видит: вопрос → исследование → Proof → Evidence. Вся сложность Pattern/Memory/Mechanisms/Telemetry остаётся внутри.
3. **Интеллект развивается только контролируемо.** Никакого хаотичного самообучения. Новая способность появляется только через реальные Proof → проверку → human approval → release → telemetry.
4. **Всё должно быть измеримо.** Мы обязаны понимать, стал ATLAS лучше или нет: качество, Evidence, Memory usage, dead ends, corrections, cost.
5. **Каждая версия сохраняет исходный смысл продукта.** Ядро всегда одно: ATLAS доказывает и развивается через доказанный опыт.

**Практический тест для любого решения:**
> Если реализация выглядит сложнее, чем сама идея, значит мы, скорее всего, усложнили её лишним.

**Архитектурное правило подписки:**
> Доступ определяет, можно ли начать новое исследование. Изменение доступа не должно задним числом уничтожать уже легитимно созданные Proof или ломать уже начатую работу.

**Масштаб:**
> Не пытаться сейчас сделать систему идеальной на 100 000 пользователей. Сделать её правильной на первых 100, но так, чтобы при 100 000 не пришлось выбрасывать фундамент.

# ЧАСТЬ 2 — ПЯТЬ ЖЁСТКИХ АРХИТЕКТУРНЫХ ТРЕБОВАНИЙ

1. **Research Job — настоящая сущность.** Не «нажал кнопку → большой API request → получил ответ». У исследования есть ID, состояние и связь с пользователем/задачей. Можно закрыть приложение и вернуться, не потеряв работу.
2. **Entitlement проверяется на сервере.** Скрытая кнопка в DEMO не защищает CORE. UI только показывает состояние; решение «можно ли запустить research» принимает backend.
3. **Interpreter хранится отдельно от Research.** Логировать цепочку `Original Question → Normalized Task → Research Plan → Proof`. Это позволяет во время валидации сразу увидеть, где именно сломался интеллект.
4. **ARI не привязан к одной AI-модели.** Research Engine обращается к AI abstraction layer (`ModelGateway` / `SearchGateway` / `ContentFetcher`), а не размазан вызовами конкретного API по всему приложению. Накопленный интеллект живёт в ATLAS-owned структурах данных, не в провайдере.
5. **Project Memory и пользовательская история — разные вещи.** Удаление пользователем своего Proof не удаляет независимо верифицированное системное знание. И наоборот: приватный вопрос пользователя не превращается в публичную память.

# ЧАСТЬ 3 — ФАЗЫ РЕАЛИЗАЦИИ

Ориентировочная последовательность. Точный план формируется **после** audit + gap report.

| № | Фаза | Оценка | Зачем |
|---|---|---|---|
| 0 | Audit + gap report | 0.3–0.5 нед | Понять, что есть, прежде чем писать код |
| 1 | Домен + БД | 1–1.5 | Project/Topic/User как полноценные сущности |
| 2 | Telegram identity + app shell + onboarding + Motion System | 1.5–2 | Идентификация, навигация, i18n, основа анимаций |
| 3 | Job-инфраструктура | 1 | Persistent ResearchJob, state machine, идемпотентность |
| 4 | Question Interpreter + Scope/Entitlement Gate | 1.5–2 | Понять запрос дёшево до дорогого research |
| 5 | Research Memory + Planner + 5 checks | 2–2.5 | Ядро: Memory guides, Evidence verifies |
| 6 | Research Engine + Evidence + Recovery | 2.5–3 | Сердце продукта, самая тяжёлая фаза |
| 7 | Proof + layered output + Ownership/Privacy | 1.5–2 | Проверка качества, приватность по умолчанию |
| 8 | Research Experience Record | 0.5–1 | Observability (без авто-анализа) |
| 9 | Admin v1 | 0.5–1 | Issues, ручные правки, аудит-лог |
| 10 | Regression harness + Source Health Check | 1–1.5 | Blind/robustness тесты, мониторинг источников |
| 10.5 | Proof Map (3 узла) + Access Control | 0.5–1 | Визуализация поверх Proof Core |
| 11 | SubscriptionService | 1–1.5 | Жизненный цикл подписки |
| 12 | Telegram Stars | 1–1.5 | Единственный платёжный канал |
| 13 | Hardening | 1.5–2 | Финальная защита перед реальными пользователями |
| | **ИТОГО** | **17–20.5 нед** | |

Затем — **Closed Validation Phase**: продукт собран, но доступ ограничен owner-only флагом. Владелец лично прогоняет ~75 исследовательских ситуаций через реальный продукт. После валидации флаг снимается.

Матрица валидации: 5 проектов × 3 сильных вопроса × 5 исследовательских позиций ≈ 75 ситуаций. Цикл: ~30 → ARI Review #1 → ~30 → ARI Review #2 → ~15 → Final Review.

**Критерии успеха — не «75/75 правильных ответов», а:**
- ARI понимает по-разному сформулированные вопросы
- меняет путь исследования при смене ракурса
- не просто подтверждает формулировку пользователя
- переносит предыдущий исследовательский опыт
- обнаруживает релевантные ограничения
- честно обходится с неопределённостью
- умеет остановиться при достаточных доказательствах
- умеет остановиться с нерешённым выводом, когда доказательств нет
- исследование становится менее повторяющимся без потери качества

Доступ на этом этапе — владелец/admin. Отдельную систему тестировщиков сейчас не строить; при необходимости позже — простой allowlist поверх существующего доступа.

# ЧАСТЬ 4 — БЕЗОПАСНОСТЬ ПО ФАЗАМ

Безопасность — не отдельная фаза в конце. Каждая фаза имеет свой обязательный security-пункт, входящий в её Definition of Done.

| Фаза | Требования |
|---|---|
| **1 — Домен + БД** | Секреты только через переменные окружения, никогда в коде/миграциях. Деньги — целочисленные единицы, не float. |
| **2 — Identity** | initData проверяется строго на сервере, клиентским данным не доверять. Разделение ролей пользователь/админ с первого дня. |
| **3 — Job** | Жёсткий бюджетный потолок на каждый job (макс. запросов/стоимости/времени). Идемпотентность retry — повторный запуск не создаёт дубликаты и не тратит бюджет дважды. |
| **4 — Interpreter** | Пользовательский ввод — всегда данные, никогда не часть системных инструкций модели (закладывается в промпт-архитектуру сейчас). Защита от прямых prompt-инъекций. |
| **5 — Memory** | Lifecycle `OBSERVED → CANDIDATE → ACTIVE` не обходится никогда, даже в тестах — единственный барьер против отравления памяти. |
| **6 — Research Engine** | **SSRF-защита именно здесь**, а не в Hardening — как только система начинает fetch'ить произвольные URL, нужна защита от internal IP/localhost/приватных диапазонов. Лимиты размера контента и таймауты. Защита от indirect prompt injection: контент чужих страниц передаётся модели строго как данные для анализа, не как инструкции. |
| **7 — Proof** | Валидация structured output на каждом критическом шаге (вердикт, confidence) — при несоответствии схеме результат не идёт дальше. `visibility = PRIVATE` по умолчанию. Проверка владения на сервере. |
| **8 — Experience** | Неизменяемая запись — видно, откуда и когда что-то попало в память. |
| **9 — Admin** | Неизменяемый append-only лог всех ручных правок: кто/когда/что поменял. |
| **10 — Regression** | Тест-кейсы включают попытки prompt-инъекции, не только штатные вопросы. |
| **11–12 — Подписка/платежи** | Идемпотентность платежей — двойной клик не списывает дважды. Backend никогда не доверяет `payment_success` с фронтенда, только верифицированному серверному событию. |
| **13 — Hardening** | Rate limiting. Redirect validation, таймауты. Бэкапы БД **+ проверенное восстановление** (restore-тест обязателен, не только backup). Раздельные emergency-флаги (`GLOBAL_RESEARCH_PAUSED`, `NEW_PAID_ACTIONS_PAUSED`, `STARS_PURCHASES_PAUSED`, `LIVE_CHANGES_PAUSED`). Явный список того, что **нельзя** логировать: initData secrets, auth tokens, payment secrets, приватные ключи. Финальный security review. |

Пользовательский контент — недоверенные данные. Пользователь не может изменить: системные инструкции, capability contract, Research Pattern, learning boundary, бюджетные лимиты, verdict policy.

# ЧАСТЬ 5 — КОНФИГУРАЦИЯ CLAUDE CODE

## Стартовая конфигурация

```
ATLAS PROOF
├── CLAUDE.md              ← неизменяемые законы проекта (корень репозитория)
├── .claude/skills/
│   ├── atlas-core         ← методология Research Engine
│   ├── atlas-intent       ← понимание запроса и роутинг
│   ├── atlas-memory       ← Research Memory, freshness, verified-only
│   ├── atlas-proof        ← структура результата, вердикты, язык
│   └── atlas-product-ui   ← продуктовые и UI-правила, motion
├── Hooks                  ← добавить, когда появятся первые работающие CORE-тесты
│   ├── core regression tests
│   └── lint / typecheck / tests
├── Subagents              ← добавить, когда работа разделится по областям
│   ├── core-engineer
│   ├── frontend-engineer
│   └── reviewer
└── MCP                    ← только под конкретную внешнюю необходимость
```

## Порядок внедрения

1. `CLAUDE.md` в корень репозитория
2. 5 Skills в `.claude/skills/`
3. **Audit + gap report** (см. `00_START_HERE.md`)
4. Реализация по утверждённому плану
5. Когда появятся первые работающие CORE-тесты → Hooks
6. Когда работа разделится на frontend/core/review → Subagents
7. MCP — только при реальной внешней необходимости

## Hooks

**Hook 1 — после изменения Research Engine:**
```
CORE file changed → unit tests → blind regression suite → robustness suite
```
Автоматически прогоняются: TAO, SUI, TIA, staking-safety, BTC passive holder, SOL valuation, TAO Moon.

**Hook 2 — после frontend-изменений:** lint, typecheck, tests.

**Hook 3 (позже) — перед опасными командами:** удаление больших директорий, destructive миграции, изменения production config.

**Hooks проверяют, но не решают стратегию.** Никаких автоматических approve.

## Subagents

| Агент | Область | Skills |
|---|---|---|
| `core-engineer` | Research Engine, Memory, Intent, Proof, Evidence | atlas-core, atlas-intent, atlas-memory |
| `frontend-engineer` | экраны, компоненты, UX, responsive, design system | atlas-product-ui, atlas-proof |
| `reviewer` | проверка чужой работы на нарушения концепции, edge cases, регрессии | все |

Смысл reviewer — чтобы не было «придумал → написал → сам себе сказал идеально».

## MCP — важное разделение

```
MCP Claude Code       →  строит приложение
ATLAS CORE runtime    →  исследует digital assets
```

Это разные уровни. Если будущему ARI нужны web/onchain инструменты, это **не** значит, что тот же research MCP нужно давать coding-агенту. Не смешивать.

## Memory-дисциплина

```
важная архитектура        → CLAUDE.md / Skills
мелкие рабочие наблюдения → agent memory
```
Не наоборот. Стратегия не должна случайно рождаться в auto-memory.

# ЧАСТЬ 6 — ЧТО СЕЙЧАС ОТЛОЖЕНО

**ARI Self-Learning Loop** — механизм, где ARI сам анализирует накопленный опыт и предлагает изменения методологии: `ArISelfReview`, `PatternCandidate` (ADD_RULE / NARROW_RULE / REMOVE_RULE / GENERALIZE_RULE / NEW_BRANCH), `LearningNeed`, `NextCaseRecommendation`, shadow validation, публичное версионирование `IntelligenceRelease`, ARI Review Panel.

**Строим сейчас:** `ResearchExperienceRecord` — полная фиксация опыта по каждому Proof. Это observability, нужна независимо.

**Откладываем:** сам механизм самоанализа. Pattern v1→v2 в BETA — полностью ручной переход, человек формулирует изменения на основе накопленных записей.

**Причина:** механизм самоанализа нужно тренировать и тестировать на реальном разнообразном опыте, которого до валидации ещё нет. Спроектированный вслепую, он с высокой вероятностью потребует переделки.

**Business Review Panel** (конверсия DEMO→CORE, подписки) — также откладывается до появления реальных пользователей.
