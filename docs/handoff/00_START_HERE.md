### Что аудировать

Пройди по репозиторию и определи по каждому пункту: **что есть / чего нет / что противоречит спецификации**.

#### 1. Entitlement state model
Может ли текущая архитектура надёжно представить:
- `DEMO`
- `ARI_CORE` active
- `ARI_CORE` expired
- refunded / cancelled subscription
- lifetime DEMO usage (счётчик на уровне User, не плана)
- read-only доступ к историческим Proof

Ключевое правило: **entitlement определяет, можно ли НАЧАТЬ новую операцию. Последующее изменение entitlement не должно задним числом уничтожать легитимно созданные Proof или обрывать уже авторизованный Research Job.**

Отдельно оцени: нужно ли снапшотить entitlement в ResearchJob при создании (`entitlement_at_start`).

#### 2. Research Job lifecycle
Проверь/спроектируй state machine. Минимум: `QUEUED / RUNNING / SUCCEEDED / FAILED / CANCELLED`. Если нужны дополнительные состояния — обоснуй.

Аудируй: retries, дублирующее создание job, двойные нажатия, прерванные запросы, частичные результаты, идемпотентность, возможность случайно сгенерировать/списать один Proof дважды, восстановление после рестарта.

**Жёсткое требование:** UI обещает пользователю «можете вернуться позже — ARI продолжит работу». Это серверный контракт, не декоративная надпись. Легитимно запущенный ResearchJob обязан продолжаться независимо от сессии Mini App. Закрытие приложения не прерывает research. Повторное открытие восстанавливает текущее состояние job или готовый Proof.

Не строй распределённую job-платформу, если v1 в ней не нуждается.

#### 3. Question Interpreter boundary
Проверь, что сырой пользовательский текст не может в обычном потоке обойти:
```
interpretUserQuestion()
→ schema validation
→ entitlement/scope validation
→ Research Engine
```
Аудируй: строгую валидацию structured output, обработку malformed AI output, таймауты модели, retry-стратегию, **максимум 2 попытки уточнения**, статусы `READY / NEEDS_CLARIFICATION / OUT_OF_SCOPE / INVALID`, сохранение пользовательских допущений как допущений, а не как проверенных фактов.

Interpreter должен оставаться лёгким. Он **не** второй Research Engine.

#### 4. Scope vs Entitlement — не смешивать
Пример: Aave может быть внутри research scope ATLAS, но недоступен для DEMO.
```
Question Interpreter: READY
Scope:                SUPPORTED
Entitlement:          CORE_REQUIRED
```
Проверь, не слиты ли эти понятия в текущих доменных типах. Entitlement Gate должен проверять **все** сущности, упомянутые в normalized research task, а не только основную.

#### 5. Dynamic Project roster
ARI • CORE — это доступ к развивающемуся Research Intelligence, **не** покупка фиксированного каталога проектов.

Аудируй: модель статусов проекта, механику проверки доступа, кэш и его инвалидацию, не копируются ли списки проектов внутрь пользовательской подписки.

**Отдельный migration gap:** в коде может быть зашит старый roster (Pump.fun, Hyperliquid, Aave, Ethena, Pendle, Uniswap, Jupiter, Morpho, Aerodrome, Sky). Он теперь **legacy**. Покажи все места, где он используется (UI, entitlements, access logic, `demo_project_ids`). **Не делай тихую механическую замену одного массива на другой** — сначала отчёт.

#### 6. Proof ownership и privacy
Proof приватен по умолчанию. Аудируй цепочку `User → Research → Proof → Evidence → Sources`: границы владения, авторизационные проверки, возможность запросить чужой Proof подбором ID, серверные проверки вместо UI-ограничений.

Публичных Proof URL в v1 нет. Share не должен незаметно делать Proof публичным.

#### 7. Data deletion architecture
Полноценная compliance-подсистема сейчас не нужна. Но проверь, что модель данных не сделает удаление пользователя практически невозможным позже. Определи: какие записи принадлежат пользователю, какие research-знания могут сохраняться только при подлинной анонимизации, риски каскадного удаления, логи с пользовательскими вопросами. Предложи минимальную future-safe структуру.

#### 8. Telegram Stars isolation
Цена сейчас: **ARI • CORE — 2 999 Stars/месяц**, но она должна идти из конфигурации, не быть захардкожена по всему UI. Проверь, что Telegram-специфика платежей не протекает в доменную модель. Мы должны иметь возможность поменять цену/реализацию платежей без переписывания Research Engine и Proof.

#### 9. Source health vs Research regression
Разделить:
- **Pattern regression** — валидация методологии после её изменения (дорого, запускается по триггеру)
- **Source health check** — битые URL, недоступные endpoint, удалённые страницы (дёшево, периодически)

Предложи минимальную архитектуру периодических health-check без перезапуска полноценных Proof.

#### 10. Concurrency / дублирующие действия
Что происходит при: двойном нажатии "Начать Proof", обновлении Mini App, закрытии приложения во время research, открытии на другом устройстве, retry после таймаута. Не должно возникать случайной дублирующей дорогой research-работы. Предложи стратегию идемпотентности для v1.

#### 11. Motion architecture vs Research state
UI-состояние не должно быть завязано на блокирующий API-запрос.
```
Хорошо: interaction → немедленный UI-отклик → research асинхронно → UI наблюдает состояние
Плохо:  interaction → ждём API → разблокируем UI
```
Найди места, где текущая архитектура этому противоречит.

#### 12. ARI future evolution
Не реализуя будущие фичи, проверь, что v1 не зашивает намертво:
- ровно одну тему навсегда
- фиксированное число CORE-проектов
- ровно один Pattern навсегда
- provider-специфичное поведение AI прямо в домене
- project-специфичную логику по всему Research Engine

## ПРАВИЛА РАБОТЫ

1. **Не задавай владельцу вопросы, которые решаются здравым инженерным суждением.** Продуктовые решения уже приняты — они в `01_LOCKED_DECISIONS.md`. Используй инженерное суждение там, где продуктовое намерение уже ясно.
2. **Не генерируй бесконечный список теоретических edge case.** Только то, что материально влияет на корректность, целостность данных, приватность, платежи, исполнение Research Job, надёжность Interpreter, производительность Mini App или способность развивать ARI дальше без переписывания фундамента.
3. **Не расширяй scope. Не перепроектируй продукт. Не вводи спекулятивную enterprise-архитектуру.**
4. Если реализация потребует изменить зафиксированную продуктовую концепцию — останови работу и выведи:
   **STRATEGY REVIEW REQUIRED**

Цель: построить наименьший технически прочный фундамент для уже определённого ATLAS PROOF v1.
