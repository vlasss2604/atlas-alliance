## 1. HIGH-находки

### HIGH-1. S5 не встроен в канонический путь исполнения — интеграция тест-only (направление 5)

Факты, каждый проверен по коду:

- `reconcileAndPersistComponent` (`src/server/engine/component-reconciliation-store.ts:122`)
  импортируется ровно одним файлом репозитория —
  `tests/phase6-s5-persistence.test.ts`. Ни один production-модуль его
  не импортирует.
- Контроллер получил *опциональный* хук
  `ControllerRunInput.reconcile` (`controller.ts:129`) и честно вызывает
  его после каждой попытки (`controller.ts:610-612`). Но единственная
  объявленная production-точка интеграции — `runS4ResearchJob`
  (`run-job.ts:72`) — вызывает
  `runResearchController({ db, jobId, view, executor, now })`
  **без** `reconcile`. Комментарий этого же файла (строки 20–23) прямо
  говорит: «so a future S5 slice has a single integration point to
  call» — S5 эту точку не обновил.
- `runS4ResearchJob` сам не имеет вызывающих (worker Фазы 5 запускает
  только `runMemoryPlanningStage`, `src/server/jobs/worker.ts`), что
  санкционировано заморозкой S4 (`research_enabled=false`). Но это
  означает: даже когда S10 включит исполнение, канонический путь в его
  нынешнем виде не произведёт ни одной строки
  `research_component_results`.

План §17 называет «интеграция с контроллером» частью порядка разработки
S5, а гейт §17.2 подразумевает работающий срез, а не only-via-tests хук.
Тест `tests/phase6-s5-persistence.test.ts:385-400` даже фиксирует
поведение «без хука — ни одной строки S5» — то есть текущее поведение
production-пути зафиксировано как *отсутствие* S5.

**Требуется:** передача `reconcileAndPersistComponent` в
`runResearchController` из `runS4ResearchJob` (или новое явное решение
владельца, где живёт связка), плюс тест, который проверяет именно
production-каллсайт, а не возможность хука.

### HIGH-2. Crash между терминальной записью попытки и персистенцией S5 теряет результат S5 навсегда (направление 4)

Трасса (все шаги по коду `controller.ts`):

1. Executor персистирует Evidence (внутри `executor.execute`,
   s4-executor).
2. Контроллер персистирует терминальный статус попытки
   (`controller.ts:582-602`, UPDATE `research_attempts` → `SUCCEEDED`).
3. **Crash здесь** — до `await reconcile(...)` (`controller.ts:610-612`).
4. Рестарт: `runResearchController` строит `pending` фильтром
   `!succeededKeys.has(key)` (`controller.ts:462-464`) — компонент со
   статусом SUCCEEDED исключается из цикла, хук `reconcile` для него
   больше **никогда** не вызывается. Ни в контроллере, ни в
   `run-job.ts`, ни где-либо ещё нет финальной свертки «реконсилировать
   все компоненты workQueue».

Проба DBP1 на реальном Postgres (хук, бросающий исключение после
терминального UPDATE — эквивалент смерти процесса; затем честный
рестарт с настоящим `reconcileAndPersistComponent`):

```
DBP1 rerun stopReason: WORK_QUEUE_EXHAUSTED attemptsThisRun: 0 s5 rows: 0
```

Evidence в БД есть, попытка SUCCEEDED есть, результата S5 нет и не
будет. Тот же разрыв воспроизводится без «crash»: любое исключение
внутри `reconcile` (например, zod-ошибка контента Pattern в
`loadPatternContentForJob`) наступает после того, как попытка уже
терминальна. Смежное следствие: путь `ALREADY_CLAIMED → continue`
(`controller.ts:517-522`) тоже пропускает реконсиляцию — компонент,
доведённый до SUCCEEDED другим инвокейшном, в этом инвокейшне
реконсилирован не будет.

План §12 обещает: «Падение между S5 и S6 безопасно: S6 читает строки».
Падение **между S4-попыткой и S5** не рассмотрено ни планом, ни кодом,
ни тестами — при том, что персистентность попыток строилась именно ради
resume (S3).

**Требуется:** идемпотентная свертка при завершении job'а (реконсиляция
всех (step, component) workQueue перед выходом или при resume), либо
вызов reconcile до/атомарно-с терминальным UPDATE попытки — плюс тест
именно этого сценария.

### HIGH-3. Вытеснение выполняется строками, неспособными устанавливать компонент (направление 2; нарушение D-093/D-094)

`component-reconciler.ts:377-391`: пул кандидатов вытеснения фильтруется
только по `normalizedState !== "UNKNOWN" && temporalBasis !== null`;
условие 4 (§8.1) реализовано `atLeastAsCapable(...)`
(`component-reconciler.ts:249-257`) как **чистое членство класса** в
`establishingClasses`. Ни `relationship`, ни `directness`, ни
`officiality` не участвуют.

Следствие: более новая строка допустимого класса, которая сама по себе
**ничего установить не может** (INFERRED; CONTEXT; LIMITS; INDIRECT),
вытесняет более старую DIRECT SUPPORTS установившую строку — та
получает `SUPERSEDED_BY_NEWER` и выпадает из установления, а «новая»
затем сама исключается (`DIRECTNESS_INSUFFICIENT` /
`RELATIONSHIP_NOT_SUPPORTING`). Компонент падает в
`INSUFFICIENT_EVIDENCE` или деградирует.

Пробы (чистая функция, MECHANISM_SPEC, establishing =
[OFFICIAL_DOCS, GOVERNANCE]; старая строка DIRECT SUPPORTS CONFIRMED
LIVE 2025; новая — 2026, state DEPRECATED):

| Проба | Новая строка | Результат | Ожидание по контракту |
|---|---|---|---|
| P1a | INFERRED SUPPORTS OFFICIAL_DOCS | `INSUFFICIENT_EVIDENCE` [`ALL_EVIDENCE_EXCLUDED`]; старая `SUPERSEDED_BY_NEWER`, новая `DIRECTNESS_INSUFFICIENT` | `SUPPORTED` |
| P1b | CONTEXT OFFICIAL_DOCS | `INSUFFICIENT_EVIDENCE` | `SUPPORTED` |
| P1c | LIMITS OFFICIAL_DOCS | `INSUFFICIENT_EVIDENCE` | `SUPPORTED` |
| P1d | INDIRECT CLAIMED OFFICIAL_DOCS | `PARTIALLY_SUPPORTED` [`INSUFFICIENT_AUTHORITY`,`INDIRECT_ONLY`] — установление держится на слабой строке, сильная вытеснена | `SUPPORTED` |

Почему это нарушение контракта, а не толкование:

- D-093 (каноника): условие 4 — «новый **не менее пригоден
  устанавливать именно этот компонент** по требованиям активного
  Pattern». «Пригодность устанавливать» определена §4 плана и включает
  `relationship = SUPPORTS` (условие 3) и `directness = DIRECT`
  (условие 4: «INFERRED не может ничего»).
- D-094 (каноника): «элемент недопустимого для компонента класса **или
  INFERRED** не отключает документально установленный механизм — иначе
  враждебная страница обесценивала бы выводы». Вытеснение здесь — ровно
  «отключение установленного механизма» элементом, который установить
  его не может. `mechanismState`, `publishedAt`, `directness`,
  `relationship` — выход модели-экстрактора S4 (`s4-executor.ts:547-570`),
  то есть данная поверхность действительно доступна враждебной странице
  на официальном домене.
- Комментарий в коде (`component-reconciler.ts:242-248`) осознанно
  выбирает «class-membership only», ссылаясь на буллеты §8.1a, — но
  буллеты §8.1a раскрывают частный случай (класс B вне множества), а не
  отменяют определение пригодности §4, на которое §8.1a сам ссылается
  («по требованиям активного Pattern (§4, §5)»).

Штатные тесты (мутации 6/23/23b) покрывают только случай «новый класс
вне establishingClasses» и не покрывают «новый класс допустим, но строка
не устанавливающая».

**Требуется:** условие 4 должно требовать полную пригодность B к
установлению (минимум `SUPPORTS` + `DIRECT` + допустимый класс; для
компонентов с §6-гейтами — и их), либо новое решение владельца, явно
сужающее §4 для целей вытеснения. Плюс дискриминирующие тесты P1a–P1d.

### HIGH-4. S5 читает произвольную строку Pattern, а не ACTIVE-версию (направление 6)

`component-reconciliation-store.ts:16-24`:

```ts
const [pattern] = await db.select().from(researchPatterns)
  .where(eq(researchPatterns.topicId, job.topicId));
```

— без фильтра `status = 'ACTIVE'`, без `ORDER BY`, берётся первая
строка. Схема `research_patterns` (`catalog.ts:58-`,
`uq_research_patterns_topic_version`) допускает много версий на топик;
уникален только ACTIVE (`uq_research_patterns_one_active`). Рядом
существует специально написанный для Фазы 6 ACTIVE-only lookup —
`loadActivePatternVersion` (`active-pattern.ts`), который S5-store **не
использует**, хотя план всюду говорит о «требованиях активного Pattern»
(§5, §8.1a, §11.1), а §12 объявляет «несовпадение `patternVersion`»
системным сбоем. Кросс-чека версии против `contract.patternVersion`
в S5-персистенции тоже нет (он есть только в `buildContractView`,
которая S5-store не проходит).

Проба DBP2 на реальном Postgres: v1 переведён в RETIRED, добавлен v2
ACTIVE, в котором `SOURCE_OF_VALUE.establishingClasses = []`:

```
DBP2 result with v1 RETIRED + v2 ACTIVE: SUPPORTED []
```

Реконсиляция прошла по **RETIRED v1** и установила компонент, который
действующий CORE устанавливать запретил. Порядок строк из heap'а не
гарантирован — результат ещё и недетерминирован между БД.

**Требуется:** выбор строго ACTIVE-строки (и/или строки той версии, под
которую заморожен контракт job'а) + жёсткий отказ при отсутствии/
несовпадении версии + тест с несколькими версиями Pattern.

### HIGH-5. Идентичность состояния токена подменена наличием квалификатора (направление 1; нарушение D-096)

Три независимых дефекта в одном механизме
(`component-reconciler.ts:120-172, 519-545`):

**(a) Канонический сценарий U падает.** `requiredTokenState`
сравнивается точным совпадением с *обнаруженным квалификатором*
(`"ve"`, `"staked"`, …), а не с идентичностью состояния токена. При
`requiredTokenState = "veCRV"` — ровно та форма, которую нормативный
§9.1 приводит как пример («Компонент, чьё требование прямо названо
`veCRV`») и которую сценарий U плана фиксирует буквально — совпадения
нет никогда:

```
P2a: requiredTokenState="veCRV", fragment "veCRV holders receive protocol fees"
→ PARTIALLY_SUPPORTED + TOKEN_STATE_UNQUALIFIED   (ожидание плана: SUPPORTED)
```

Это прямое нарушение уточнения владельца в D-096: «Требуемое состояние
явно то же — понижения нет» и «понижать за точность формулировки
запрещено». Существенно: **штатные тесты U/24/29 ослаблены** — в них
`requiredTokenState: "ve"` вместо планового `"veCRV"`, а тест I
ожидает `tokenStateMentions` содержащим `"ve"` вместо планового
`["veCRV"]`. Тесты подогнаны под реализацию, а не под контракт.

**(b) Разные ve-состояния слиты.** При `requiredTokenState = "ve"`
(единственная работающая форма) Evidence про **veBAL** проходит без
понижения там, где требование означало veCRV:

```
P2b: requiredTokenState="ve", fragment "veBAL holders receive protocol fees"
→ reasonCodes [] (понижения нет)
```

veCRV и veBAL — состояния разных токенов; квалификаторное сравнение
структурно не способно их различить. D-096: «разные состояния токена
никогда не сливаются как эквивалентные» — здесь слиты молча.

**(c) stkAAVE / stAAVE / stETH не обнаруживаются вовсе.** Закрытый
список квалификаторов содержит только словарные слова + fused-`ve`;
fused-«staked»-тикеры (каноника D-096 прямо называет
«`AAVE ≠ stkAAVE`») не детектируются:

```
P2c: fragment "stkAAVE holders receive safety incentives"
→ tokenStateMentions = [], понижения нет, SUPPORTED
P2d: fragment "stETH balances rebase daily…"
→ tokenStateMentions = []
```

То есть для самого именитого класса производных состояний S5 не
выполняет даже «обнаружение и перенос вперёд» — S6 не получит
наблюдения. Штатный тест V обходит проблему, используя текст
«staked AAVE» (раздельное слово) вместо тикера `stkAAVE` из плана.

**Требуется:** решение владельца о семантике `requiredTokenState`
(идентичность токен-состояния, а не квалификатор), извлечение
фактического квалифицированного тикера в `tokenStateMentions`
(vе-fusion уже умеет находить позицию — но выбрасывает сам тикер),
расширение закрытого списка fused-префиксов (`stk`, `st`, `w`, …) —
и восстановление тестов U/I/V/24/29 в плановой форме.

## 2. MEDIUM-находки

### MEDIUM-1. CONTRADICTED и метки relationship: обе стороны D-094 нарушены по-разному (направление 3)

`component-reconciler.ts:430-451`: пул противоречий — только
core-eligible DIRECT строки с состоянием ≠ UNKNOWN; конфликт — либо
разные состояния у двух SUPPORTS, либо **любая** пара
SUPPORTS/CONTRADICTS.

- **Фабрикация без конфликта состояний.** SUPPORTS(LIVE) +
  CONTRADICTS(**LIVE**) → `CONTRADICTED` (проба P6). Каноника D-094
  требует «машиночитаемые состояния несовместимы»; здесь терминальное
  CONTRADICTED создаётся *меткой relationship* (выход модели S4) при
  идентичных состояниях. Порог классов/DIRECT при этом соблюдён, так
  что дешёвой атаки «с любой страницы» нет, но на допустимом домене
  модель-экстрактор одной меткой останавливает компонент.
- **Подавление настоящего противоречия.** DIRECT CONTRADICTS
  допустимого класса CONFIRMED, но без `mechanism_state` (модель его не
  извлекла — штатная ситуация для «механизм отменён» без словарного
  состояния) молча исключается как `RELATIONSHIP_NOT_SUPPORTING`, и
  компонент остаётся SUPPORTED (проба P4a). Текст плана §7 (условие 2,
  вторая ветвь «либо один SUPPORTS, другой CONTRADICTS при сопоставимом
  классе») требования состояния для этой ветви не содержит.

План §7 и каноника D-094 здесь расходятся между собой; реализация не
совпадает ни с одной из них (у плана нет требования state-bearing для
ветви relationship; у каноники нет ветви relationship при равных
состояниях). Нужна диспозиция владельца, после неё — тесты на обе
стороны (сегодня ветка relationship не покрыта ни одним тестом — см.
MEDIUM-4/M5).

### MEDIUM-2. Партиция provenance нарушена: id одновременно «исключён» и «несёт противоречие» (направление 8)

Проба P3a: SUPPORTS(LIVE) + DIRECT CONTRADICTS(DEPRECATED), оба
допустимы → `CONTRADICTED`, и при этом CONTRADICTS-строка присутствует
**одновременно** в `contradictingEvidenceIds` и в `excludedEvidence`
с reason `RELATIONSHIP_NOT_SUPPORTING`
(`component-reconciler.ts:409-417`: строка кладётся в
`contradictionCapable` и тут же в `excluded`).

§10 определяет исключение как «элемент не участвует в этой
реконсиляции» — строка, породившая терминальное состояние, участвует
максимально. Для S6 и аудита («какое Evidence дало состояние»)
партиция supporting/contradicting/excluded перестаёт быть разбиением;
потребитель, полагающийся на дизъюнктность (например, при подсчёте
«сколько строк реально исключено»), получит двусмысленность.
Аналогично в SUPPORTED-исходе P4a: строка «не участвует» с кодом,
описывающим не причину непригодности, а роль (CONTRADICTS ≠
«not supporting» в смысле непригодности).

**Требуется:** либо отдельная категория вывода для
contradiction-bearing строк вне `excludedEvidence`, либо инвариант
дизъюнктности трёх множеств, закреплённый тестом.

### MEDIUM-3. Отсутствующий целиком `componentRequirements` неотличим от намеренно пустого; посев закрепляет это в проде (направление 7)

- `patternContentSchema.componentRequirements` — `.optional()`
  (`pattern.ts:98`); `componentRequirementsFor` возвращает
  `NO_REQUIREMENT` (в т.ч. `establishingClasses: []`) и для
  отсутствующего компонента, и для отсутствующего ключа целиком
  (`pattern.ts:123-137`).
- Проба DBP4 (реальный Postgres): контент Pattern **без**
  `componentRequirements` (ровно то, что лежит в БД, посеянной до S5) →
  `INSUFFICIENT_EVIDENCE` + `ALL_EVIDENCE_EXCLUDED`
  (`CLASS_NOT_ADMISSIBLE` для полноценной OFFICIAL_DOCS-строки) — без
  какого-либо сигнала о неполном CORE.
- `seed.ts:45-52` вставляет Pattern c
  `onConflictDoNothing({ target: [topicId, version] })`: существующая
  прод-БД при повторном посеве **не получит** новый контент с матрицей.
  Итог: на не-мигрированном CORE вся Фаза 6 будет молча выдавать
  «исследовали и не нашли» вместо «CORE не сконфигурирован для S5».

План действительно говорит «отсутствующий ключ означает отсутствующее
требование» (D-095) — на уровне *одного компонента* это осмысленно
(сценарий Y). Но неотличимость «CORE ещё не мигрирован» от «владелец
осознанно запретил все десять компонентов» противоречит §12
(«невалидный контракт/Pattern — системный сбой») по духу: конфигурация,
при которой ни один компонент Pattern v1 не может быть установлен
никогда, — не рабочее состояние CORE, а его отсутствие. Минимально:
различать «ключ `componentRequirements` отсутствует целиком» (hard
fail или явный код результата) от «отдельный компонент отсутствует»
(текущая семантика Y), и/или мигрировать посев (upsert контента для
ACTIVE v1). Требуется диспозиция владельца.

## 3. LOW-находки

### LOW-1. Конфликт состояний среди INDIRECT-строк невидим

Две INDIRECT SUPPORTS строки с LIVE и DEPRECATED →
`PARTIALLY_SUPPORTED` [`INDIRECT_ONLY`] (проба P4b), конфликт никак не
отражён (ни кода, ни упоминания). По D-094 (порог = установление) сам
отказ от CONTRADICTED защитим — INDIRECT не устанавливает полностью; но
при `requiresLiveMechanismState`/`requiresCurrentState` поле
`currentState` берётся из лучшей по §12-сортировке строки — то есть при
реальном конфликте партиальных источников состояние выбирается молча,
что план §8.1 называет недопустимым («молчаливый выбор строки»).
Дешёвое улучшение: не заполнять `currentState` при несогласных
состояниях партиальных строк.

### LOW-2. `tokenStateMentions` теряется на не-establishing исходах

Обнаружение ведётся только по устанавливающим строкам (санкционировано
§9 «которое действительно поддерживает компонент»), поэтому при
`CONTRADICTED` результат всегда несёт `tokenStateMentions: []`, даже
если обе конфликтующие строки говорят о квалифицированном состоянии.
Наблюдение, которое D-096 велит «переносить в S6 всегда», на этих
исходах не переносится. Осознать и задокументировать (или собирать
mentions и с contradiction-строк).

## 4. Что проверено и держится (подтверждаю явно)

- **Персистенция (направление 9).** Уникальная тройка
  `(research_job_id, pattern_step, component)` + upsert
  (`0014_s5_component_results.sql`, store): повторный прогон не плодит
  строк (штатный тест), три конкурентных
  `reconcileAndPersistComponent` сходятся к одной корректной строке
  (проба DBP3 — зелёная), delete + rerun даёт идентичный результат
  (штатный тест; чистота функции это гарантирует). FK cascade на job.
- **Детерминизм.** Полный порядок §12 реализован
  (`compareDeterministic`), дедуп выбирает представителя после
  сортировки — порядок входа не влияет (K, L2 — дискриминирующий);
  мутация M4 (нестрогая новизна) ловится.
- **Границы S5 §17.1 структурно соблюдены**: `reconcileComponent` —
  чистая функция без db/сети/модели; store пишет только
  `research_component_results`; Evidence и память не мутируются
  (штатные тесты 13/14/19/20 + структура кода). Инъекционная
  поверхность отсутствует: `fragment/summary` читаются лексически.
- **SOCIAL и счёт**: не устанавливает (B), не блокирует (R/10), счёт
  силы не даёт (S/2/16); `officiality` не пересчитывается; CLAIMED
  ограничивает до PARTIALLY (C/3) и не мешает противоречию (28).
- **Относительность авторитета компоненту** для случая «класс вне
  множества» работает и защищена настоящими зубами (W/X/6/23/23b, M1
  поймана). Дефект HIGH-3 — в другой оси (непригодность по
  relationship/directness).
- **Нормализация словаря** (D-094): точное совпадение, неопознанное →
  UNKNOWN, UNKNOWN не создаёт ни противоречия, ни состояния (Q/11);
  `PAUSED` включён; `currentState` в выводе — только нормализованный.
- **Контроллерная механика не ослаблена S5**: хук вызывается вне
  claim-транзакции, не влияет на бюджет/статусы/stop reason (штатный
  тест), FOR UPDATE-сериализация клеймов не тронута.
- **CURRENT_STATE-семантика**: окно свежести — свойство компонента из
  `memory_stale_after_days`; `fetched_at` принимается только для
  ONCHAIN_VERIFIABLE; stale → `STALE_CURRENT_STATE` (H/9); порядок
  «вытеснение → противоречие → установление» даёт F/G/W/X как в плане;
  проба P5a подтвердила, что новая непригодная строка не крадёт и не
  искажает reason-код stale-случая.
