## 1. Что заморожено

**S7 — Intent Sufficiency / Claim-Level Support.** Граница среза
объявлена и заморожена ровно так:

Вход:
- `normalized_intent`
- `task_type`
- CORE `IntentRequirementSet` (`Pattern.intentRequirements`, D-105)
- контекст Pattern/Contract, необходимый вычислителю
- `MechanismAssemblyResult` S6 и связанный вышестоящий provenance

Выход:
- детерминированный `ClaimSupportResult`
- персистированная проекция `research_claim_support`

S7 отвечает: **«удовлетворяет ли восстановленный механизм структурным
требованиям, связанным с этим исследовательским намерением?»**

S7 **не** выполняет проверку произвольной естественно-языковой
пропозиции. Это осознанная граница возможностей беты v1 (D-105, §3.3
`phase-6-s7-plan.md`), а не недоделка.

**S7 остаётся:** детерминированным, **model-free**, **network-free**,
ограниченным CORE-данными, связанным с provenance, воспроизводимым по
повтору.

## 2. Замороженные статусы

Статус утверждения задачи (`ClaimSupportResult.status`):

```
SUPPORTED · PARTIALLY_SUPPORTED · NOT_SUPPORTED · INSUFFICIENT_EVIDENCE
```

Статус атомарного требования (`ClaimRequirementResult.status`):

```
SATISFIED · PARTIAL · CONTRADICTED · UNSATISFIED
```

## 3. Замороженные семантические правила

| Правило | Формулировка |
|---|---|
| Источник семантики | `normalized_intent` → CORE `IntentRequirementSet` — единственный источник; свободный текст задачи семантическим входом не является |
| `claim_key` | не наделяется семантикой (D-060, D-068), в вход S7 не участвует вовсе |
| Числа/доли/кванторы/сила/полярность | не представлены в S7 v1 (D-109); соответствующие коды закрытого словаря структурно недостижимы, а не игнорируются эвристикой |
| `PARTIAL` | никогда не считается полным удовлетворением; `SUPPORTED` требует, чтобы **каждый** `REQUIRED`-атом был точно `SATISFIED` |
| `NOT_SUPPORTED` | требует **положительно установленной несовместимости** (§18 плана); отсутствие/`UNKNOWN`/неразрешённость/неполнота никогда не становятся опровержением (D-078) |
| Реляционные требования | требуют когерентной поддержки одним потоком S6 (D-108); распространено на весь составной набор `REQUIRED`-атомов, не только на один реляционный атом |
| Cross-flow cherry-picking | запрещён на уровне атома (D-108) и на уровне составного требования (расширение этого среза) |
| Ярлык механизма | не подразумевает экономический исход (`Mechanism Label ≠ Economic Outcome`, §17 плана) |
| Confidence | S7 confidence не порождает (D-110); детерминированная чистая функция от `ClaimSupportResult` — задача будущего Proof Core |
| Proof-проза | S7 не порождает объяснений, вердиктов на естественном языке, `ProofComposer`/`ProofFilter` |
| Мутация вышестоящих слоёв | S7 не мутирует Evidence, S5, S6, Research Memory |
| Модель/сеть | S7 не вызывает модель и не обращается к сети |

## 4. Потолки утверждения-пропозиции (D-106)

### `normalized_intent = CLAIM_FACT_CHECK`

```
ноль доказательств механизма  → INSUFFICIENT_EVIDENCE
есть доказательства механизма → максимум PARTIALLY_SUPPORTED
SUPPORTED                     → недостижимо в v1
NOT_SUPPORTED                 → структурно недостижимо для этого намерения,
                                 пока не существует структурированного
                                 набора требований
```

### `task_type = CLAIM_VERIFICATION`

```
нижележащий SUPPORTED            → потолок опускает до PARTIALLY_SUPPORTED
нижележащий INSUFFICIENT_EVIDENCE → без изменений
нижележащий NOT_SUPPORTED         → без изменений
```

Потолок применяется **независимо от кажущейся простоты** свободного
текста пропозиции; эвристического исключения нет и не появится (§3.2
плана).

## 6. Классификация долговечности (`DURABILITY_ESTABLISHED`)

`DURABILITY_ESTABLISHED` полностью реализован и протестирован (прямыми
переопределениями CORE в тестах), но **ни одно производственное
намерение** в `PATTERN_V1_CONTENT` его сейчас не объявляет.

**Финальная классификация: ПРИНЯТОЕ НЕЗАКРЫВАЮЩЕЕ ЗАМЕЧАНИЕ ПОКРЫТИЯ /
КОНФИГУРАЦИИ.**

Причина: решение о том, требует ли конкретное производственное
намерение долговечности — методологическое решение владельца CORE. S7
не вправе изобретать это требование самостоятельно.

## 7. Принятые LOW

**LOW 1.** `FLOW_IDENTITY_UNRESOLVED` специально сопоставлен только для
`valueSource`.

Принято, поскольку S6 сейчас порождает этот разрыв только для
`SOURCE_OF_VALUE`/`valueSource`. Если S6 в будущем расширит этот разрыв
на другие атрибуты, S7 может потребовать уточнения кодов причин.
Текущая семантика статусов безопасна.

**LOW 2.** Нет мутационного теста с реальным вызовом сети/модели на
появление такого вызова в S7.

Принято, поскольку граница S7 структурно свободна от модели/сети: нет
входа провайдера/модели, нет точки вызова сети, нет зависимости от
резолвера, отсутствие подтверждено статическим/исходным анализом
(grep-развёртка) на каждом раунде.

## 9. Правило freeze

**После этого freeze S7 НЕ переоткрывается ради:**

- косметических рефакторингов;
- более широких семантических классификаторов;
- «удобного» разрешения квантора/числа/силы;
- снятия потолка §3.2 для «очевидно простых» утверждений;
- отложенных LOW/NOTE из §5, §7;
- требований Proof Core, Claim Normalization, S8/S10, UI.

**S7 переоткрывается только при:**

1. воспроизведённом материальном регрессе против замороженного
   инварианта S7;
2. дефекте корректности или безопасности;
3. явном новом решении владельца, изменяющем D-105…D-111 или D-112;
4. бета-данных, показывающих, что отложенное ограничение материально
   блокирует корректное суждение о достаточности.

Любое будущее изменение замороженной семантики S7 требует явного нового
решения владельца и регрессионного ревью (D-112).

## 11. Наследство для S8 и далее

Будущие срезы получают `ClaimSupportResult`: детерминированный статус
утверждения задачи, атомарные результаты требований, provenance до
S6/S5/Evidence, закрытые коды причин.

Что последующие срезы обязаны сохранить:

1. **Не переоткрывать S7, S6, S5 и S4.** Каждый трогается только при
   воспроизведённом регрессе.
2. **`SUPPORTED` — не число и не проза.** Proof Core вправе рендерить,
   но не переопределять суждение S7.
3. **Отсутствие доказательства — не доказательство отсутствия.**
   `INSUFFICIENT_EVIDENCE` остаётся законным успешным исходом.
4. **Числа/кванторы/сила/полярность не досочиняются** — их появление
   требует отдельного контракта Claim Normalization и отдельного
   решения владельца.
5. **Confidence остаётся детерминированной функцией кода** (D-081) в
   Proof Core; модель число не называет.
6. **Живой гейт S10 не ослабляется** ради того, чтобы S7/Proof Core
   «увидели настоящие данные».
