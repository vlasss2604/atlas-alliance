## FIX BEFORE FREEZE

### HIGH-1 — вывод режима семантически небезопасен

Один закрытый шаг при семи неизвестных давал `TARGETED_REFRESH` и молча
снимал отчёт о границе доступа. Воспроизведено исполнением планировщика:
DEMO с 0 закрытых → граница срабатывает (8 записей `excludedScope`);
DEMO с 1 закрытым → граница молчит (0 записей), хотя 7 шагов без знания.

**Решение:** принято, D-058. Режим выводится из наличия `MISSING`-шагов.
`excludedScope`/`stopConditions` при зажатии заполняются всегда.

### HIGH-2 — `health` не влияет ни на что

Запись `lifecycle_state='ACTIVE'`, `health='DEPRECATED'`, confidence 95,
свежая — возвращается production-гейтвеем и закрывает шаг. Подтверждено
end-to-end. `grep` по `src/server` даёт только объявления схемы.

**Решение:** принято, D-059. `DEPRECATED` исключается из retrieval,
`QUESTIONABLE`/`REVERIFY`/`STALE` направляют перепроверку, но шаг не
закрывают.

### MEDIUM-2 — блокирующая метрика приёмки тавтологична

`falseReuseCount` считал только элементы с непромоутнутым `claimKey`, а
retrieval конструктивно возвращает лишь `ACTIVE` — метрика не могла стать
ненулевой. Опасный вид ложного переиспользования (закрытие шага
просроченным фактом) ею не измерялся вовсе.

**Решение:** принято, D-061. Семь причин непригодности, счёт по шагам.

### MEDIUM-3 — слепой оценщик не мог быть слепым

При `memory_enabled=false` все восемь шагов всегда `MISSING` — OFF-контракт
опознаётся структурно независимо от того, что скрыто. Дополнительно
`knownInformation` содержит тексты памяти и выдаёт происхождение прямо.

**Решение:** принято, D-063. Критерий переформулирован: судить качество
плана без утечки происхождения; `knownInformation` исключается из вида.

### MEDIUM-4 — `claim_key` не связан с шагом Pattern

Свободный текст, никакой валидации: `claim_key='economic_source'` с
`pattern_step=8` закрывает «Durability». Одна запись закрывает целый шаг
независимо от полноты покрытия.

**Решение:** принято как блокирующее, D-060. Компоненты шага, валидация
пары `(pattern_step, component)`, покрытие по всем компонентам.

### MEDIUM-5 — барьер промоушена только в приложении

Триггер проверяет `promoted_by IS NOT NULL`, но не роль актёра. Прямым SQL
доказано: обычный пользователь записывается как `promoted_by`, переход в
`ACTIVE` проходит. Роль проверяет только `assertAdmin` в коде.

**Решение:** принято, D-065. Обоснование прямое: D-010 требует инвариантов
в БД, а не в дисциплине кода; D-025 называет lifecycle **единственным**
барьером против отравления. Самое ответственное поле системы памяти — кто
санкционировал промоушен — не может быть защищено слабее остальных
инвариантов.

### MEDIUM-6 — агрегаты метрик завышены определением

`recall`/`precision` присваивались `1`/`1` при пустом ожидаемом множестве.
Пять сценариев из восьми имеют пустое ожидание, то есть отчётные
«recall = 1, precision = 1» более чем наполовину определительные.

**Решение:** принято, D-066. Усреднение только там, где метрика
определена; для негативных сценариев — отдельная метрика отсутствия
ложных срабатываний.

### LOW-2 — противоречивая ACTIVE-память закрывает шаг

Две записи `ACTIVE`, обе прошедшие health и свежесть, относящиеся к одному
шагу и несущие несовместимые утверждения, обе попадали в
`knownInformation`, и шаг при этом считался закрытым. Планировщик не имеет
понятия конфликта.

**Решение:** принято как блокирующее, D-062. Классифицировано по
серьёзности как LOW, но по последствию блокирует freeze: шаг, закрытый при
неразрешённом противоречии, — это ровно «плохая память → плохое
исследование», против чего строится вся фаза.

Правило: две записи `ACTIVE`, прошедшие health и свежесть, относящиеся к
одному `(pattern_step, component)` и несущие **различный
`mechanism_state`**, образуют конфликт. Шаг не может быть
`ALREADY_SATISFIED` — он получает `REQUIRED_FRESH` с причиной
`CONTRADICTED`, и конфликтующие `memoryId` остаются предъявимыми в
контракте. Противоречие разрешается свежим доказательством, а не выбором
«более уверенной» записи.

Граница правила: обнаруживается только конфликт состояний; расхождение
свободного текста `statement` конфликтом не считается.

### MEDIUM-1 — `stale_after` в месяцах и часах усекается в ноль

`EXTRACT(DAY FROM stale_after)` проверено: `'3 months'` → 0, `'1 year'` →
0, `'36 hours'` → 0. Ноль не является nullish, поэтому фолбэк из конфига
не срабатывает и запись становится вечно просроченной.

**Решение:** принято как обязательное сопутствующее. Фиксируемая
семантика свежести (D-059, D-061) без этого неисполнима: политика
свежести на уровне записи молча игнорируется, а направление отказа
безопасное — значит `false_reuse_rate` этого никогда не покажет.

### Блокер: `decideComponent()` строил конфликт только из `reusable`

`decideComponent()` вычислял множество для проверки противоречия
mechanism_state из `reusable` — записей, уже прошедших
`memory_min_confidence_reuse`. Свежая, health='OK' запись с confidence
НИЖЕ порога переиспользования молча выпадала из проверки конфликта ДО
сравнения состояний: планировщик "разрешал" противоречие выбором более
уверенной записи — ровно то, что D-062 запрещает прямым текстом
(«Противоречие разрешается свежим доказательством, а не выбором «более
уверенной» записи»). Обрыв порога был демонстрируем: конфликтующая
запись confidence=70 давала `CONTRADICTED`, confidence=69 — молча
исчезала, и шаг закрывался.

**Исправление.** Множество кандидатов на конфликт строится отдельно от
множества кандидатов на удовлетворение: право представлять текущее
состояние — `health='OK'` и не просрочено (то же самое условие, что уже
определяет ACTIVE-пригодность записи для D-059); `confidence` в это
множество не входит вовсе. `confidence` остаётся порогом ТОЛЬКО для
того, может ли запись САМА закрыть компонент — на удовлетворение
(`SATISFIED`) это исправление не влияет никак. Не вводит семантическое
обнаружение противоречий в свободном тексте — сравнение остаётся по
`mechanism_state`.

### LOW-находки повторного ревью — отложены с долгом

Не путать с LOW-2/LOW-4 первого ревью выше (другая нумерация, другой
раунд). Владелец подтвердил: не блокеры freeze Фазы 5.

- **LOW-1** — `promoted_by` можно переписать повторным `UPDATE` уже после
  промоушена (граф lifecycle это не запрещает — переход состояния уже
  произошёл, дальнейшее изменение поля `promoted_by` без изменения
  `lifecycle_state` не проходит через триггер перехода). Долг: либо
  запретить `UPDATE promoted_by` отдельным триггером/констрейнтом после
  первого выставления, либо явно задокументировать как admin-only
  операционное поле.
- **LOW-2** — `loadActivePattern()` (`plan-job.ts`) не фильтрует явно
  `status = 'ACTIVE'` в запросе к `research_patterns`, полагаясь на
  партиальный уникальный индекс «одна ACTIVE-версия» как единственную
  гарантию. Долг: добавить явный `WHERE status = 'ACTIVE'` — защита от
  будущего кода, который вставит не-ACTIVE версию без осознания
  инварианта.
- **LOW-3** — пустой список `requiredComponents` для шага (гипотетически,
  если будущий Pattern v2 допустит шаг без обязательных компонентов) даёт
  вакуумно `SATISFIED` (`components.every(...)` на пустом массиве истинно).
  Недостижимо в Pattern v1 (все 8 шагов имеют ≥1 компонент, см.
  `patternContentSchema`/`requiredComponentsSchema`), но не защищено явно.
  Долг: либо `min(1)` constraint на уровне схемы уже достаточен и
  оставить как есть, либо добавить явную защиту в планировщике при
  введении Pattern v2.
- **LOW-4** (повторного ревью, не путать с LOW-4 первого ревью выше про
  `research_plans.version`) — два значения `InvalidReason`
  (`WRONG_STEP_MAPPING`, `UNPROMOTED` пересекается с существующим
  покрытием, но конкретно `WRONG_STEP_MAPPING`) не имеют собственного
  golden-сценария, демонстрирующего их независимо. Долг: добавить
  сценарий, использующий `WRONG_STEP_MAPPING` как `invalidReason`, когда
  появится содержательный кейс (сегодня некорректное сопоставление
  `(pattern_step, component)` отклоняется на уровне БД и до retrieval не
  доходит вовсе — см. D-060 DB guard, `0008` — поэтому естественного
  runtime-пути для этой причины через golden set сегодня нет).
