## 0. Что реально доступно S7 (проверено по коду, не по плану)

Это определяет всё остальное, поэтому идёт первым, и здесь же лежит
главная находка среза.

### 0.1 Где в системе живёт «утверждение»

| Место | Что содержит | Машиночитаемо? |
|---|---|---|
| `research_jobs.original_question` | оригинальный вопрос пользователя verbatim | **нет**, свободный текст |
| `research_jobs.normalized_task` | `{ project_slug, project_slugs, task }` — `task` есть `research_task` интерпретатора, ≤400 символов, английский | **нет**, свободный текст |
| `interpretations.result` (jsonb) | полный `InterpreterModelResult` | **частично** |
| → `normalized_intent` | enum из 11 значений | **да** |
| → `task_type` | enum из 9 значений | **да** |
| → `user_assumptions[]`, `ambiguities[]` | свободный текст ≤200 символов | нет |
| `research_plans.contract` | `ResearchBoundaryContract` | да, но **утверждения не содержит вовсе** |

```ts
// src/server/interpreter/schema.ts — единственные машиночитаемые оси
RESEARCH_INTENTS = [
  "TOKEN_UTILITY", "PASSIVE_HOLDER_OUTCOME", "PROTOCOL_REVENUE_TO_TOKEN",
  "USAGE_TO_TOKEN_LINKAGE", "REWARD_SOURCE", "BURN_OR_SUPPLY_EFFECT",
  "MECHANISM_CURRENT_STATE", "VALUE_CAPTURE", "SCENARIO_CAUSAL_IMPACT",
  "CLAIM_FACT_CHECK", "UNKNOWN" ];

TASK_TYPES = [ "PROJECT_MECHANISM", "PROJECT_REVENUE", "TOKEN_VALUE", "RISK",
  "CLAIM_VERIFICATION", "COMPARISON", "CHANGE_OVER_TIME", "EXPLANATION",
  "OTHER_RESEARCH" ];
```

### 0.2 Главная находка — структурированного утверждения не существует

**Замороженная система не содержит машиночитаемого представления
утверждения.** Отсутствуют полностью:

- полярность (утверждение против отрицания);
- квантор (`все` / `большая часть` / `только` / `50%`);
- числовое значение и его единица;
- ожидаемый экономический исход;
- ожидаемое состояние токена;
- ожидаемый актор и действие;
- временна́я область (сейчас против исторического);
- сила утверждения (`сильно`, `материально`, `значительно`).

`ResearchBoundaryContract` — это раскладка **памяти по шагам Pattern**, а
не утверждение. Таблицы `research_results` не существует.

**Второе следствие, ещё важнее:** продукт в подавляющем большинстве
случаев получает **вопрос**, а не утверждение. «Доходит ли выручка
протокола до держателей?» — это вопрос; проверять его «достаточность для
утверждения» не к чему. Пропозиция появляется только при
`task_type = CLAIM_VERIFICATION` / `normalized_intent = CLAIM_FACT_CHECK`,
и даже там она остаётся свободным текстом.

Формулировать это прямо, а не обходить, — обязанность стратегии: **S7 в
том виде, в каком он описан задачей («достаточно ли механизма для
утверждения пользователя»), не реализуем на замороженных входах без
нового контракта утверждения.**

### 0.3 Что даёт S6

```ts
MechanismAssemblyResult { researchJobId, patternVersion,
  flows: MechanismFlow[], unassignedGaps: MechanismGap[] }

MechanismFlow { flowId, lineage, sharedPrefixId, branchPointStep,
  lifecycle: "CURRENT"|"HISTORICAL"|"NOT_ESTABLISHED",
  nodes, edges, shape: "COMPLETE_PATH"|"PARTIAL_PATH",
  attributes: { valueSource, direction, recipientKind, destinationKind,
                tokenState, assetSymbol },   // любое может быть UNKNOWN
  netEffect, durability, gaps: MechanismGap[] }
```

Все атрибуты потока — семантические и могут быть `UNKNOWN` (D-101).
Числовых фактов, долей и количеств нет **нигде** в цепочке S4→S5→S6.

### 0.4 Что уже ждёт на выходе

```sql
verdict ENUM = SUPPORTED | PARTIALLY_SUPPORTED | NOT_SUPPORTED
             | INSUFFICIENT_EVIDENCE | NOT_APPLICABLE
proofs.confidence smallint NOT NULL
```

Словарь вердикта Proof **уже существует** и отличается от словаря S5:
там `NOT_SUPPORTED`, а не `CONTRADICTED`. `confidence` объявлен
`NOT NULL` — значит число обязано существовать к моменту создания Proof
(§23).

## 3. Что именно судит S7 — три варианта и рекомендация

Вопрос §3 задачи решён здесь и **утверждён владельцем (D-105)**.

| Вариант | Содержание | Оценка |
|---|---|---|
| **A** | Pattern/Boundary Contract уже кодирует достаточно требований | **Отвергнут фактами.** Контракт не содержит утверждения ни в каком виде (§0.2) |
| **B** | Ввести новый детерминированный контракт `ClaimRequirement`, заполняемый пользователем или API | Архитектурно корректно, но **продуктовой поверхности для этого нет**: UI не собирает структурированное утверждение. Отложено до отдельного продуктового решения |
| **C** | **v1 ограничен требованиями, выводимыми из `normalized_intent`** — CORE-данные, автор-человек | **ПРИНЯТ** |

### 3.1 Принятый вариант C

S7 v1 судит **исследовательское требование задачи**, а не произвольную
пропозицию:

```
normalized_intent  →  IntentRequirementSet (CORE, человеческие данные)
                   →  детерминированная проверка против MechanismAssemblyResult
```

Почему это честно и почему этого достаточно для беты:

1. `normalized_intent` — **единственная существующая машиночитаемая ось
   намерения**, уже валидируемая контрактом интерпретатора.
2. Требования живут в CORE ровно как `componentRequirements` (D-095):
   человек их пишет, код потребляет и не изобретает.
3. Ни одно требование не выводится из свободного текста, значит модель
   не нужна (§27).
4. Это отвечает на реальные вопросы продукта («доходит ли выручка до
   держателя», «откуда берётся награда», «действует ли механизм сейчас»),
   которые и составляют домен Token Value Capture.

### 3.2 Жёсткое следствие — структурный потолок для проверки утверждений

При `task_type = CLAIM_VERIFICATION` либо
`normalized_intent = CLAIM_FACT_CHECK` пропозиция существует, но не
структурирована. Поэтому:

> **S7 v1 никогда не выдаёт `SUPPORTED` для таких задач.** Потолок —
> `PARTIALLY_SUPPORTED` с кодом `CLAIM_PROPOSITION_NOT_STRUCTURED`.

Потолок **структурный**, а не основанный на детекторе: он не зависит от
того, удалось ли распознать в тексте «50 %», «все» или «сильно».
Детектор мог бы промахнуться и выдать полную поддержку числовому
утверждению; структурный потолок промахнуться не может.

Это прямо закрывает пример владельца §1: «50 % выручки идёт на выкупы,
сокращающие предложение» не получит `SUPPORTED` ни при каком состоянии
механизма — потому что доля 50 % и сокращение предложения проверяются
разными механизмами, и первый из них в системе отсутствует.

**Обходить потолок запрещено.** Не разрешается определять, «выглядит ли
утверждение достаточно простым», и не разрешается снимать потолок для
«очевидных» утверждений. Эвристики здесь нет и не появится.

### 3.3 Продуктовая граница v1 — зафиксирована

> **S7 v1 — это INTENT-SUFFICIENCY JUDGMENT.** Это ещё **не** проверка
> произвольной естественно-языковой пропозиции.

S7 v1 отвечает: *«удовлетворяет ли восстановленный механизм структурным
требованиям, связанным с этим исследовательским намерением?»*

S7 v1 **не** заявляет: *«я полностью разобрал и проверил каждую
пропозицию, выраженную произвольным естественным языком»*.

Продукт содержит `research_task` (свободный текст) + `normalized_intent`
+ `task_type`, но **не содержит** структурированной пропозиции с
полярностью, квантором, числовым значением, ожидаемым актором, ожидаемым
состоянием токена, ожидаемым экономическим исходом, временно́й областью и
силой. Это осознанная граница возможностей беты v1, а не недоделка.

**Разбор утверждения внутри S7 прятать запрещено.**

### 3.4 Claim Normalization — отложенный архитектурный слой

Будущий переход

```
естественно-языковая пропозиция  →  структурированные ClaimRequirement[]
```

вводится **отдельным явным слоем Claim Normalization** перед S7, под
отдельным решением владельца. Он обязан ограничиваться и тестироваться
независимо. Модель со временем может **предлагать** структуру, но S7
обязан потреблять **валидированные структурированные требования**, а не
сырое суждение модели.

**Сейчас этот слой не реализуется.**

### 3.5 Следствие для позиционирования беты

Первая внутренняя альфа надёжно проверяет ограниченный набор намерений
Token Value Capture. До появления контракта структурированной пропозиции
её **нельзя** описывать — ни внутри, ни снаружи — как

> «Atlas умеет проверить любое утверждение о крипте на естественном
> языке».

Более узкая надёжная возможность предпочтительнее поддельной
универсальности.

## 4. Модель состояний поддержки

Симметрия с S5 проверена, а не принята по умолчанию, и **отвергнута
частично**: словарь берётся из уже существующего enum `verdict`, потому
что второй словарь истины рядом с ним породил бы расхождение при
рендеринге Proof.

Семантика заблокирована точно (D-107, уточнение владельца):

| Состояние | Условие входа |
|---|---|
| `SUPPORTED` | **все** `REQUIRED`-атомы положительно удовлетворены по точным правилам когерентного потока и области (§9, §10); потолок §3.2 не применяется |
| `PARTIALLY_SUPPORTED` | **как минимум один материальный `REQUIRED`-атом положительно установлен**, но полная требуемая конъюнкция не установлена — **при условии, что нет положительной несовместимости, доминирующей над тем самым атомом, который судится**; либо действует потолок §3.2 |
| `INSUFFICIENT_EVIDENCE` | требуемая пропозиция не может быть установлена, потому что доказательства или структура **отсутствуют, не разрешены, `UNKNOWN`, неполны либо неисчерпывающи** |
| `NOT_SUPPORTED` | **положительно установленная несовместимость** с требованием (§18) — и только она |

Оговорка «доминирующей над тем самым атомом» существенна: положительная
несовместимость по атому **A** не оставляет атом A в `PARTIAL` —
она делает его `CONTRADICTED`. Частичность допустима только там, где
установленный атом не опровергнут по себе.

`NOT_APPLICABLE` в S7 не выдаётся: задача, не относящаяся к области,
отсекается раньше (`OUT_OF_SCOPE`, D-006) и до сборки не доходит.
Значение остаётся в enum для Proof, но S7 его не порождает.

Ответы на вопросы §5 задачи:

- **Может ли структурно полное быть экономически опровергнутым?** Да —
  `COMPLETE_PATH` + `NOT_SUPPORTED` возможны одновременно, если поток
  полон, но его атрибуты положительно несовместимы с требованием (§18).
- **Может ли `UNKNOWN` обязательного звена лишить поддержки?** Да —
  `UNKNOWN` не удовлетворяет требование никогда.
- **Может ли составное утверждение быть частично поддержано?** Да, §9.
- **Требует ли `NOT_SUPPORTED` положительного контрдоказательства?** Да,
  безусловно (§18).
- **«Не доказано» остаётся `INSUFFICIENT_EVIDENCE`**, а не
  `NOT_SUPPORTED`. Это D-078 на уровне задачи.

## 5. Декомпозиция на атомы

Требование задачи раскладывается на **атомарные требования**, каждое из
которых проверяется отдельно и предъявляется в выводе.

```ts
type RequirementKind =
  | "COMPONENT_ESTABLISHED"     // компонент установлен на релевантном потоке
  | "FLOW_RELATIONSHIP"         // источник → получатель в ОДНОМ потоке
  | "FLOW_ATTRIBUTE"            // атрибут потока равен требуемому значению
  | "NET_EFFECT_ESTABLISHED"    // исход установлен, а не назван ярлыком
  | "LIFECYCLE"                 // временна́я область потока
  | "DURABILITY_ESTABLISHED";   // основание долговечности

interface ClaimRequirement {
  requirementId: string;        // стабильный, из CORE
  kind: RequirementKind;
  optionality: "REQUIRED" | "OPTIONAL";
  components?: string[];              // для COMPONENT_ESTABLISHED
  relationshipFrom?: string;          // для FLOW_RELATIONSHIP
  relationshipTo?: string;
  attribute?: "valueSource" | "direction" | "recipientKind"
            | "destinationKind" | "tokenState";
  expectedValues?: string[];          // закрытые словари S6
  expectedLifecycle?: "CURRENT" | "HISTORICAL";
}
```

Шесть видов — минимальный набор, каждый из которых выводится из
существующих полей S6. Полей `requiredQuantity` и `polarity` в v1 **нет**:
им нечем питаться (§17, §8).

Пример владельца — «выручка протокола идёт на выкупы, сокращающие
предложение» — раскладывается на четыре атома, и три из них проверяемы:

```
R1 COMPONENT_ESTABLISHED   [SOURCE_OF_VALUE]              REQUIRED
R2 FLOW_RELATIONSHIP       SOURCE_OF_VALUE → DESTINATION  REQUIRED
R3 FLOW_ATTRIBUTE          destinationKind ∈ {BUYBACK_HOLD, BURN}  REQUIRED
R4 NET_EFFECT_ESTABLISHED                                 REQUIRED
```

Доля «50 %» атомом не становится — её не из чего построить.

## 6. Источник требований

**CORE, как и требования компонентов (D-095).** `research_patterns.content`
получает аддитивный ключ `intentRequirements`, ключ — значение
`normalized_intent`:

```ts
intentRequirements: Record<ResearchIntent, {
  requirements: ClaimRequirement[];
  ceiling?: "PARTIALLY_SUPPORTED";   // §3.2
}>
```

Дисциплина копирует D-095 целиком: расширение аддитивно; поведение
планировщика Фазы 5 не меняется; `eval:memory` идентичен; отсутствующий
ключ — **ошибка конфигурации**, а не пустое требование (иначе «CORE не
настроен» превратилось бы в «исследовали и не нашли» — ровно та ошибка,
которую закрыл MEDIUM-3 аудита S5).

`normalized_intent = UNKNOWN` — не ошибка конфигурации, а явный
`INSUFFICIENT_EVIDENCE` с кодом `INTENT_NOT_CLASSIFIED`.

**`claim_key` семантикой не наделяется** (D-060, D-068): он остаётся
идентификатором и во входе S7 не участвует вовсе.

## 7. Полярность

**v1 поддерживает только положительные требования.**

Отрицательное утверждение («держатели не получают выручку», «токены не
сжигаются») требует **положительно установленного несовместимого
состояния** — то есть той же машинерии `NOT_SUPPORTED` (§18), а не
отсутствия доказательства. Поскольку структурированной полярности во
входах нет (§0.2), v1 не пытается её определить: поле `polarity` не
вводится, отрицательные формулировки судятся как положительные
требования соответствующего намерения, а их специфика попадает под
потолок §3.2.

D-078 сохраняется буквально: **отсутствие доказательства никогда не
поддерживает отрицательное утверждение.**

## 8. Правило достаточности

```
Требование задачи = R1 ∧ R2 ∧ … ∧ Rn   (только REQUIRED)

SUPPORTED  ⟺  ∀ Ri ∈ REQUIRED : satisfied(Ri) = SATISFIED
              ∧ потолок §3.2 не применяется
```

**Усреднения нет. «3 из 4» полной поддержкой не является.** `OPTIONAL`
требование не блокирует полную поддержку, но и не заменяет
`REQUIRED`. Взвешенной нечёткой достаточности не существует.

Статус атома — закрытый: `SATISFIED` · `PARTIAL` · `CONTRADICTED` ·
`UNSATISFIED`. Атом `PARTIAL` (например, компонент пришёл из S5
`PARTIALLY_SUPPORTED`) полной поддержки не даёт, но и не опровергает.

---

## 9. Требование когерентного потока

> **Реляционное требование удовлетворяется одним когерентным потоком S6
> либо не удовлетворяется вовсе.**

Запрещено собирать синтетическое доказательство из разных потоков:
источник из потока A + исполнение из потока B + чистый эффект из потока C.
Единственное исключение — когда S6 **явно** установил общую родословную
(`sharedPrefixId`), и тогда общей является только префиксная часть.

Пример, который обязан проваливаться:

```
Поток A: выручка → казначейство
Поток B: эмиссия → стейкеры
Требование: «выручка распределяется стейкерам» → НЕ удовлетворено
```

Оба факта существуют; отношения между ними нет. Это `Reward ≠ Revenue`,
`Same Asset ≠ Same Economic Flow` и `System Utility ≠ Passive Holder
Capture` одним структурным правилом. Зубы — мутации 9, 42, 47, 48.

**Существование двух фактов не является отношением.** Совпадение тикера
отношением не является тем более.

---

## 10. Релевантность разрывов

«Любой разрыв где угодно → недостаточно» запрещено: разрыв на
несвязанном параллельном потоке не имеет отношения к требованию.

**Правило:** разрыв блокирует требование тогда и только тогда, когда он
лежит на **том же потоке**, который претендует удовлетворить требование,
и на **позиции Pattern, входящей в это требование**.

| Разрыв S6 | Действие при попадании на релевантный путь |
|---|---|
| `MISSING_COMPONENT` | атом `UNSATISFIED`, код `REQUIRED_COMPONENT_MISSING` |
| `PARTIAL_COMPONENT` | атом `PARTIAL`, код `REQUIRED_PATH_PARTIAL` |
| `CONTRADICTED_COMPONENT` | атом `CONTRADICTED`, код `REQUIRED_PATH_CONTRADICTED`; победитель не выбирается |
| `TOKEN_STATE_MISMATCH` | атом `CONTRADICTED`, код `TOKEN_STATE_MISMATCH` (§13) |
| `TEMPORAL_STATE_MISMATCH` | атом `UNSATISFIED`, код `TEMPORAL_SCOPE_MISMATCH` |
| `NET_EFFECT_UNRESOLVED` | атом `UNSATISFIED`, код `NET_EFFECT_NOT_ESTABLISHED` |
| `RECIPIENT_UNRESOLVED` / `DESTINATION_UNRESOLVED` | атом `UNSATISFIED`, код `REQUIRED_RELATIONSHIP_UNRESOLVED` |
| `FLOW_IDENTITY_UNRESOLVED` | атом `PARTIAL`, код `FLOW_IDENTITY_UNRESOLVED` |
| `BRANCH_ATTRIBUTION_UNRESOLVED` | атом `UNSATISFIED`, код `BRANCH_ATTRIBUTION_UNRESOLVED` — привязка недоказана, значит отношение недоказано |
| `FLOW_ENUMERATION_INCOMPLETE` | атом не блокируется, но **исчерпывающие требования недостижимы**, код `FLOW_ENUMERATION_INCOMPLETE` |

Разрывы вне релевантного пути записываются в вывод как контекст и
статуса не меняют (сценарий M, мутация 18).

---

## 11. Множественные потоки

Требование, удовлетворённое **любым** когерентным потоком, считается
удовлетворённым: экзистенциальная семантика — единственная, которую
можно честно проверить.

**Исчерпывающие требования («вся выручка», «только», «100 %») в v1
недостижимы**: доказать полноту перечисления потоков нельзя — S6 сам
объявляет `FLOW_ENUMERATION_INCOMPLETE` там, где перечисление оборвано, а
отсутствие такого разрыва не доказывает, что других потоков не
существует. Это `Absence of Mechanism Is a Valid Finding` в обратную
сторону, и подделывать его запрещено. Такие формулировки попадают под
потолок §3.2.

---

## 12. Состояние токена

Требование `FLOW_ATTRIBUTE` по `tokenState` сравнивается **точным
нормализованным равенством**, семантической эквивалентности S7 не
выводит (наследование D-096 и D-101).

Разбор случая владельца:

| Требование | Что установил S6 | Исход |
|---|---|---|
| `veCRV` | `veCRV` | `SATISFIED` |
| `CRV` (ликвидный, явно требуемый) | `veCRV` | **`CONTRADICTED`** — положительно установлен иной квалифицированный получатель |
| любой | `tokenState = null` | `UNSATISFIED`, не `CONTRADICTED` |

Различие принципиально: `veCRV` против явно требуемого ликвидного `CRV` —
это **не отсутствие доказательства о ликвидном CRV**, а положительное
доказательство другого получателя. Отсутствие же упоминания состояния
даёт неопределённость, а не конфликт — это прямое продолжение принятого
правила S6 (freeze §5): несовпадение требует **двух положительно
представленных** идентичностей.

Обобщение `veCRV → CRV holders` запрещено (мутация 7).

---

## 13. Actor × Action

Актор в v1 представлен `recipientKind` — закрытым словарём S6.
Требование `FLOW_ATTRIBUTE` по `recipientKind` проверяется точным
совпадением значения.

`PASSIVE_HOLDER` **никогда не выводится из отсутствия** и никогда — из
того, что токен кому-то нужен. Разбор случая LINK:

```
Требование «конечный пользователь обязан держать токен»
  ← recipientKind = NODE_OPERATOR   → НЕ удовлетворено
  ← абстракция платежа              → НЕ удовлетворено
Требование «токен остаётся в расчётном пути»
  ← установленный поток с этим токеном → может быть удовлетворено
```

`Abstraction ≠ Removal` и `System Utility ≠ Passive Holder Capture`
работают одним и тем же правилом: сравнивается **точное требуемое
значение**, а не «токен как-то используется». Свободного имени актора в
S6 нет, поэтому более тонкие требования об акторе в v1 честно
недостижимы и дают `UNSATISFIED`, а не догадку (мутации 8, 24).

## 14. Временна́я область

`LIFECYCLE`-требование сравнивается с `MechanismFlow.lifecycle`, который
S6 уже вычислил.

| Требуется | `lifecycle` потока | Исход |
|---|---|---|
| `CURRENT` | `CURRENT` | `SATISFIED` |
| `CURRENT` | `HISTORICAL` | `UNSATISFIED`, `TEMPORAL_SCOPE_MISMATCH` |
| `CURRENT` | `NOT_ESTABLISHED` | `UNSATISFIED` |
| `HISTORICAL` | `HISTORICAL` или `CURRENT` | `SATISFIED` |

Текущее утверждение **никогда** не поддерживается историческим или
устаревшим механизмом (мутации 13, 44). Время требования берётся из
`IntentRequirementSet` в CORE — из свободного текста грамматическое
время не разбирается: `MECHANISM_CURRENT_STATE` требует `CURRENT` по
определению намерения, остальные намерения в v1 требуют `CURRENT` по
умолчанию CORE, и это решение человека, а не разбор прозы.

---

## 15. Долговечность

`DURABILITY_ESTABLISHED` — требование **опциональное по умолчанию** и
становится `REQUIRED` только там, где CORE это объявил. Разрыв
долговечности не блокирует поддержку требования, которое долговечности не
требует.

Формулировки «навсегда», «гарантированно», «программно» в v1 из текста не
распознаются — они попадают под потолок §3.2. Нечёткой семантической
интерпретации не вводится.

---

## 16. Числа, доли, кванторы, сила

**Нормализованных числовых фактов в системе нет ни на одном слое**: ни S4
их не извлекает, ни S5 не хранит, ни S6 не собирает.

Отсюда закрытое и жёсткое правило v1:

> **Точные числовые, долевые, квантифицированные и силовые утверждения
> не поддерживаются никогда.**

```
«50 % выручки идёт на выкупы»    → механизм выкупа может быть установлен,
                                    доля 50 % — нет
«18,48 % предложения выкуплено»   → не поддерживается «выкупы происходили»
«$200M ежегодно»                  → не поддерживается
«вся выручка распределяется»      → §11, исчерпывающая полнота недостижима
«токен сильно захватывает ценность» → «сильно» не поддерживается
                                    (`Existence ≠ Strength`)
```

Разбор прозы в авторитетные числа внутри S7 **запрещён**: заблокированного
детерминированного контракта числового извлечения не существует, и
создавать его в S7 значило бы поставить самый ненадёжный слой в основание
самого сильного утверждения. Коды: `NUMERIC_VALUE_NOT_ESTABLISHED`,
`QUANTIFIER_NOT_ESTABLISHED`, `STRENGTH_NOT_ESTABLISHED`.

---

## 17. Ярлык ≠ исход

`Mechanism Label ≠ Economic Outcome` реализуется структурно:

| Требование | Чем удовлетворяется | Чем **не** удовлетворяется |
|---|---|---|
| «протокол делает выкупы» | `EXECUTION_EVIDENCE` на потоке | — |
| «выкупы сокращают предложение» | `NET_EFFECT_ESTABLISHED` | `destinationKind = BURN`; словом «burn» в тексте |
| «награды стейкинга идут из выручки» | `FLOW_RELATIONSHIP` источник→получатель в одном потоке | раздельным существованием наград и выручки |
| «100 % выручки идёт держателям» | недостижимо (§11, §16) | — |

`NET_EFFECT` берётся у S6 и не пересчитывается (мутации 5, 6, 26).

## 18. Противоречие на уровне задачи

`NOT_SUPPORTED` требует **положительно установленной несовместимости**:

1. атрибут релевантного потока установлен (`≠ UNKNOWN`) **и** входит в
   закрытый словарь **и** не совпадает с требуемым значением; либо
2. релевантный компонент пришёл от S5 как `CONTRADICTED`; либо
3. `lifecycle = HISTORICAL` при требовании `CURRENT` **и** установленном
   `DEPRECATED`/`REMOVED`.

### 18.1 Закрытый список того, чем `NOT_SUPPORTED` не является (нормативно)

`NOT_SUPPORTED` **никогда** не означает всего лишь:

```
отсутствующее доказательство · UNKNOWN · неразрешённая привязка ветви
отсутствующий NET_EFFECT · отсутствующий числовой факт
отсутствующий квантор · невозможность разобрать пропозицию
невозможность доказать отрицание
```

Ни одно из девяти не является положительной несовместимостью. Если у
обязательного атома нет **положительной противоречащей структуры**,
исход по умолчанию — `INSUFFICIENT_EVIDENCE` либо `PARTIAL` по закрытым
правилам §4 и §10, **никогда** `NOT_SUPPORTED`.

`Отсутствие доказательства ≠ доказательство отсутствия` (D-078)
сохраняется буквально на уровне задачи. Зубы — мутации 16, 17, 41, 51.

Разбор примера владельца: требование «купленные токены сжигаются» при
`destinationKind = TREASURY` и установленном `NET_EFFECT` без сжигания —
`NOT_SUPPORTED`; при разрыве `DESTINATION_UNRESOLVED` —
`INSUFFICIENT_EVIDENCE`.

## 19. Частичная поддержка

`PARTIALLY_SUPPORTED` возникает по двум структурно разным причинам, и они
**различимы кодом**:

| Причина | Код |
|---|---|
| часть обязательных атомов удовлетворена, часть нет | `REQUIRED_ATOM_UNSATISFIED` |
| атом удовлетворён, но сам пришёл из S5/S6 `PARTIAL` | `REQUIRED_PATH_PARTIAL` |
| действует структурный потолок §3.2 | `CLAIM_PROPOSITION_NOT_STRUCTURED` |

Как и в S5, `PARTIALLY_SUPPORTED` без кода из закрытого списка
невозможен и мусорной корзиной не является.

## 21. Схема результата

```ts
interface ClaimSupportResult {
  researchJobId: string;
  patternVersion: number;
  intent: ResearchIntent;
  requirementSetVersion: number;
  status: "SUPPORTED" | "PARTIALLY_SUPPORTED"
        | "NOT_SUPPORTED" | "INSUFFICIENT_EVIDENCE";
  reasonCodes: ClaimReasonCode[];        // закрытый §20, для не-SUPPORTED непуст
  requirementResults: ClaimRequirementResult[];
  contextGaps: MechanismGapRef[];        // разрывы вне релевантного пути
}

interface ClaimRequirementResult {
  requirementId: string;
  optionality: "REQUIRED" | "OPTIONAL";
  status: "SATISFIED" | "PARTIAL" | "CONTRADICTED" | "UNSATISFIED";
  reasonCodes: ClaimReasonCode[];
  matchedFlowIds: string[];              // отсортированы
  blockingGaps: MechanismGapRef[];
  provenance: ClaimProvenance;
}
```

Числа `confidence` в схеме **нет** (§23). Полей с именами `verdict`,
`proven`, `probability` нет — вердикт Proof выводится из `status` в
Proof Core и не пересчитывается (§26).

## 22. Provenance

```
ClaimRequirementResult
  → matchedFlowIds → MechanismFlow / MechanismGap (S6)
  → lineage.componentResultKey → ComponentReconciliationResult (S5)
  → evidenceIds → evidence.id → retrieved_url + content_hash
```

Каждое `SATISFIED`/`PARTIAL`/`CONTRADICTED` требование обязано нести
непустой provenance; отсутствие — нарушение инварианта и системный сбой
(§25). `UNSATISFIED` несёт `blockingGaps`, что тоже является provenance
отсутствия.

**S7 не цитирует и не пересуживает Evidence.** Текст в вывод не
копируется; прозу построит Proof Core по этим же идентификаторам.

## 23. Confidence под D-081

**Рекомендация: числа в S7 нет.**

- Информации сверх `status` + закрытых кодов + результатов атомов число
  не добавляет: количественных входов в системе нет (§16), поэтому любая
  формула была бы перекодировкой уже имеющихся состояний — то есть
  косметикой, которую задача прямо запрещает.
- Дублирование S5 реально: авторитет источников уже учтён в статусах
  компонентов, повторный их пересчёт создал бы вторую систему истины.
- **Но `proofs.confidence` объявлен `NOT NULL`**, значит число обязано
  существовать к моменту создания Proof.

Поэтому: **число вычисляется в Proof Core как чистая детерминированная
функция от `ClaimSupportResult`** — рендеринг, а не суждение. Формула
блокируется отдельным решением (**D-110**) вместе со срезом Proof Core.
D-081 соблюдён: функция кода, модель числа не называет, вероятностей
модели нет.

## 24. Персистенция

Производная проекция `research_claim_support`, ключ
`(research_job_id, pattern_version, requirement_set_version)`.

Источник истины остаётся: `intentRequirements` (CORE) + S6 + вышестоящий
provenance. Удаление и пересчёт из тех же замороженных входов дают
семантически идентичный результат. Upsert, replay-безопасно,
конкурентно-безопасно. Записей в память нет, Evidence не мутируется.

`requirement_set_version` в ключе нужен потому, что человек может
изменить требования CORE, не меняя `patternVersion`; без него старый
результат молча выдавался бы за новый.

---

## 25. Сбой против неустановленности

**Успешные исходы:** `SUPPORTED`, `PARTIALLY_SUPPORTED`,
`NOT_SUPPORTED`, `INSUFFICIENT_EVIDENCE`. Ни один не является сбоем job'а.

**Системный сбой — закрытый список:**

1. отсутствие `intentRequirements` для намерения (ошибка конфигурации
   CORE, не вывод);
2. расхождение `patternVersion` между контрактом, S6 и S7;
3. невозможный инвариант S6 (дубль `flowId`, узел без provenance);
4. требование `SATISFIED` без provenance;
5. висячая ссылка на `flowId` или результат S5;
6. ошибка БД.

**Replay.** S6 собран → падение до S7 → перезапуск обязан вывести S7 из
замороженной проекции: **без нового поиска, без открытия источников, без
модельной стоимости, без фиктивных попыток**. Системный сбой S7 не
разрушает проекцию S6.

## 26. Граница S7 / Proof Core

| Слой | Вопрос | Выход |
|---|---|---|
| S6 | какой механизм собирается | `MechanismAssemblyResult` |
| **S7** | отвечает ли механизм требованию задачи | `ClaimSupportResult.status` |
| Proof Core | как это показать человеку | `verdict` + `confidence` + слои |

**Двух систем истины не будет.** Proof Core **не переинтерпретирует**
истину: он детерминированно проецирует `status` в `verdict` и вычисляет
`confidence` по заблокированной формуле. Проза, редактура и Proof Map —
целиком там, в S7 их нет ни в каком виде.

## 27. Детерминизм и отсутствие модели

Те же требования, Pattern, Boundary Contract и сборка S6 → тот же
`ClaimSupportResult`, независимо от порядка БД, порядка потоков, разрывов
и Evidence.

| Коллекция | Ключ сортировки |
|---|---|
| `requirementResults` | `requirementId` |
| `matchedFlowIds` | `flowId` лексикографически |
| `reasonCodes` | фиксированный порядок словаря §20 |
| `blockingGaps` / `contextGaps` | `afterStep` → `kind` → `component` |

**Модели в S7 нет.** Все правила структурны: сравнение enum'ов, равенство
нормализованных строк, проверка принадлежности потоку, сортировка.
Свободный текст `research_task` **не читается вовсе** — ни детектором,
ни иначе; потолок §3.2 структурен. Значит поверхности prompt-инъекции в
срезе нет, сети нет, бюджета S7 не тратит.

Если владелец впоследствии захочет судить произвольные утверждения, это
**отдельный слой Claim Normalization** перед S7 (модель предлагает
структуру, код и человек её валидируют), а не вызов модели внутри S7.

## 28. Область беты v1

Намерения, для которых `IntentRequirementSet` пишется в CORE:

| Намерение | Ядро требования |
|---|---|

## 32. Утверждённые решения

Все семь приняты владельцем 2026-08-22 на коммите стратегии `3cf8f74`.
D-107 принято **с уточнением**, внесённым в §4 и §18.1 как нормативное.
Канонические формулировки — в `docs/DECISIONS.md`.

| ID | Решение | Статус |
|---|---|---|
| **D-105** | **S7 v1 судит структурированный набор требований намерения.** Канонический источник: `normalized_intent` → детерминированный `IntentRequirementSet` в CORE / Pattern-управляемых данных. Притворяться, будто произвольный текст задачи уже является машиночитаемой пропозицией, запрещено. S7 v1 отвечает: «удовлетворяет ли восстановленный механизм структурным требованиям этого исследовательского намерения?» и **не** заявляет, что полностью разобрал и проверил каждую пропозицию произвольного естественного языка. Это намеренная граница возможностей беты v1. `claim_key` семантикой не наделяется (D-060, D-068) | **LOCKED** |
| **D-106** | **Структурный потолок для проверки утверждений.** Для `CLAIM_VERIFICATION` и `CLAIM_FACT_CHECK` пропозиция остаётся свободным текстом, поэтому S7 v1 **никогда** не возвращает полную поддержку самой пропозиции: максимум — `PARTIALLY_SUPPORTED` с кодом `CLAIM_PROPOSITION_NOT_STRUCTURED`. Потолок **структурный, а не эвристический**: определять, «выглядит ли текст утверждения достаточно простым», запрещено, обходить потолок для «очевидных» утверждений запрещено. Полная проверка утверждений в будущем требует явного контракта Claim / слоя Claim Normalization под отдельным решением владельца | **LOCKED** |
| **D-107** | **Словарь и точная семантика состояний.** Используется существующий канонический словарь вердикта (`SUPPORTED`, `PARTIALLY_SUPPORTED`, `NOT_SUPPORTED`, `INSUFFICIENT_EVIDENCE`); второй конкурирующий словарь истины не создаётся. Семантика заблокирована точно: `SUPPORTED` — все `REQUIRED`-атомы положительно удовлетворены по точным правилам когерентного потока и области; `PARTIALLY_SUPPORTED` — как минимум один **материальный** `REQUIRED`-атом положительно установлен, полная требуемая конъюнкция не установлена, **и нет положительной несовместимости, доминирующей над самим судимым атомом**; `INSUFFICIENT_EVIDENCE` — пропозиция не может быть установлена, потому что доказательства или структура отсутствуют, не разрешены, `UNKNOWN`, неполны либо неисчерпывающи; `NOT_SUPPORTED` — **только положительно установленная несовместимость** с требованием. `NOT_SUPPORTED` **никогда** не означает всего лишь отсутствующее доказательство, `UNKNOWN`, неразрешённую привязку ветви, отсутствующий `NET_EFFECT`, отсутствующий числовой факт, отсутствующий квантор, невозможность разобрать пропозицию или невозможность доказать отрицание. Нет положительной противоречащей структуры — исход по умолчанию `INSUFFICIENT_EVIDENCE` либо `PARTIAL` по закрытым правилам, никогда `NOT_SUPPORTED`. `Отсутствие доказательства ≠ доказательство отсутствия` (D-078) сохраняется | **LOCKED** (уточнено) |
| **D-108** | **Требование когерентного потока.** Реляционные требования удовлетворяются **одним** когерентным потоком S6, если контракт требования явно не разрешает агрегацию. Cherry-picking запрещён: источник из потока A + получатель из потока B + исход из потока C синтетической поддержки не создают. `выручка → казначейство` вместе с отдельным `эмиссия → стейкеры` **не** поддерживает «выручка распределяется стейкерам». Когерентная родословная S6 обязательна | **LOCKED** |
| **D-109** | **Числа, кванторы, сила и полярность вне области v1.** S7 v1 не заявляет поддержку точных числовых значений, процентов, квантифицированных утверждений, исчерпывающей семантики «вся / только / большая часть», утверждений силы (`сильный`, `материальный`, `значительный`) и произвольных отрицательных пропозиций — пока точное требование не представлено положительно будущим структурированным контрактом. Замороженные вышестоящие слои не содержат нормализованных авторитетных числовых фактов. Существование механизма не устанавливает «50 % выручки»; существование выкупа не устанавливает «18,48 % предложения»; наличие некоторого потока не устанавливает «вся выручка». **Разбор свободной прозы Evidence в авторитетные числа внутри S7 запрещён.** Эти ограничения — не системный сбой: используются канонические коды причин и структурный потолок | **LOCKED** |
| **D-110** | **Числового confidence в S7 нет.** Косметический балл не создаётся. D-081 соблюдён: требуемое схемой Proof число вычисляется позже в Proof Core как **детерминированная чистая функция** от `ClaimSupportResult` и вышестоящего структурированного состояния; модель число не выбирает никогда. Proof Core вправе **рендерить** confidence и **не вправе** самостоятельно изменять суждение истины S7 | **LOCKED** |
| **D-111** | **Персистенция и граница с Proof Core.** `ClaimSupportResult` персистируется как **производная проекция** `research_claim_support`; источник истины — `IntentRequirementSet` (в будущем — контракт `ClaimRequirement`) + `MechanismAssemblyResult` S6 + вышестоящий provenance. Обязательные свойства: детерминированность, воспроизводимость по повтору, идемпотентность, безопасность при конкурентности, «удаление + пересчёт даёт семантически идентичный результат», отсутствие мутации Evidence, отсутствие мутации S6, отсутствие промоушена памяти, **нулевой расход поиска, модели и провайдера**. Proof Core потребляет S7 и **не пересуживает** утверждение | **LOCKED** |

Решений на реализационные мелочи не заводится.
