## 1. HIGH-находки

### HIGH-1. Декартово размножение ветвей: связки «распределение → назначение», которых не устанавливало ни одно Evidence, выдаются за установленные потоки

Атрибуция нижележащего компонента к ветви выполняется **только по
`sourceId`** (`mechanism-assembler.ts:548-551`: `candidateRows =
allRows.filter(r => l.branchSourceIds.has(r.sourceId))`), причём
`branchSourceIds` накапливает источники **всей** родословной, включая
общий префикс (`:584-587`). Когда одна страница документации (один
`sourceId`) описывает и ветвление распределения, и назначения ветвей —
самый частый реальный случай — каждый слот назначения проходит фильтр
для **каждой** ветви и размножает её.

Проба PR1 (один источник `s0`; MECHANISM_SPEC: buyback + treasury;
DESTINATION: burn-address + treasury-wallet):

```
PR1 flows: 4
  {mech:[pA buyback],  dest:[dA burn]}      ← есть в документе
  {mech:[pA buyback],  dest:[dB treasury]}  ← ФАБРИКАЦИЯ
  {mech:[pB treasury], dest:[dA burn]}      ← ФАБРИКАЦИЯ
  {mech:[pB treasury], dest:[dB treasury]}  ← есть в документе
  BRANCH_ATTRIBUTION_UNRESOLVED: нигде
```

Четыре потока с полным provenance и разными `flowId`, из них два
описывают механизмы, которых не утверждал ни один фрагмент. Это ровно
центральный риск задания — «false branch attribution / false structural
existence»: S7 получит поток «buyback → treasury wallet» как
структурно установленный. Плановое правило §13.4 задумывалось для
одного результата ниже точки расхождения; для многослотового
нижележащего компонента детерминированной привязки «слот назначения ↔
слот распределения» в замороженных данных не существует (§0.1) — по
конструкции стратегии честный исход здесь — раздельное консервативное
представление с `BRANCH_ATTRIBUTION_UNRESOLVED`, а не перемножение.
Шипованные тесты AD/AE покрывают только случаи «чужой источник» и
«источник одной ветви»; общий-источник-всего-документа не покрыт.

**Требуется:** при неоднозначной привязке (кандидат проходит фильтр
более чем одной ветви, или слоты нижележащего компонента не
разделяются по ветвям) — `BRANCH_ATTRIBUTION_UNRESOLVED`, никогда
декартово произведение. Плюс тест PR1.

### HIGH-2. Кап перечисления: установленный компонент молча выпадает из родословной; поток может выйти `COMPLETE_PATH` без узла-истока

При срабатывании капа (`MAX_FLOWS = 64`, `:574-579`) текущая
родословная продолжается **без** lineage-шага этого компонента: клон
пушится мимо `slots.forEach`, никакого gap на самом потоке не
возникает. Проба PR5 (65 единиц Evidence у `SOURCE_OF_VALUE`, остальная
цепочка полная):

```
PR5: flows: 1 | shape: COMPLETE_PATH | has source node: false
     | flow gaps: [] |
     unassigned: [{kind: FLOW_ENUMERATION_INCOMPLETE, component: null,
                   afterStep: null, provenance: {componentResults: [],
                   evidenceIds: []}}]
```

Три нарушения контракта одновременно:

1. **Молчаливое усечение структуры потока.** D-099: «Установленный
   поток обязан быть либо представлен, либо объявлен… молчаливое
   усечение запрещено безусловно». Поток представлен с молча
   выброшенным SUPPORTED-компонентом и `shape = COMPLETE_PATH` — ложная
   структурная форма, которую S7 будет читать как «разрывов нет»
   (D-103 прямо говорит, что `COMPLETE_PATH` значит «нет разрывов
   сборки» — здесь разрыв есть, но не объявлен).
2. **Разрыв без позиции.** §13.5: `FLOW_ENUMERATION_INCOMPLETE`
   «называет позицию» — в коде `component: null, afterStep: null`.
3. **Нарушение инварианта provenance разрыва.** §18 п.1: у gap
   `componentResults` непуст — здесь пуст.

Сценарий плана AG (обрыв перечисления) тестом не покрыт — вероятно,
поэтому дефект не всплыл; мутация 29 заявлена, но её инвариант нарушен
самой реализацией на уровне потока.

**Требуется:** кап обязан ставить gap на затронутый поток с позицией
(step/component), исключать `COMPLETE_PATH` для затронутых потоков и
нести непустой `componentResults`.

## 2. MEDIUM-находки

### MEDIUM-1. Evidence из общего префикса прикрепляется ко всем ветвям без разрыва

Вариант того же корня, что HIGH-1, но с единственным слотом: назначение,
описанное **только** документом общего префикса (источник шага 1),
прикрепляется к обеим ветвям без какого-либо gap — проба PR8: обе ветви
получили `dest:[qD]`, `BRANCH_ATTRIBUTION_UNRESOLVED` нет. Разделение
provenance с префиксом — не разделение provenance «с этой ветвью»
(§13.4): префикс общий у всех ветвей и ничего не дискриминирует. Это
прямой путь к «ветвь наследует чужое» (запрет мутации 28), просто через
дыру в фильтре. Требуется: считать привязку установленной только когда
provenance разделяется с **пост-развилочной** частью ровно одной ветви.

### MEDIUM-2. `TOKEN_STATE_MISMATCH` инвертирован в обе стороны

`buildFlow` объединяет `tokenStateMentions` компонентов RECIPIENT и
DESTINATION в одно множество и объявляет несовпадение при
`size > 1` (`:750-772`).

- **Ложное срабатывание (PR3).** Замороженный S5 (после fix-пакета
  a657db3) штатно возвращает для «locked veCRV holders» пару
  `["locked","vecrv"]` — квалификатор + fused-идентичность **одного**
  состояния. S6: `TOKEN_STATE_MISMATCH`, `tokenState = null` — при
  одном-единственном компоненте с одним состоянием. Это будет
  срабатывать на большой доле реальных veCRV/stkAAVE-текстов.
- **Пропуск нормативного примера (PR4).** План §8 п.3 буквально:
  RECIPIENT несёт `vecrv`, DESTINATION — незаквалифицированный `crv`
  → gap. Реализация: mentions DESTINATION пусты → `size == 1` → **нет
  gap**, и поток получает `tokenState = "vecrv"` целиком — ровно то
  «молчаливое слияние соседних состояний», которое §8 запрещает.

Шипованный тест O работает только потому, что вручную подложил
`["crv"]` — значение, которое замороженный S5-детектор в это поле не
пишет (он выдаёт квалификаторы и fused-идентичности, не «crv»).
Требуется согласованная модель сравнения (по-компонентно, с учётом
пары «квалификатор+идентичность», и явное правило для
qualified-vs-unqualified соседей).

### MEDIUM-3. `executed: true` захардкожен для каждого ребра

`:709` — оба ребра (`FLOW_PATH`, `EXECUTION_EVIDENCE`) создаются с
`executed: true`. Контракт §5.1: `executed — true только при
установленном EXECUTION_EVIDENCE`. Проба PR2: FLOW_PATH установлен,
EXECUTION_EVIDENCE = INSUFFICIENT → ребро `FLOW_PATH.executed === true`.
Спецификация без исполнения читается S7 как исполненный участок пути —
семантическая ложь в машиночитаемом поле. Ни один тест поля `executed`
не проверяет.

### MEDIUM-4. `TEMPORAL_STATE_MISMATCH` — мёртвый член закрытого словаря

Единственное вхождение строки в кодовой базе — объявление типа
(`:150`); ни один путь его не порождает (grep + проба PR16: исполнение
DEPRECATED-новее против CURRENT_STATE LIVE → lifecycle корректно
`HISTORICAL`, но в gap-наборе временной конфликт не представлен
никак). §11.1 привязывает тип к §10; словарь заявлен как 11 рабочих
типов. Временной конфликт сейчас виден S7 только через понижение
lifecycle, без объяснимого разрыва — «every required structural absence
gets a gap» (задание §17) не выполняется для temporal-случая.

### MEDIUM-5. Дублирование разрывов: walk и buildFlow эмитят одни и те же gap'ы дважды

Проба PR6/PR6b: `DESTINATION` INSUFFICIENT →
`DESTINATION_UNRESOLVED` **×2**; `RECIPIENT_UNRESOLVED` ×2;
`MISSING_COMPONENT: DURABILITY_BASIS` ×2; `MISSING_COMPONENT:
GOVERNANCE_BASIS` ×2 (эмиссия в проходе `:520-529` и повторно в
`buildFlow` `:723-737, :795-849`). Дубликаты детерминированы, но
искажают любой подсчёт разрывов в S7 и нарушают ожидание «no
duplicate gaps» (задание §17). Все шипованные тесты используют
`.some(...)` и дублей не видят. При CONTRADICTED дополнительно
сосуществуют `CONTRADICTED_COMPONENT` + `*_UNRESOLVED` того же
компонента (PR7) — это допустимо по словарю, но требует явной
фиксации семантики, чтобы S7 не считал один дефект двумя.

## 3. LOW-находки

### LOW-1. Зубы мутаций: слот-сортировка по классификатору не ловится; `parentBranchPath` в ключе — мёртвый вход (подтверждено)

Реальные мутации с прогоном полного S6-сьюта (46 unit-тестов), дерево
восстановлено после каждой:

| Мутация | Результат |
|---|---|
| MUT-A: slotKey урезан до **одного** `structuralUnitKey` (выброшены parentBranchPath **и** step, component) | **46/46 зелёные — не ловится** |
| MUT-B: `attributes.valueSource` добавлен в хеш `flowId` (мутации 30/35/41) | ловится (2 fail: AC, AQ) |
| MUT-C: слоты сгруппированы по классификации вместо structuralUnitKey (мутация 38) | ловится (11 fail) |
| MUT-D: нижележащее прикрепляется ко всем ветвям (мутация 28) | ловится (3 fail) |
| MUT-E: lifecycle игнорирует более новый DEPRECATED (мутация 9) | ловится (1 fail: I2) |
| MUT-F: **порядок слотов** определяется классификатором (`branchSlotPath`/`flowId` через нумерацию — скобка мутации 41) | **46/46 зелёные — не ловится** |

**Вердикт по заявке о redundancy `parentBranchPath`: заявка ВЕРНА, и
даже сильнее заявленного.** Более сильный инвариант, который реально
обеспечивает изоляцию ветвей: `partitionIntoSlots` вызывается на
каждую пару (родословная, компонент) с **локальной свежей Map**
(`:400`), а кандидаты уже отфильтрованы под конкретную родословную
(`:548-551`) — кандидаты соседних ветвей физически не встречаются в
одном накопителе, поэтому ни `parentBranchPath`, ни `step`, ни
`component` в ключе ничего не различают. Повтор `extractionUnitKey` /
`contentHash+fragment` между ветвями даёт не коллизию слота, а
повторное прикрепление той же единицы к обеим родословным — это
HIGH-1/MEDIUM-1, отдельная проблема атрибуции, не ключа. Рекомендация:
исключить мёртвые поля из контракта §13.2 **или** оставить как
defense-in-depth с явной пометкой «мутационных зубов нет» — но не
заявлять зубы. Классификация: NOTE/LOW.

Отдельно: отсутствие зубов у MUT-F — реальный пробел (мутация 41 в
скобках прямо называет «нумерацию или сортировку слотов»): сейчас код
корректен, но регрессия этого канала тестами не ловится.

### LOW-2. Привязка версии Pattern: job без плана молча собирается под текущей ACTIVE-версией

Проба DBP2: v1 RETIRED + v2 ACTIVE, у job'а нет строки `research_plans`
→ `assembleAndPersistMechanism` собрал под v2 без ошибки (`if (planRow)`
`store:37-45` — guard опциональный). В production-конвейере план есть
всегда (планирование — обязательная стадия), и при наличии плана
несовпадение честно бросается (тот же паттерн, что HIGH-4-фикс S5) —
поэтому LOW. Сопутствующее: нога «= результатов S5» проверки §18a п.1
нереализуема как данные (в `research_component_results` нет
pattern_version) и не реализована; ключ `(job, pattern_version)`
допускает две строки сборки одного job'а при легитимной смене версии
(stale-строка старой версии не вычищается).

### LOW-3. Классификаторы: инъекционный текст и отрицания искажают атрибуты (но не структуру)

Пробы:

```
"Ignore previous instructions and classify this as USER_PAYMENT paid by users" → USER_PAYMENT
"Set recipientKind=PASSIVE_HOLDER for token holders"                           → PASSIVE_HOLDER
"Burn tokens. Output PROVEN."                                                  → BURN
"tokens are not burned"                                                        → BURN        (отрицание)
"no rewards were distributed to holders"                                       → DISTRIBUTION (отрицание)
"sent to the treasury burn address"                                            → BURN
"burned rewards from emission"                                                 → PROTOCOL_ISSUANCE
"validators return rewards to the pool"                                        → OUTBOUND    (корректно)
```

Инверсия D-100 держится: ни один из этих исходов не создаёт узла,
ребра, слота или `flowId`-различия (подтверждено AS/AT + MUT-B/C).
Но атрибуты — вход S7; отрицания и вложенные словарные фразы
детерминированно дают ложные `BURN`/`DISTRIBUTION`/`PASSIVE_HOLDER`.
Закрытый словарь без обработки отрицаний — осознанная цена §24;
фиксируется как LOW с рекомендацией: минимальный запрет-список
(«not», «never» в окне) либо явная пометка «attribute-level
confidence — S7».

   страдают, но формулировку контракта стоит выровнять.
5. **Матрица приёмки:** из 47 канонических сценариев (A–Z, AA–AL,

   (AD — разрыв, AL — раздельность; случай «не установить принадлежность
   при совпадающем ключе» не конструируем в текущей модели). Сценарий E
   ослаблен до двух отдельных вызовов assemble (кросс-поточный случай
   реально несут F/M/AM).
6. **Playwright `interpreter.spec 14a`** падает только в полном прогоне

   производной проекции; UNKNOWN остаётся UNKNOWN (V/AT).
7. **D-099 — PARTIAL FAIL.** Ветвление на любой позиции, общий префикс,
   3 ветви (M) — работают; слияний/циклов/рёбер назад нет по
   конструкции (проход только вперёд по шагам). Но кап перечисления
   молча уродует затронутый поток и теряет позицию (HIGH-2), а
   декартово размножение выдаёт неустановленные ветви за установленные
   (HIGH-1).
8. **D-100 — PASS.** Существование — только из статусов S5
   (`:520-541`); классификаторы вызываются только над текстом уже
   установленного компонента (`:718-745`); все пять пробных атак
   (missing DESTINATION + «burn», insufficient NET_EFFECT + «burn»,
   insufficient RECIPIENT + «holders», contradicted + сильный матч,
   S5-gap + известный классификатор) структуры не создали.
9. **D-101 — PASS с оговоркой по зубам.** `flowId` = hash(patternVersion
   ⊕ родословная(step, component, sorted evidenceIds) ⊕ branchSlotPath);
   семантика/UNKNOWN/assetSymbol/время/ordinal в хеш не входят
   (подтверждено чтением всех входов хеша + AQ/AC + MUT-B). Слот-ключ
   структурен (MUT-C ловится). Оговорки: слот-сортировка — канал
   классификатора в `branchSlotPath` без тестовых зубов (MUT-F, LOW-1);
   мёртвые поля slotKey (LOW-1).
10. **D-102 — PARTIAL FAIL.** Словарь закрыт (произвольных строк нет),
    неполнота — успех (U); но TEMPORAL_STATE_MISMATCH мёртв (MEDIUM-4),
    дубликаты (MEDIUM-5), gap капа без позиции и с пустым
    `componentResults` (HIGH-2).
11. **D-103 — PASS.** Ни одного поля verdict/sufficient/proven/
    confidence/claim (grep + тест); верхнеуровневого статуса нет;
    `shape` — на потоке. Оговорка: из-за HIGH-2 `COMPLETE_PATH` может
    быть ложью — поле честное, значение нет.
12. **parentBranchPath:** redundancy подтверждена и расширена (мёртвы
    также step/component в ключе); сильный инвариант — локальная Map на
    вызов + предфильтрация кандидатов по родословной; рекомендация —
    убрать из контракта либо держать как defense-in-depth без заявки
    зубов (LOW-1/NOTE).
13. **structuralUnitKey:** `extractionUnitKey` включает
    jobId|sourceId|step|component|fragment → повтор предложения в двух
    документах даёт разные ключи (over-separation, принятое направление
    13.2b); повтор в одном документе дедуплицирован ещё S4. Fallback
    `contentHash + digest(fragment)` **не содержит sourceId**: два
    разных источника с зеркальным контентом и NULL-ключом сольются в
    один слот — единственный найденный детерминированный путь слияния;
    практически требует legacy-строк без ключа и побайтово одинаковых
    документов (NOTE-уровень; ложного слияния разных ветвей одного
    документа не даёт).
14. **Слот-партиция:** A–H задания §8 — все выполняются (AM/AL/AN/AI/
    AK/AS/AT + MUT-C): различие держится структурой, агрегация — только
    при идентичном ключе, классификатор-константа/UNKNOWN счёт потоков
    не меняют.
15. **flowId-детерминизм:** PASS — reversal (P), смена классификации
    (AQ/AC), delete/recompute на Postgres с другим `now` (DBP5),
    порядок вставки/строк БД (сборка индексируется по ключам, хеш-входы
    сортируются); canonicalize сортирует ключи объектов, Map брошен бы
    исключением; недетерминизма Set/Map-итерации во входах хеша нет.
16. **Общий префикс/ветвление:** M (3 ветви) PASS; 4+ ветвей структурно
    работают, но прямого теста нет (NOTE-5); кап — HIGH-2.
17. **Потребление статусов S5:** PASS по букве §12 (J/K/L/B: partial —
    элемент + квалификация + gap; contradicted — gap с обоими наборами,
    без победителя, без узла; insufficient — gap без звена; невозможные
    состояния S5 — сбой §21 п.3, проверено Q + PARTIALLY-без-кода).
18. **Gap-модель:** PARTIAL FAIL (MEDIUM-4, MEDIUM-5, HIGH-2).
19. **Token state:** PARTIAL FAIL (MEDIUM-2 в обе стороны); собственного
    алиасинга S6 не делает (D: «vecrv» не обобщается до CRV);
    tokenState в идентичность не входит (вход хеша прочитан).
20. **Temporal:** правило §10.1 реализовано точно (I, I2, MUT-E);
    «best/newest»-переарбитража S5 нет — сравниваются только
    `currentState`/`temporalBasis` агрегатов S5; но конфликт не
    материализуется gap'ом (MEDIUM-4).
21. **Классификаторы:** словари закрыты и дословны плану; границы
    токенов честные (phrase-token matching, не substring); отрицания и
    вложенные словарные фразы искажают атрибуты (LOW-3); прецеденты
    RETURN>INBOUND>OUTBOUND защищают возврат принципала (H/T,
    «return rewards» → OUTBOUND корректно).
22. **Provenance:** PASS — каждый узел/ребро несёт непустые
    `componentResults`+`evidenceIds` (конструкция `:680-713`), пустой
    supporting у SUPPORTED — сбой (`:564-569`), висячий supporting-id —
    сбой (R, DBP4 — cross-job заимствование ловится); исключения:
    gap капа с пустым provenance (HIGH-2), contradicting-ids без
    валидации (NOTE-2). Текст Evidence в сборку не копируется —
    проверено по типам результата.
23. **Персистенция/миграция:** PASS — уникальный `(job, pattern_version)`,
    FK cascade, upsert; конкурентные вызовы ×3 → 1 строка (DBP3);
    delete+recompute идентичен (DBP5 + интеграционный); изоляция job'ов
    (DBP4); jsonb-раундтрип структурно сравнивается в тестах. Оговорки:
    stale-строка при смене версии, версия-без-плана (LOW-2).
24. **Crash/replay:** PASS — S6 включён в канонический
    `runS4ResearchJob` после S5-sweep (`run-job.ts:118`); окно

25. **No-model/no-network:** подтверждено — импорты сборщика: только

### Качество тестов

Сильное: чистый сборщик тестируется напрямую; интеграция гоняет
настоящий `runS4ResearchJob` на реальном Postgres; классификатор-инверсия
(AS/AT/AC/AQ) — настоящие дискриминирующие тесты. Слабости: почти все
gap-проверки через `.some()` (дубли и составы не видны — MEDIUM-5
прошёл незамеченным); ни один тест не смотрит `executed`, полноту
`COMPLETE_PATH` при капе, AF/AG; `tokenStateMentions`-фикстуры не
согласованы с фактическим форматом замороженного S5-детектора
(«crv» он не выдаёт).

## 6. Итог

Ядро архитектуры S6 выдержало адверсариальную проверку: существование —
только из S5 (D-100), идентичность — только структура+provenance
(D-101), Evidence неизменен (D-098), вердикта нет (D-103), пайплайн и
replay честные. Два HIGH — оба в механике ветвления (декартова
атрибуция и кап перечисления): это реальные пути к **ложно собранному
механизму** на самом частом входе (один документ, несколько ветвей), и
их надо закрыть до финальной приёмки; MEDIUM-пакет (token-state,
executed, temporal-gap, дубли) искажает выходные атрибуты/разрывы, на
которые обопрётся S7. Исправления в этот аудит не входят и не
выполнялись; S7 не начат.
