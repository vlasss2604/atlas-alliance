# Фаза 6, срез S6 — Mechanism Assembly. Стратегия и контракт

> Статус: **НА УТВЕРЖДЕНИЕ владельцу.** Код не пишется до подтверждения.
>
> База: замороженный S5 — HEAD `a657db39eee22353d5243ff3ea55a0a3d308be60`,
> freeze `54df1a9` (D-097); замороженный S4 — `d7e5b8a`, freeze `a258b99`
> (D-091). Ни один срез не переоткрывается. Фаза 5 заморожена,
> `research_enabled = false`.
>
> Всё ниже спроектировано на полях, которые S5 и S4 **действительно
> пишут**, а не на полях, которые план когда-то перечислил. Там, где
> замороженные данные не содержат нужного — это сказано прямо, а не
> обойдено выводом.
>
> Принцип среза: S5 отвечает «что установлено про **этот** компонент»;
> S6 отвечает «какой **механизм** складывается из установленного» — и
> ничего сверх. Достаточность и вердикт остаются за S7.

---

## 0. Что реально доступно S6 (проверено по коду, не по плану)

Это определяет всё остальное, поэтому идёт первым.

**S5 пишет в `ComponentReconciliationResult`** (`component-reconciler.ts`,
таблица `research_component_results`):

```
step · component · status · reasonCodes[] · supportingEvidenceIds[]
contradictingEvidenceIds[] · excludedEvidence[] · currentState
temporalBasis{basisField, at} · tokenStateMentions[] · requiresFreshEvidence
```

**Pattern v1 даёт** (`domain/pattern.ts`, `PATTERN_V1_CONTENT`): 8 шагов,
`requiredComponents` (10 компонентов, распределены по шагам),
`componentRequirements` (`establishingClasses`, `requiresCurrentState`,
`requiresLiveMechanismState`, `freshnessClass`, `tokenStateSensitive`,
`requiredTokenState`). `componentRequirementsFor` бросает
`PatternConfigurationError` на отсутствующий компонент — молчаливого
дефолта нет.

**`ContractView` даёт**: `patternVersion`, `mode`, `workQueue`, `reused`,
`excludedComponents`, `stopConditions`.

### 0.1 Четыре следствия, которые невозможно обойти

**1. Ни actor, ни action, ни asset, ни valueSource в замороженных данных
не существуют.** `evidence.value_source` — колонка есть, S4 её не пишет,
остаётся `NULL` (то же самое обнаружилось в S5 и было честно записано).
`EconomicLink { fromActor, action, asset, valueSource, toActor }` из
плана §9.1 **не выводится из имеющихся структурных полей ни при каком
детерминированном правиле**. Требовать этого от S4 — переоткрыть
замороженный срез.

**2. `destinationKind` и `recipientKind` тоже не существуют как поля.**
Единственное, что о них известно структурно, — статус компонентов
`DESTINATION` и `RECIPIENT` от S5 плюс их `tokenStateMentions`.

**3. Единственные машиночитаемые семантические поля, дошедшие до S6, —
`currentState` (нормализованный словарь CORE CHECK 2 + `PAUSED`) и
`tokenStateMentions` (закрытый лексический детектор S5).** Всё остальное
содержательное лежит в свободном тексте `fragment` / `summary`.

**4. Порядок цепочки уже задан Pattern'ом**, а не выводится: шаги 1→8
и распределение компонентов по ним — данные CORE, которые меняет человек.

### 0.2 Что из этого следует для стратегии

Есть ровно три честных выхода, и выбирать нужно осознанно:

| Выход | Цена |
|---|---|
| A. Ввести модель в S6 для разбора прозы | нарушает предпочтение владельца §24, вводит поверхность инъекции, требует бюджета и профиля стоимости (D-090) |
| B. Собирать только структурный скелет из статусов S5, без классификации | честно, но `buyback ≠ burn` и `Reward ≠ Revenue` останутся невыразимыми — а это ядро методологии |
| C. Существование звена — **только** из статуса S5; классификация звена — детерминированный закрытый словарь по уже допущенному Evidence, `UNKNOWN` по умолчанию | сохраняет детерминизм и даёт структурные различия CORE |

**Рекомендация — C**, с жёсткой инверсией, описанной в §5.3:
**классификация никогда не создаёт звено, она только помечает звено,
существование которого установил S5.** Слово «burn» в тексте не может
породить звено burn, если компонент `DESTINATION` не установлен S5.

## 1. Цель S6 одним предложением

> Превратить детерминированные результаты компонентов S5 в **структурное
> машиночитаемое представление экономического механизма** — со звеньями,
> разрывами, идентичностью потока и полной трассируемостью до Evidence —
> не вынося суждения о том, доказано ли утверждение пользователя.

## 3. Входной контракт

### 3.1 Читает ли S6 Evidence напрямую

**Да — но только те строки, которые S5 уже допустил, и только для
разметки, никогда для переадjudication.**

Принцип: **S5 — единственный судья на уровне компонента.** S6 не
пересматривает допустимость, класс, официальность, свежесть и статус. Но
без доступа к тексту допущенного Evidence невозможны ни `valueSource`,
ни `destinationKind`, ни `recipientKind` (§0.1) — а без них методология
CORE (CHECK 1, CHECK 3, `Reward ≠ Revenue`) не представима структурно.

**Правило доступа — закрытое:**

1. S6 читает **только** строки, чьи `id` присутствуют в
   `supportingEvidenceIds` или `contradictingEvidenceIds` результата S5.
   Любая другая строка `evidence` для S6 не существует.
2. S6 читает **только** перечисленные ниже неизменяемые поля.
3. S6 **никогда** не пишет в `evidence` — ни одной колонки, включая
   `value_source` (§7).
4. S6 **никогда** не выводит из этих полей допустимость, статус или
   авторитет — только классификацию уже установленного.

| Поле | Зачем именно оно |
|---|---|
| `id` | provenance |
| `sourceClass` | атрибуция базиса `DURABILITY_BASIS` (§17), не авторитет |
| `officiality` | перенос оговорки в атрибут звена, не пересчёт |
| `mechanismState` | перенос состояния (S5 уже нормализовал агрегат; §10) |
| `publishedAt` / `fetchedAt` | временная совместимость (§10) |
| `fragment` / `summary` | закрытая словарная классификация (§5.3) |
| `retrievedUrl` / `contentHash` | provenance для Proof Core |

Всё остальное (`does_not_prove`, `claim_key`, `snapshot_ref`, …) S6 не
читает: не нужно — значит не читается.

### 3.2 Вход

```ts
interface MechanismAssemblyInput {
  researchJobId: string;
  patternVersion: number;          // сверяется с ContractView; расхождение = сбой
  pattern: PatternContent;         // ACTIVE, привязанный к контракту job'а
  contractView: Pick<ContractView,
    "patternVersion" | "mode" | "workQueue" | "reused" | "excludedComponents">;
  componentResults: ComponentReconciliationResult[];  // все, что есть у job'а
  admittedEvidence: AssemblyEvidenceProjection[];     // §3.1, только допущенные
}
```

`now` **не передаётся**: вся временная работа уже сделана S5 и лежит в
`temporalBasis`. Введение `now` в S6 сделало бы сборку зависящей от
момента запуска и сломало бы §19 (тот же вход → тот же выход).
Отсутствие `now` — это инвариант, а не упущение.

Бюджет, очередь и контроллер во вход не входят: у сборщика не должно быть
доступа к тому, чем он не имеет права управлять (та же дисциплина, что в
S5 §11.1).

## 4. Pattern v1 → семантика сборки

Не каждый компонент становится узлом. Явное распределение:

| Компонент | Шаг | Роль в сборке | Почему |
|---|---|---|---|
| `SOURCE_OF_VALUE` | 1 | **узел-исток** + задаёт `valueSource` потока | откуда ценность берётся — начало пути (CHECK 3, CHECK 5) |
| `FLOW_PATH` | 2 | **ребро** исток → механизм | это описание движения, а не точка |
| `MECHANISM_SPEC` | 3 | **узел-механизм** | точка, где принимается правило распределения |
| `GOVERNANCE_BASIS` | 3 | **атрибут авторитета** узла-механизма | одобрение доказывает полномочие, а не движение ценности — экономическим узлом не является |
| `EXECUTION_EVIDENCE` | 4 | **гейт ребра** механизм → назначение | без него ребро остаётся спецификацией, а не исполнением |
| `CURRENT_STATE` | 5 | **гейт жизненного цикла потока** | атрибут, а не передача ценности (§10) |
| `DESTINATION` | 6 | **терминальный узел** + `destinationKind` | куда ценность попадает |
| `RECIPIENT` | 6 | **атрибут терминального узла** + `recipientKind` | кто держит право — не отдельная точка пути, иначе «есть получатель» превратится в «есть поток» |
| `NET_EFFECT` | 7 | **атрибут исхода потока** | исход, а не звено; ярлык звена его не создаёт (§16) |
| `DURABILITY_BASIS` | 8 | **метаданные механизма** | не экономическая передача (§17) |

Из десяти компонентов узлами становятся **три** (`SOURCE_OF_VALUE`,
`MECHANISM_SPEC`, `DESTINATION`), рёбрами — **два** (`FLOW_PATH`,
исполнение), остальные пять — атрибуты и гейты. Это и есть ответ на «не
предполагать, что каждый компонент — узел графа».

## 5. Модель механизма

### 5.1 Не граф (вариант C по §5 задачи)

Общий граф не нужен и вреден: он позволяет выразить структуры, которых
Pattern v1 не порождает, и тем самым создаёт места, где может вырасти
недоказанный вывод. Берётся **ограниченная Pattern'ом цепочка** —
подтверждение уже утверждённого плана §9.1 («не граф, упорядоченная
цепочка типизированных звеньев»), расширенное ограниченным ветвлением
(§13).

```ts
type MechanismNodeKind = "VALUE_SOURCE" | "MECHANISM" | "DESTINATION";

interface MechanismNode {
  kind: MechanismNodeKind;
  component: string;            // компонент, который его установил
  componentStatus: ComponentReconciliationStatus;
  qualifications: NodeQualification[];   // закрытый список, §12
  attributes: NodeAttributes;   // §5.2
  provenance: Provenance;       // §18 — непусто всегда
}

interface MechanismEdge {
  from: MechanismNodeKind;
  to: MechanismNodeKind;
  basisComponent: string;       // FLOW_PATH | EXECUTION_EVIDENCE
  basisStatus: ComponentReconciliationStatus;
  executed: boolean;            // true только при установленном EXECUTION_EVIDENCE
  qualifications: NodeQualification[];
  provenance: Provenance;
}

interface MechanismFlow {
  flowKey: FlowKey;             // §6 — идентичность потока
  lifecycle: "CURRENT" | "HISTORICAL" | "NOT_ESTABLISHED";  // §10
  nodes: MechanismNode[];       // в порядке шагов Pattern
  edges: MechanismEdge[];
  shape: "COMPLETE_PATH" | "PARTIAL_PATH";   // §22 — форма, не вердикт
  netEffect: NetEffectAttachment | null;      // §16
  durability: DurabilityAttachment | null;    // §17
  gaps: MechanismGap[];         // §11 — закрытый словарь
}

interface MechanismAssemblyResult {
  researchJobId: string;
  patternVersion: number;
  flows: MechanismFlow[];       // детерминированный порядок, §19
  unassignedGaps: MechanismGap[];  // разрывы, не принадлежащие ни одному потоку
}
```

**Верхнеуровневого статуса у `MechanismAssemblyResult` нет** — §22.

### 5.2 Атрибуты узлов — закрытые словари

```ts
type ValueSource =            // CHECK 3, словарь atlas-core, дословно
  | "USER_PAYMENT" | "PROTOCOL_ISSUANCE" | "TREASURY" | "EXTERNAL_INCENTIVE"
  | "FEES" | "COLLATERAL_RETURN" | "BURN_LINKED_ISSUANCE" | "MARKET_PURCHASE"
  | "UNKNOWN";

type DestinationKind =        // план §9.1, дословно
  | "BURN" | "BUYBACK_HOLD" | "TREASURY" | "DISTRIBUTION" | "LP"
  | "NONE" | "UNKNOWN";

type RecipientKind =          // план §9.1, дословно
  | "PASSIVE_HOLDER" | "STAKER" | "NODE_OPERATOR" | "TREASURY" | "LP"
  | "EXTERNAL" | "NONE" | "UNKNOWN";

type FlowDirection = "INBOUND" | "OUTBOUND" | "RETURN";  // §14
```

Ни один словарь не изобретается в S6: `ValueSource` взят из CHECK 3
`atlas-core`, `DestinationKind`/`RecipientKind` — из уже утверждённого
плана §9.1. Новая только `FlowDirection` (§14), и она минимальна.

### 5.3 Инверсия, на которой держится вся безопасность среза

> **Существование звена определяет статус S5. Классификация только
> помечает уже существующее звено. Классификация не создаёт звеньев
> никогда.**

Практически:

1. Узел `DESTINATION` появляется **только** если компонент `DESTINATION`
   имеет статус `SUPPORTED` или `PARTIALLY_SUPPORTED`. Слово «burn» в
   тексте `MECHANISM_SPEC` узла не создаёт.
2. `destinationKind = BURN` возможен **только** на уже существующем узле
   `DESTINATION` и **только** если закрытый детектор нашёл соответствующий
   термин в Evidence, которое S5 допустил **для этого компонента**.
3. Ничего не найдено или найдено неоднозначно → `UNKNOWN`.
   **`UNKNOWN` — это разрыв (§11), а не мягкое значение по умолчанию:**
   он порождает `gap`, а не догадку.
4. Классификатор — та же дисциплина, что у детектора состояния токена S5
   (D-096): закрытый кодом владеемый список, проверка границ токенов,
   консервативный отказ. Словаря тикеров, онтологии и вывода синонимов
   нет. Текст читается как **данные**, никогда как инструкция (§25).

Именно эта инверсия делает мутации 3, 4, 5 (§27) невозможными не по
договорённости, а по конструкции.

## 6. `Same Asset ≠ Same Economic Flow`

Критический раздел. Один токен фигурирует в экономически разных ролях —
FIL (оплата услуги, залог, награда, gas, возврат принципала), BTC
(комиссия пользователя против эмиссионной субсидии), RENDER (сжигание
при оплате клиентом против эмиссионной награды ноде).

### 6.1 Идентичность потока — четыре поля, тикера среди них нет

```ts
interface FlowKey {
  valueSource: ValueSource;      // CHECK 3 — откуда ценность
  direction: FlowDirection;      // §14 — движение, а не сумма
  recipientKind: RecipientKind;  // CHECK 1 — кто получает право
  tokenState: string | null;     // D-096 — в каком состоянии актив
}
```

**`assetSymbol` в идентичность не входит вовсе** и присутствует только
как атрибут отображения. Это и есть структурная реализация правила:
совпадение тикера не является основанием для слияния, потому что тикер
не участвует в ключе.

Два результата различны по `FlowKey` → **два разных `MechanismFlow`**,
даже если актив один. Слияние потоков с разными ключами запрещено и
роняет мутацию 1.

### 6.2 Почему именно эти четыре

| Урок | Поле, которое его выражает |
|---|---|
| BTC: комиссия пользователя ≠ эмиссионная субсидия | `valueSource` `USER_PAYMENT` ≠ `PROTOCOL_ISSUANCE` |
| RENDER: сжигание клиентом ≠ награда ноде | `valueSource` + `recipientKind` `NODE_OPERATOR` |
| FIL: возврат залога ≠ награда | `direction` `RETURN` + `valueSource` `COLLATERAL_RETURN` |
| CRV: `CRV` ≠ `veCRV` | `tokenState` |
| `System Utility ≠ Passive Holder Capture` | `recipientKind` не становится `PASSIVE_HOLDER` без положительного установления |

Пятое поле не добавляется: каждое из четырёх обосновано конкретным
воспроизведённым уроком, а не симметрией модели.

### 6.3 Когда идентичность не разрешается

Компоненты установлены, но `valueSource` или `recipientKind` пришли
`UNKNOWN` → поток не получает ключа и **не сливается ни с каким другим**.
Он существует с `gap` типа `FLOW_IDENTITY_UNRESOLVED`. Слить «на всякий
случай» запрещено: неразрешённая идентичность консервативнее ложного
объединения.

## 7. `value_source` — где он живёт

Freeze S5 (§9 п.4) говорит: «заполнение `evidence.value_source` — работа
S6 и не повод переоткрывать S4». Это указывает **чья** это работа, но не
утверждает, что значение обязано быть записано в строку Evidence. Разница
принципиальна, поэтому решается явно.

### 7.1 Что показал репозиторий

- Колонка `evidence.value_source` существует (миграция 0009), nullable,
  **не пишется никем**.
- Комментарий схемы: «fees / issuance / treasury / collateral_return —
  структурно, не в прозе (CHECK 3)».
- План §6 перечислял `value_source` в одном ряду с `mechanism_state` как
  поле **нормализации при извлечении**. `mechanism_state` S4 пишет,
  `value_source` — нет.

То есть исходный замысел был **extraction-time**, и S4 его не
реализовал. Заполнить его сейчас «задним числом» означало бы вычислить
классификацию в S6 и записать её в строку наблюдения.

### 7.2 Почему S6 не должен писать в Evidence

1. **D-077 запрещает схлопывание понятий.** `EVIDENCE` — что было
   наблюдено; `FACT` — что из этого следует. `value_source` в S6 — это
   вывод классификатора, а не наблюдение. Запись вывода в таблицу
   наблюдений превращает `EVIDENCE` в `FACT` — ровно то схлопывание,
   которое запрещено.
2. **Evidence — неизменяемый provenance** (D-076, freeze S4 §6). Строка
   фиксирует, что ARI видел тогда. Обратная дозапись делает её
   изменяемой и ломает воспроизводимость Proof.
3. **S5 уже создал прецедент** и он принят: производный результат живёт в
   отдельной проекции (`research_component_results`), истина остаётся в
   `evidence`. S6 обязан следовать той же дисциплине.
4. **Дозапись небезопасна при повторе.** Одна и та же строка Evidence
   может участвовать в разных job'ах; классификация же зависит от
   компонента и потока. Одно поле на строку не выражает это без потери.

### 7.3 Рекомендация — D-098

`valueSource` — **атрибут уровня сборки** в производной проекции S6.
`evidence.value_source` остаётся `NULL` и **зарезервированной** под
возможный будущий extraction-time контракт (`evidence_contract_version = 3`),
который был бы отдельным решением владельца и отдельным срезом, а не
побочным эффектом S6. S6 в `evidence` не пишет ничего.

`SOURCE ≠ EVIDENCE ≠ FACT ≠ MEMORY ≠ PROOF` остаётся целым.

## 8. Перенос состояния токена

`tokenStateMentions` от S5 — **вход для суждения, а не готовый вывод**
(D-096). S6 распоряжается им так:

1. **Перенос без обобщения.** `RECIPIENT`, установленный из «veCRV
   holders», даёт `tokenState = "vecrv"` на терминальном узле. Превращение
   его в «держатели CRV» запрещено и роняет мутацию 2. Обобщение
   квалифицированного состояния до ликвидного — не упрощение, а подмена
   экономического права.
2. **Отсутствие вывода в обратную сторону.** `DESTINATION` = токен в
   казначействе не даёт «сожжён»: `destinationKind` останется `TREASURY`,
   а `BURN` появится только из собственного установленного основания.
3. **Несовместимые состояния соседних компонентов не сливаются.** Если
   `RECIPIENT` несёт `vecrv`, а `DESTINATION` — незаквалифицированный
   `crv`, S6 **не выбирает** между ними: узлы сохраняют свои состояния,
   поток получает `gap` типа `TOKEN_STATE_MISMATCH`.
4. **`TOKEN_STATE_PATH_MISMATCH` отдельным результатом не вводится** —
   это `MechanismGap` типа `TOKEN_STATE_MISMATCH` (§11). Отдельный
   верхнеуровневый результат был бы вердиктом в маскировке (§22).
5. **Сравнение — точное нормализованное равенство строк**, ровно как в
   S5. Семантическая эквивалентность состояний в S6 не выводится ни в
   какую сторону.

## 9. Actor × Action

CHECK 1 требует не допускать «нода получает награду ⇒ пассивный держатель
получает доход».

**Решение: в v1 актор представлен `recipientKind` из закрытого словаря и
привязан к терминальному узлу, свободного именования акторов нет.**

Обоснование: свободное имя актора извлекается только из прозы, то есть
требует модели; закрытый словарь выражает ровно то различие, ради
которого CHECK 1 существует, и не требует семантики.

Три правила, которые это обеспечивают:

1. `recipientKind = PASSIVE_HOLDER` ставится **только** при
   положительном установлении из компонента `RECIPIENT`. Из отсутствия
   информации он не выводится никогда — иначе `System Utility ≠ Passive
   Holder Capture` было бы обойдено молчанием.
2. `recipientKind` относится к **этому потоку**, а не к токену вообще.
   Второй поток с `NODE_OPERATOR` не даёт первому ничего.
3. `RECIPIENT` не установлен → `recipientKind = UNKNOWN` и
   `gap: RECIPIENT_UNRESOLVED`. Узел получателя без основания не
   создаётся.

`action` как свободная строка (поле из плана §9.1) в v1 **не
заполняется**: её нечем заполнить детерминированно. Роль действия несут
`basisComponent` ребра и `direction` потока.

## 10. Состояние механизма и временная совместимость

S5 уже вынес суждение на уровне компонента; S6 его не повторяет. Но
собранный поток обязан не выдавать историческое за текущее.

### 10.1 Правило жизненного цикла потока — детерминированное

`lifecycle` вычисляется из статусов и состояний компонентов потока:

```
CURRENT — если ВСЕ условия:
  · CURRENT_STATE ∈ {SUPPORTED, PARTIALLY_SUPPORTED}
  · currentState ∈ {LIVE, IMPLEMENTING}
  · ни один компонент потока не несёт currentState ∈ {DEPRECATED, REMOVED}
    с temporalBasis строго новее, чем temporalBasis CURRENT_STATE

HISTORICAL — если поток имеет установленное исполнение, но:
  · currentState ∈ {DEPRECATED, REMOVED, PAUSED}, либо
  · более новый компонент несёт DEPRECATED/REMOVED

NOT_ESTABLISHED — иначе (в том числе CURRENT_STATE
  INSUFFICIENT_EVIDENCE или CONTRADICTED)
```

`IMPLEMENTING` в `CURRENT` допускается **только** с квалификацией
`STATE_NOT_FULLY_LIVE` на потоке — S5 уже пометил это кодом, S6 переносит.

### 10.2 Пример из задачи

Исполнение 2025 + механизм объявлен `DEPRECATED` в 2026 → **не** текущий
живой путь. Поток собирается с `lifecycle = HISTORICAL`; текущий поток из
тех же компонентов не порождается. Мутация 9 обязана падать.

`NOT_ESTABLISHED` — не сбой и не вердикт: это форма, у которой нет
установленного жизненного цикла.

## 11. Разрывы

**S6 не изобретает отсутствующее звено никогда.** Разрыв представляется
явно и машиночитаемо.

### 11.1 Закрытый словарь типов

```ts
type MechanismGapKind =
  | "MISSING_COMPONENT"        // S5: INSUFFICIENT_EVIDENCE
  | "PARTIAL_COMPONENT"        // S5: PARTIALLY_SUPPORTED, оговорка перенесена
  | "CONTRADICTED_COMPONENT"   // S5: CONTRADICTED — победитель не выбирается
  | "TOKEN_STATE_MISMATCH"     // §8.3
  | "FLOW_IDENTITY_UNRESOLVED" // §6.3
  | "TEMPORAL_STATE_MISMATCH"  // §10
  | "RECIPIENT_UNRESOLVED"     // §9.3
  | "DESTINATION_UNRESOLVED"   // DESTINATION не установлен либо kind = UNKNOWN
  | "NET_EFFECT_UNRESOLVED";   // §16
```

Девять типов, каждый привязан к конкретному правилу выше. Свободного
текста в разрыве нет — только `kind`, `component`, `afterStep`,
`provenance`. Это и мешает «разрыву» стать мусорным ведром.

### 11.2 Пример из задачи

```
Revenue ✅ → Allocation ✅ → Execution ✅
→ [GAP: DESTINATION_UNRESOLVED] → [GAP: NET_EFFECT_UNRESOLVED]
```

Ровно так и собирается: три звена с provenance плюс два типизированных
разрыва. Ничего за разрывом не достраивается.

### 11.3 Отдельного канала warnings нет

Всё, что было бы «предупреждением сборки», уже является разрывом или
квалификацией (§12). Второй параллельный канал сообщений создал бы место
для мягких формулировок, не обязанных быть закрытым словарём. Ответ на
частичный вопрос §2 задачи: **нет, отдельные warnings не вводятся.**

## 12. Потребление статусов S5

Правила для каждого статуса — точные и без исключений:

| Статус S5 | Что даёт сборке | Чего не даёт никогда |
|---|---|---|
| `SUPPORTED` | полноценный узел/ребро/атрибут | — |
| `PARTIALLY_SUPPORTED` | тот же элемент, но **обязательно** с `NodeQualification`, перенесённой из `reasonCodes` S5, и с сопутствующим `gap: PARTIAL_COMPONENT` | безоговорочного элемента; элемент без квалификации структурно невозможен |
| `CONTRADICTED` | `gap: CONTRADICTED_COMPONENT` с обоими наборами `evidenceIds` | узла или ребра; выбора победителя — ни по классу, ни по свежести, ни по количеству |
| `INSUFFICIENT_EVIDENCE` | `gap: MISSING_COMPONENT` | ничего иного; выведенного звена |

```ts
type NodeQualification =      // ровно коды S5, не новый словарь
  | "INSUFFICIENT_AUTHORITY" | "INDIRECT_ONLY"
  | "STATE_NOT_FULLY_LIVE" | "TOKEN_STATE_UNQUALIFIED";
```

**Ответ на вопрос §12 задачи:** `PARTIALLY_SUPPORTED` включается как
**условный элемент**, а не как разрыв и не как полноценное звено — он
одновременно даёт элемент с квалификацией и разрыв рядом с ним. Так S7
получает и форму пути, и честную границу, не восстанавливая её сам.

`S6` не может превратить `CONTRADICTED` в `SUPPORTED` и не может достроить
`INSUFFICIENT_EVIDENCE` — оба запрета имеют мутационные зубы (11, 12).

## 13. Ветвление

Механизмы ветвятся: `100% выручки → 50% buyback / 30% treasury /
20% операции`; купленные токены → `burn` и/или `treasury` и/или стимулы.

**Ограниченная семантика ветвления, а не граф:**

1. Ветвление разрешено **ровно в одной точке** — на терминальном узле
   (`DESTINATION`). Все остальные звенья цепочки линейны.
2. Каждая ветвь — самостоятельный `DESTINATION` со своим
   `destinationKind`, своей квалификацией и своим provenance.
3. Ветвь существует **только** при собственном установленном основании.
   Доли (50/30/20) не восстанавливаются и не суммируются: числовых
   утверждений S6 не делает вовсе.
4. Ветви с разным `FlowKey` — это **разные потоки** (§6), а не ветви
   одного.
5. Схлопывание ветвей в одну запрещено (мутация 16).

**Открытый вопрос владельцу.** План §9.3 ограничивает v1 двумя цепочками.
Рекомендация: **снять числовой лимит на количество потоков** (он
произволен и может молча скрыть третий реальный поток — «no silent caps»)
и оставить ограничением **структуру**: линейная цепочка + ветвление
только на терминале. Если владелец предпочитает сохранить лимит 2 — он
обязан стать явным `gap`, а не тихим срезом. Вынесено в D-099.

## 14. Возврат принципала ≠ награда

Урок FIL. Различие делается **направлением потока**, а не прозой:

```
INBOUND  — ценность приходит к протоколу/механизму (оплата, комиссия)
OUTBOUND — ценность уходит от протокола к получателю (награда, распределение)
RETURN   — возврат ранее внесённого (залог, принципал)
```

`direction = RETURN` вместе с `valueSource = COLLATERAL_RETURN`
структурно не может быть прочитан как награда: `RETURN` не порождает
терминального узла с экономическим приобретением, и `recipientKind`
для него не становится `PASSIVE_HOLDER`.

Аналогично `PROTOCOL_ISSUANCE` (`OUTBOUND`, эмиссия) и `USER_PAYMENT` /
`FEES` (`INBOUND`, оплата клиентом) — **разные `FlowKey`**, а значит
разные потоки, которые невозможно сложить (§15).

Идентичность источника сохраняется вдоль всего пути: `valueSource`
принадлежит потоку, а не отдельному звену, поэтому «размыться» по дороге
не может.

## 15. Оплата пользователем против эмиссии протокола

BTC: комиссия, уплаченная пользователем, против субсидии, выпущенной
протоколом. RENDER: сжигание при оплате клиентом против эмиссионной
награды ноде.

Отдельной таксономии для этого **не вводится** — различие уже полностью
выражено существующим словарём CHECK 3 (`USER_PAYMENT` / `FEES` против
`PROTOCOL_ISSUANCE` / `BURN_LINKED_ISSUANCE`) в составе `FlowKey`. Раз
ключи различны — потоки различны и слиться не могут. Мутации 7 и 8
падают на этом же механизме, что и мутация 1: не на отдельном правиле, а
на конструкции ключа.

`valueSource` определяется **только** из компонента `SOURCE_OF_VALUE`
(§4). Вывод источника из тикера актива, из имени механизма или из
получателя запрещён (мутация 18).

## 16. Net Effect

`NET_EFFECT` потребляется от S5 и **не пересчитывается**.

```ts
interface NetEffectAttachment {
  componentStatus: ComponentReconciliationStatus;
  qualifications: NodeQualification[];
  provenance: Provenance;
}
```

Правила:

1. `NetEffectAttachment` появляется **только** при `NET_EFFECT` в статусе
   `SUPPORTED` / `PARTIALLY_SUPPORTED`. Иначе — `gap:
   NET_EFFECT_UNRESOLVED`.
2. **Ярлык механизма исходом не является.** `destinationKind = BURN` не
   создаёт и не подменяет `NetEffectAttachment`; `Gross Burn ≠ Net Supply
   Effect`. Ребра «сокращение предложения» без установленного
   `NET_EFFECT` не существует (мутации 3, 4).
3. `BUYBACK_HOLD ≠ BURN`, `TREASURY ≠ DISTRIBUTION` — разные значения
   закрытого словаря, между собой не переходящие (мутация 5).
4. Своего вердикта о чистом эффекте S6 не выносит: он переносит статус и
   квалификации S5 и присоединяет их к потоку.

## 17. Durability

`DURABILITY_BASIS` — не экономическая передача, поэтому звеном не
становится (§4).

```ts
interface DurabilityAttachment {
  componentStatus: ComponentReconciliationStatus;
  basisClasses: EvidenceSourceClass[];   // фактические классы допущенного Evidence
  qualifications: NodeQualification[];
  provenance: Provenance;
}
```

**Спекулятивная таксономия не вводится.** Значения вида
«governance-controlled / contractual / discretionary / time-bounded /
emission-dependent» в репозитории ничем не обоснованы и потребовали бы
семантической классификации прозы. Вместо них переносится то, что уже
установлено: статус компонента и **фактические классы источников**
допущенного Evidence (`GOVERNANCE` → основание закреплено управлением;
`OFFICIAL_DOCS` → документировано). Это фактическое наблюдение, а не
интерпретация.

## 18. Provenance

```ts
interface Provenance {
  componentResults: { step: number; component: string }[];  // ключ S5
  evidenceIds: string[];                                    // детерминированный порядок
}
```

Инварианты:

1. **Каждый узел, ребро и атрибут обязан иметь непустой `provenance`.**
   Единственное исключение — `MechanismGap`, который по определению
   ссылается на отсутствие; у него `componentResults` непуст (сам
   результат S5 существует), а `evidenceIds` может быть пуст.
2. Узел или ребро с пустым `evidenceIds` — **нарушение инварианта и
   системный сбой** (§21), а не тихая пустота (сценарий R, мутация 14).
3. `evidenceIds` — только идентификаторы. **Текст Evidence в сборку не
   копируется** ни в каком виде: проза принадлежит Proof (S7) и берётся
   там из `evidence` по этим же id.
4. Цепочка трассируемости полна и односторонняя:
   `элемент сборки → ComponentReconciliationResult → evidence.id →
   retrieved_url + content_hash`.

## 19. Детерминизм

Тот же Pattern, тот же Boundary Contract, те же результаты S5 и то же
допущенное Evidence → **тот же `MechanismAssemblyResult`**, независимо от
порядка строк в БД, порядка входного массива и порядка вставки.

Полный порядок сортировки:

| Коллекция | Ключ сортировки (полный) |
|---|---|
| `flows` | `valueSource` → `direction` → `recipientKind` → `tokenState` (`NULLS LAST`) → сериализованный `flowKey` |
| `nodes` | шаг Pattern → имя компонента |
| `edges` | шаг `from` → шаг `to` → `basisComponent` |
| `gaps` | `afterStep` → `kind` → `component` |
| `evidenceIds` | лексикографически по `id` |
| `componentResults` | `step` → `component` |

Последний ключ в каждой строке гарантирует полный порядок при полном
совпадении предыдущих. Модельной недетерминированности в срезе нет —
модели нет вовсе. `now` во вход не входит (§3.2), поэтому результат не
зависит и от момента запуска.

## 20. Персистенция

**Рекомендация: персистировать как производную проекцию** (вариант B).

Обоснование: S7 (Proof Core) обязан построить слои 1–4 и 6–7 из
собранного механизма, владелец обязан иметь возможность проверить «какое
Evidence дало это звено» без повторного прогона, а восстановление после
падения между S6 и S7 не должно требовать пересборки.

```
research_mechanism_assembly
  (research_job_id, pattern_version) UNIQUE   — одна сборка на job и версию Pattern
  flows           jsonb
  unassigned_gaps jsonb
  created_at / updated_at
```

Дисциплина — та же, что принята для S5 и уже проверена:

1. Истина остаётся в `research_component_results` и `evidence`; строка
   сборки — **производная проекция**.
2. Удаление всех строк и повторный прогон обязаны дать **семантически тот
   же** результат из тех же входов.
3. Ключ `(job, patternVersion)` + upsert → повтор не плодит строк,
   конкурентный повтор безопасен.
4. Лишних таблиц не заводится: узлы, рёбра и разрывы живут внутри
   `flows` как jsonb, потому что реляционных запросов по ним ни у кого
   нет — единственный потребитель читает сборку целиком.

## 21. Сбой против структурной неполноты

**Структурная неполнота — не сбой.** Отсутствующий `DESTINATION`,
противоречивый `CURRENT_STATE`, частичный `RECIPIENT` дают **валидный**
`MechanismAssemblyResult` с разрывами. Это прямое продолжение D-084:
недостаточность — законный успешный исход.

**Системный сбой — закрытый список:**

1. невалидный Pattern или `PatternConfigurationError` (компонент без
   `componentRequirements`);
2. расхождение `patternVersion` между контрактом, сборкой и результатами
   S5;
3. невозможный инвариант S5 (дубль по `(job, step, component)`; статус вне
   четырёх; `PARTIALLY_SUPPORTED` без кода основания);
4. узел или ребро без provenance (§18 п.2);
5. `supportingEvidenceIds` ссылается на строку `evidence`, которой нет;
6. ошибка БД.

Всё, что не в этом списке, обязано становиться разрывом, а не
исключением.

## 22. Верхнеуровневый статус результата

**Рекомендация: верхнеуровневого статуса нет.**

`ASSEMBLED` / `ASSEMBLED_WITH_GAPS` / `UNASSEMBLABLE` были бы
механически выводимы из `gaps.length` и `flows.length` — то есть не
несли бы новой информации, — но при этом создали бы единственное место в
результате, где может незаметно вырасти суждение о достаточности. Именно
такие поля со временем начинают читать как вердикт.

Форма пути нужна, но она принадлежит **потоку**, а не результату:
`MechanismFlow.shape ∈ { COMPLETE_PATH, PARTIAL_PATH }`, где
`COMPLETE_PATH` означает ровно одно: **у этого потока нет разрывов**.
Это структурная форма, а не достаточность: полный по форме поток может
оказаться недостаточным для утверждения пользователя, и решает это S7.

Ответ на частичный вопрос §2 задачи: `COMPLETE_PATH` / `PARTIAL_PATH`
допускаются **как форма на уровне потока**; верхнеуровневый статус
результата — нет.

## 23. Граница S6 и достаточности

| | Вопрос | Слой |
|---|---|---|
| S6 | «Какой механизм восстанавливается из установленных результатов компонентов?» | этот срез |
| S7 | «Достаточен ли этот механизм для утверждения пользователя?» | следующий |

Пример из задачи разбирается буквально: S6 собирает
`Revenue → Buyback → Treasury` с разрывом `NET_EFFECT_UNRESOLVED`.
Вывод «утверждение „buyback сокращает предложение“ не доказано» — **не
делается в S6**, потому что он про утверждение пользователя, а не про
механизм. S6 предоставляет форму, S7 сопоставляет её с вопросом.

Практическое следствие: в `MechanismAssemblyResult` нет ни одного поля,
имя которого содержит `verdict`, `sufficient`, `proven`, `confidence`
или `claim`. Это проверяется тестом (мутация 22).

## 24. Модель в S6

**Рекомендация: S6 полностью model-free.** Каждая операция среза
структурна: сравнение enum'ов, сопоставление статусов, сравнение
нормализованных строк, закрытый лексический детектор, сортировка.

**Где семантика действительно понадобилась бы** — названо честно, чтобы
это не выглядело обойдённым:

| Операция | Почему детерминизма не хватает | Решение v1 |
|---|---|---|
| свободное имя актора и действия | извлекается только из прозы | **не заполняется**; роль несут `recipientKind` и `direction` (§9) |
| распознавание перефразированного механизма в двух источниках | требует сравнения смыслов | это Critic-слой, отложенный планом §10.4 |
| классификация `valueSource` в источнике, не покрытом закрытым словарём | требует обобщения | `UNKNOWN` → разрыв, не догадка (§5.3) |

Ни одна из трёх не блокирует S6: во всех случаях честный ответ —
консервативный разрыв, а не вывод модели. Раз модели нет — нет и
бюджета, нет и поверхности инъекции.

Если владелец впоследствии решит, что свободное именование акторов
необходимо, это будет **отдельное решение и отдельный срез** с профилем
стоимости (D-090) и живым гейтом (S10), а не тихое добавление вызова в
S6.

## 25. Безопасность

1. **Текст Evidence — недоверенные инертные данные.** S6 не исполняет
   найденные в нём инструкции; модели в срезе нет, поэтому поверхности
   prompt-инъекции нет вовсе.
2. **Операции над текстом ограничены**: только сопоставление с закрытым
   кодом владеемым словарём по границам токенов. Ни регулярных
   выражений, построенных из содержимого страницы, ни интерпретации,
   ни исполнения.
3. **Сети нет.** Ни поиска, ни загрузки, ни внешних вызовов.
4. **Структурные поля приоритетнее текста**: где значение доступно из
   `componentResults` или Pattern, текст не читается вовсе.
5. **Записи нет нигде, кроме собственной проекции**: `evidence`,
   `research_component_results`, память Фазы 5 остаются нетронутыми.
