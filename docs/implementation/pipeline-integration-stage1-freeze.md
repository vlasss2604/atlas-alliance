## 3. Терминальный контракт

Принятое разделение:

```
job.state              = исход исполнения
job.termination_reason = почему исполнение остановилось
job.error_code          = техническая деталь / информационный код
                           способности там, где он установлен
research_claim_support.status = доказательный результат
```

Эти четыре понятия различны и **не подлежат схлопыванию в последующих
срезах**.

Принятые отображения:

```
WORK_QUEUE_EXHAUSTED                  → SUCCEEDED
BUDGET_EXHAUSTED                      → BUDGET_LIMIT_REACHED
CAPABILITY_BOUNDARY_NO_ELIGIBLE_WORK  → SUCCEEDED + errorCode=CAPABILITY_BOUNDARY
Исключение исполнения                 → FAILED
                                         + terminationReason=SYSTEM_OR_PROVIDER_FAILURE
                                         + без сфабрикованного research_claim_support
```

## 4. Инвариант сбоя исполнения (заморожен)

Технический/системный/провайдерский сбой исполнения **никогда** не
маскируется под:

```
SUPPORTED · PARTIALLY_SUPPORTED · NOT_SUPPORTED · INSUFFICIENT_EVIDENCE
```

Если исследование предметно не выполнялось, доказательный вывод S7 не
выдумывается из пустого Evidence.

Интеграционный тест с `MissingActivePatternError` (Stage 1) принят как
достаточное доказательство общей ветки сбоя исполнения для этого
non-live среза. Семантика сбоя/rate-limit живого провайдера остаётся
работой S10.

## 5. Принятое замечание о budget-stop (НЕ блокирует)

**NON-BLOCKING ARCHITECTURAL NOTE.**

Отображение `BUDGET_EXHAUSTED → BUDGET_LIMIT_REACHED` корректно.

Однако текущий продакшн-worker Stage 1 ещё не содержит жизненного
цикла retry/resume, который естественно делал бы этот путь достижимым
из обычного одноразового подхвата worker'а. Движок поддерживает
возобновлённое исполнение против персистированной истории попыток —
это уже используется в тестах Stage 1 напрямую (два вызова
`runS4ResearchJob`), но не через продакшн-путь worker'а.

**Будущий срез, вводящий retry/resume worker'а, обязан доказать
`BUDGET_EXHAUSTED` end-to-end через настоящий продакшн жизненный цикл.**
Этот freeze-коммит такой жизненный цикл не реализует.

## 6. Принятые LOW

**LOW 1.** Комментарий про `INTERRUPTED` в `worker.ts` неточен: он
подразумевает, что «более поздний подхват worker'а возобновляет job».
Фактическое текущее поведение:

- эта ветка структурно недостижима на пути worker'а Stage 1;
- если бы она была достигнута, автоматического re-queue не существует;
- восстановление зависших job'ов идёт через sweep, а не через resume.

Классификация: LOW / не блокирует, поскольку ветка сейчас недостижима.
Не исправляется в этом документационном freeze-коммите без отдельного
запроса владельца.

**LOW 2.** Sweep зависших `RUNNING` job'ов (`sweepStaleRunningJobs`)
сейчас выполняется только при старте worker'а. Периодический
maintenance-путь этот sweep не выполняет.

Классификация: LOW / не блокирует, предсуществующий долг. Сейчас не
задействован принятым путём Stage 1, поскольку `INTERRUPTED`
недостижим. Зафиксировано как будущий долг укрепления жизненного
цикла — не реализуется сейчас.

**LOW 3.** DEMO-резервация сейчас разрешается `RELEASED` при
`SUCCEEDED`. Принято для Stage 1, поскольку Proof Core ещё не
существует, а D-084 возвращает квоту до появления Proof.

**Обязательство на будущее:** когда Proof Core введёт настоящий
успешный исследовательский исход с Proof — включая валидный Proof с
`INSUFFICIENT_EVIDENCE` — успешно завершённое исследование обязано
ПОТРЕБЛЯТЬ квоту согласно D-084. Семантика квоты в Stage 1 не меняется.

## 7. Конвенция CAPABILITY_BOUNDARY (принята)

`SUCCEEDED + errorCode=CAPABILITY_BOUNDARY` — установленная
информационная конвенция, **не** сбой исполнения.
`termination_reason` теперь даёт авторитетное объяснение остановки.

**Будущие потребители не вправе предполагать:**
`error_code != null ⇒ FAILED`.

Редизайн в Stage 1 не требуется.

---

## 8. Replay / идемпотентность (принято)

Повторный подхват worker'ом после терминального перехода — no-op. Ни
Evidence, ни проекция S5, ни сборка S6, ни S7 claim support, ни
терминальный переход не дублируются повтором терминального job'а.

---

## 9. TRACE ≠ EVIDENCE (заморожено)

Операционные/debug/worker-метаданные — не Evidence. Принятый non-live
end-to-end путь может породить попытки и проекции S5/S6/S7 при нуле
строк Evidence, не фабрикуя источник подтверждения.

**Будущая observability Stage 2 обязана сохранить TRACE ≠ EVIDENCE.**

## 13. Правило freeze

**После этого freeze Stage 1 НЕ переоткрывается ради:**

- косметических рефакторингов;
- реализации retry/resume жизненного цикла worker'а «заодно»;
- исправления LOW 1/LOW 2/LOW 3 без отдельного запроса владельца;
- требований Stage 2, S8, S9, S10, Proof Core.

**Stage 1 переоткрывается только при:**

1. воспроизведённом материальном регрессе против замороженного
   терминального контракта;
2. дефекте корректности или безопасности;
3. явном новом решении владельца, изменяющем терминальный контракт или
   интеграцию worker'а (D-113/D-114);
4. бета-данных, показывающих, что отложенный LOW материально блокирует
   корректную работу.

**Любое будущее семантическое изменение терминального контракта Stage 1
или интеграции worker'а требует явного решения владельца и
регрессионного ревью.**
