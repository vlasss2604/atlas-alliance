## 0. Что реально доступно S5 (проверено по коду, не по плану)

Это определяет всё остальное, поэтому идёт первым.

**S4 пишет в `evidence`:** `research_job_id`, `proof_id = NULL`, `source_id`,
`pattern_step`, `component`, `relationship`, `directness`, `fragment`,
`summary`, `mechanism_state`, `source_class`, `officiality`, `fetched_at`,
`published_at`, `does_not_prove`, `retrieved_url`, `content_hash`,
`extraction_unit_key`, `evidence_contract_version = 2`.

**S4 НЕ пишет** (колонки существуют, остаются `NULL`): `value_source`,
`claim_key`, `observed_at`, `data_as_of`, `freshness_class`, `snapshot_ref`.

Четыре следствия, которые невозможно обойти:

1. **Единственная дата документа — `published_at`** (извлекает модель,
   nullable). `fetched_at` — время нашей загрузки, оно почти одинаково для
   всего job'а и ранжировать документы по актуальности им нельзя.
2. **`freshness_class` на Evidence отсутствует**, поэтому окно свежести
   не может быть свойством записи — оно становится свойством **компонента**
   (§5). Требовать его от S4 значило бы переоткрыть замороженный срез.
3. **`mechanism_state` — свободная строка от модели**, без enum в БД.
   Значит S5 обязан нормализовать её по закрытому словарю CORE и считать
   неопознанное **отсутствующим**, а не отдельным состоянием (§6).
4. **Структурной квалификации состояния токена и экономического потока
   нет вовсе** (`value_source` пуст, поля token state не существует) — §9.

**Из S0/S3 доступны:** `ComponentWorkItem { step, stepName, component,
state, blockers, memoryIds, conflictingMemoryIds }`, `ContractView`,
`research_attempts`. Комментарий схемы S3 уже резервирует имя
`research_component_results` за S5 — оно и используется (§11).

## 1. Цель S5 одним предложением

> Превратить детерминированный, provenance-несущий набор Evidence одного
> компонента в **машиночитаемое состояние этого компонента** с
> перечислимыми причинами — без поиска, без модели и без выводов о
> механизме в целом.

## 3. Состояния компонента

Четыре. `NOT_APPLICABLE` **не вводится**: в Pattern v1 `requiredComponents`
перечисляет все десять компонентов как обязательные — ни один нельзя
объявить структурно неприменимым, а неиспользуемое состояние
«неприменимо» рано или поздно станет местом, куда прячут отсутствие
доказательств. Вводить его можно будет только тогда, когда Pattern
научится объявлять компонент опциональным (Pattern v2, D-022).

| Состояние | Условия входа | Терминально для S5 | Разрешает сборку в S6 | Требует ещё исследования | Природа |
|---|---|---|---|---|---|
| `SUPPORTED` | есть ≥1 **устанавливающий** элемент (§4) и нет неразрешённого противоречия | да | да, без оговорки | нет | установлено |
| `PARTIALLY_SUPPORTED` | есть устанавливающий элемент, но применима ровно перечислимая оговорка (§8) | да | да, **с объявленной границей** | опционально, если бюджет позволяет | установлено с ограничением |
| `CONTRADICTED` | §7 | да | **нет** — компонент не считается установленным | да, и только свежим доказательством | конфликт |
| `INSUFFICIENT_EVIDENCE` | ни один элемент не устанавливает компонент | да | нет | да | неопределённость |

**«Нет доказательств» и «доказательства противоречат» остаются разными
состояниями** — это разные действия для контроллера и разные тексты для
пользователя.

**Согласование со словарём плана §11.1.** План перечислял семь состояний.
`UNRESOLVED` и `NOT_FOUND` схлопываются в `INSUFFICIENT_EVIDENCE`,
различаясь **кодом причины** (`NO_EVIDENCE_FOUND` против
`ALL_EVIDENCE_EXCLUDED` и остальных) — состояние отвечает на «что
установлено», код причины на «чего не хватило». `EXCLUDED` и
`REUSED_FROM_MEMORY` S5 не выдаёт никогда: их ставит контракт/контроллер
(`ContractView.excludedComponents`, `ContractView.reused`), и до
реконсиляции такие компоненты не доходят.

## 4. Что устанавливает компонент

**Устанавливающий элемент** — Evidence, одновременно удовлетворяющий
всем условиям:

1. `evidence_contract_version = 2` (у legacy-строк нет классификации);
2. `pattern_step` и `component` совпадают с запрошенными;
3. `relationship = SUPPORTS`;
4. `directness = DIRECT` — `INDIRECT` устанавливать не может (даёт
   максимум §8), `INFERRED` не может ничего: это вывод модели, а не
   наблюдение;
5. `source_class` входит в множество допустимых **для этого компонента**
   (§5);
6. компонент, требующий текущего состояния, — дополнительно §6;
7. элемент не исключён по §10.

**Количество не участвует в правиле нигде.** Один устанавливающий элемент
достаточен; десять неустанавливающих не дают ничего. Это прямое
исполнение D-074 и D-080: сила источника — не повторяемость.

**Дедупликация до подсчёта чего бы то ни было.** Единицей считается
`extraction_unit_key`; при его отсутствии — `(source_id, нормализованный
fragment)`. Дубль даёт `DUPLICATE_UNIT` и не участвует дважды ни в чём.
Несколько элементов с одного `source_id` — один источник, а не два
независимых подтверждения.

**`officiality` не пересчитывается** (D-089): берётся как есть из строки.
`CLAIMED` не запрещает установление, но ограничивает результат до
`PARTIALLY_SUPPORTED` (§8) — иначе холодный старт был бы невозможен, а
неподтверждённое выдавалось бы за подтверждённое.

## 5. Допустимость класса источника по компоненту

Матрица уже утверждена планом §11.2 и **не переписывается**:

| Компонент | Классы, способные установить самостоятельно | Требует текущего состояния |
|---|---|---|
| `SOURCE_OF_VALUE` | `OFFICIAL_DOCS`, `GOVERNANCE`, `ONCHAIN_VERIFIABLE` | нет |
| `FLOW_PATH` | `OFFICIAL_DOCS`, `ONCHAIN_VERIFIABLE` | нет |
| `MECHANISM_SPEC` | `OFFICIAL_DOCS`, `GOVERNANCE` | нет |
| `GOVERNANCE_BASIS` | `GOVERNANCE` | нет |
| `EXECUTION_EVIDENCE` | `ONCHAIN_VERIFIABLE`, `OFFICIAL_REPORT` | нет (но §6.3) |
| `CURRENT_STATE` | `ONCHAIN_VERIFIABLE`, `OFFICIAL_DOCS`, `OFFICIAL_REPORT` | **да** |
| `DESTINATION` | `ONCHAIN_VERIFIABLE`, `OFFICIAL_DOCS` | нет |
| `RECIPIENT` | `ONCHAIN_VERIFIABLE`, `OFFICIAL_DOCS`, `GOVERNANCE` | нет |
| `NET_EFFECT` | `ONCHAIN_VERIFIABLE`, `OFFICIAL_REPORT`, `DATA_PROVIDER` | нет |
| `DURABILITY_BASIS` | `GOVERNANCE`, `OFFICIAL_DOCS` | нет |

Три следствия матрицы, которые и делают её содержательной:

- **`SOCIAL` не появляется ни в одной строке** — ни один компонент им не
  устанавливается, сколько бы таких элементов ни накопилось (D-074).
- **`OFFICIAL_DOCS` не может установить `EXECUTION_EVIDENCE`**:
  документация описывает механизм, а не факт его исполнения. Документы
  становятся контекстом, компонент — `INSUFFICIENT_EVIDENCE` с
  `MISSING_EXECUTION_EVIDENCE`.
- **`OFFICIAL_DOCS` не может установить `NET_EFFECT`**: «в документации
  написано burn» — это ярлык механизма, а не доказанный чистый эффект
  (`Mechanism Label ≠ Economic Outcome`, `Gross Burn ≠ Net Supply Effect`).
- **`GOVERNANCE` устанавливает `GOVERNANCE_BASIS` и может участвовать в
  `MECHANISM_SPEC`, но не `EXECUTION_EVIDENCE`**: одобренное предложение
  доказывает полномочие и намерение, не исполнение.

**Где живёт матрица — D-095, утверждено.** В `research_patterns.content`
рядом с `requiredComponents`, а не в коде реконсилятора. CORE —
человеческая методология (D-022), а `ComponentReconciler` обязан
оставаться переиспользуемым для Pattern v2: он **потребляет** требования
и никогда их не изобретает. Там же живут признак «требует текущего
состояния» и признак чувствительности к состоянию токена (§9.1).

Расширение `content` обязано быть аддитивным и обратно-совместимым:

- поведение планировщика Фазы 5 не меняется;
- семантика `steps` и `requiredComponents` не меняется;
- семантика памяти Фазы 5 не меняется;
- `npm run eval:memory` даёт идентичный результат;
- автоматической эволюции CORE не появляется — требования меняет человек.

Технически это уже безопасно: планировщик читает только `steps` и
`requiredComponents`, а `patternContentSchema` (zod-объект) неизвестные
ключи отбрасывает. Требования — не гипотеза реализации: отсутствующий
ключ означает отсутствующее требование, а не значение по умолчанию,
придуманное реконсилятором.

## 6. Текущее состояние и `mechanism_state`

### 6.1 Словарь — существующий, не изобретённый

Используется словарь CORE CHECK 2, тот же, что уже несёт
`research_memory.mechanism_state` (D-062 сравнивает именно его):

```
PROPOSED · APPROVED · IMPLEMENTING · LIVE · DEPRECATED · REMOVED · UNKNOWN
```

плюс `PAUSED` (план §8.1). Значения из формулировки задачи
(`ACTIVE`/`INACTIVE`/`EXECUTED`/`SUPERSEDED`) в репозитории отсутствуют и
**не вводятся**: они пересеклись бы с уже работающей семантикой D-062 в
памяти и породили бы два несовместимых словаря.

**Нормализация обязательна.** `evidence.mechanism_state` — свободная
строка от модели. S5 приводит её к словарю (регистр, пробелы, точное
совпадение). Неопознанное значение считается **отсутствующим**
(`UNKNOWN`), а не отдельным состоянием: иначе модель могла бы
изобретением строки и создать, и скрыть противоречие.

### 6.2 Что доказывает текущность

Компонент `CURRENT_STATE` устанавливается только элементом, который
одновременно: несёт нормализованное состояние ≠ `UNKNOWN`, входит в
допустимые классы и **имеет доказуемую основу текущести**:

- `published_at` внутри окна свежести компонента; **или**
- `source_class = ONCHAIN_VERIFIABLE` — ончейн-наблюдение фиксирует
  состояние в момент загрузки, поэтому основой служит `fetched_at`. Это
  единственное исключение, и оно узкое.

Нет ни того, ни другого → `MISSING_PUBLICATION_DATE`; дата есть, но вне
окна → `STALE_CURRENT_STATE`. Оба дают `INSUFFICIENT_EVIDENCE`, а не
«почти подтверждено».

**Окно свежести — свойство компонента, а не записи** (§0, следствие 2):
`CURRENT_STATE` — `HIGH_CHANGE`, `EXECUTION_EVIDENCE` — `MEDIUM_CHANGE`,
остальные — `LOW_CHANGE`; числовые значения берутся из уже существующего
`memory_stale_after_days` (D-044), новых ключей конфига не заводится.

### 6.3 Состояние ≠ исполнение

`PROPOSED`/`APPROVED` никогда не устанавливают `EXECUTION_EVIDENCE` и
никогда не дают `LIVE` для `CURRENT_STATE`. Утверждение в настоящем
времени требует `LIVE` (или `IMPLEMENTING` — с оговоркой §8), доказанного
допустимым классом.

## 7. Противоречие

**Условия — все одновременно:**

1. оба элемента относятся к одному `(step, component)` и оба пригодны;
2. оба несут нормализованное состояние ≠ `UNKNOWN` **и** различаются им;
   либо один `SUPPORTS`, другой `CONTRADICTS` при сопоставимом классе;
3. **каждый из них сам по себе способен установить именно этот компонент**
   по требованиям активного Pattern (§4, §5) — `SOCIAL`- или
   `INFERRED`-элемент не может заблокировать документально установленный
   механизм; иначе враждебная страница отключала бы выводы;
4. ни один не вытесняет другой по §8 временных правил.

Выполнены все четыре → `CONTRADICTED`, оба `memoryId`/`evidenceId`
предъявлены. Не выполнено любое → противоречия нет.

**Порог противоречия — тот же, что порог установления** (D-094):
элемент, который никогда не смог бы установить компонент, не может и
создать по нему терминальное противоречие. Проверка ведётся по
компоненту, а не по «силе источника вообще» — та же дисциплина, что в
§8.1a.

**Официальность порог не снимает и не поднимает.** `CLAIMED` не лишает
элемент пригодности устанавливать компонент (§4) — она ограничивает
результат до `PARTIALLY_SUPPORTED` (§8.2). Поэтому два пригодных
элемента с несовместимыми состояниями дают `CONTRADICTED` независимо от
`officiality`, а элемент недопустимого для компонента класса не даёт
противоречия ни при какой официальности.

**Расхождение формулировок при одинаковом состоянии противоречием не
является** (парафраз) — прямое наследование D-062.

**Разрешение — только свежим доказательством.** S5 никогда не выбирает
«более уверенную» или «более приятную» сторону: это ровно то, что закрывал
финальный блокер Фазы 5. Единственный законный путь из `CONTRADICTED` —
новое доказательство, вытесняющее одну из сторон по §8.

**Модель результата — одно состояние `CONTRADICTED`**, а не
`INSUFFICIENT_EVIDENCE` + флаг: конфликт и пустота требуют разных
действий и разных слов пользователю.

## 8. Время, вытеснение и частичная поддержка

### 8.1 Вытеснение

Элемент B вытесняет A, только если **все** условия выполнены:

1. оба несут состояние ≠ `UNKNOWN` по одному компоненту;
2. у обоих есть сопоставимая основа даты (`published_at`; для
   `ONCHAIN_VERIFIABLE` — `fetched_at`);
3. B **строго новее** A;
4. B **не менее пригоден для установления именно этого компонента**, чем A
   (D-078 в редакции D-093).

### 8.1a Условие 4 — авторитет относителен компоненту (нормативно, D-093)

**Глобального рейтинга `sourceClass` не существует и вводить его
запрещено.** Условие 4 сравнивает не «силу класса вообще», а пригодность
устанавливать **этот** компонент по требованиям активного Pattern (§5,
D-095):

- если A устанавливает компонент, то B вытесняет A только когда B тоже
  входит в множество устанавливающих классов этого компонента;
- если B в это множество не входит — вытеснения нет, каким бы «сильным»
  класс B ни выглядел в отрыве от компонента;
- сравнение всегда идёт внутри одного компонента; результат для одного
  компонента ничего не говорит о другом.

Почему это не формальность:

- `OFFICIAL_DOCS` превосходен для `MECHANISM_SPEC` и недостаточен для
  `EXECUTION_EVIDENCE` — свежая документация не вытесняет ончейн-запись
  об исполнении;
- `GOVERNANCE` устанавливает `GOVERNANCE_BASIS` и не устанавливает
  исполнение — новое одобренное предложение не вытесняет доказательство
  того, что механизм фактически работает;
- `ONCHAIN_VERIFIABLE` устанавливает исполнение и текущее состояние там,
  где Pattern это разрешает, и не становится от этого универсально
  старшим классом.

Реализация обязана выводить условие 4 из требований компонента. Любая
константа вида `CLASS_RANK`, применяемая к вытеснению между компонентами,
нарушает D-093 и роняет мутацию §15.23.

Тогда A получает `SUPERSEDED_BY_NEWER`, остаётся в выводе как история и
перестаёт участвовать в установлении и в противоречии.

Не выполнено любое условие — вытеснения нет. **«Новее — значит правее»
как самостоятельного правила не существует**: у большинства элементов
даты может не быть вовсе, и тогда единственный честный исход —
противоречие или недостаточность, а не молчаливый выбор строки. Нет
сопоставимой основы даты — вытеснение не применяется молча; отсутствие
доказательства не становится доказательством отсутствия (D-078).

> Полный порядок сортировки §12 (в нём есть ранг класса) — это
> детерминированный tie-break для **вывода**, а не правило авторитета:
> он не участвует ни в условии 4, ни в §4, ни в §7.

`2025: LIVE` → `2026: DEPRECATED` — это **вытеснение** (законный переход
состояния), а не противоречие. Два элемента одного периода с разными
состояниями и без вытеснения — **противоречие**.

Старое доказательство остаётся пригодным для `DURABILITY_BASIS` и
исторических компонентов и непригодным для `CURRENT_STATE`: пригодность
считается по компоненту, а не глобально по записи.

### 8.2 `PARTIALLY_SUPPORTED` — закрытый список оснований

Состояние ставится, только если есть устанавливающий элемент **и**
применимо хотя бы одно из четырёх, каждое со своим кодом:

| Основание | Код |
|---|---|
| лучший устанавливающий элемент имеет `officiality = CLAIMED` | `INSUFFICIENT_AUTHORITY` |
| ни одного `DIRECT`, но есть `INDIRECT` допустимого класса | `INDIRECT_ONLY` |
| состояние `IMPLEMENTING` там, где утверждение требует `LIVE` | `STATE_NOT_FULLY_LIVE` |
| компонент чувствителен к состоянию токена и выполнены все три условия §9.1 | `TOKEN_STATE_UNQUALIFIED` |

Список закрыт намеренно: **`PARTIALLY_SUPPORTED` без кода из этой
таблицы невозможен** — это и мешает состоянию стать мусорной корзиной.
Расширение списка — новое решение владельца, а не решение реализации:
`PARTIALLY_SUPPORTED` не является общим ведром для неуверенности. Всё,
что не подпадает ни под одно из четырёх оснований, обязано быть либо
`SUPPORTED`, либо `INSUFFICIENT_EVIDENCE`, либо `CONTRADICTED`.

## 9. Состояние токена и экономический поток

`CRV ≠ veCRV`, `AAVE ≠ stkAAVE`, ликвидный токен ≠ locked/staked/wrapped
/производное состояние, и `Same Asset ≠ Same Economic Flow`. Но
структурных полей для этого в Evidence **нет**: `value_source` не
заполняется, поля token state не существует. Требовать их — переоткрыть
S4, что запрещено.

**D-096: S5 обнаруживает, но не судит.**

- S5 детерминированно ищет квалификаторы производного состояния токена по
  **закрытому, кодом владеемому списку** (`ve`, `vote-escrowed`, `locked`,
  `staked`, `wrapped`, …) с проверкой по границам токенов — та же
  дисциплина, что уже применена в проверке содержания проекта S4.
- Поиск ведётся **только по персистированному содержимому Evidence,
  которое действительно поддерживает компонент** (`fragment`, `summary`
  устанавливающих элементов) — то есть по тексту, который видела модель и
  который лежит в БД. Ни поиск, ни повторная загрузка, ни вывод модели
  здесь не используются.
- Находка записывается в `tokenStateMentions` **всегда** — это наблюдение,
  переносимое в S6, а не приговор.
- Элемент **никогда** не исключается за квалификацию, разные состояния
  токена **никогда** не сливаются как эквивалентные, поддержка от
  обнаружения **никогда** не повышается.

### 9.1 Когда квалификация понижает — три условия (нормативно)

**Сама по себе точная квалификация состояния токена слабостью не
является.** «veCRV holders receive protocol fees» — это сильное, точное
доказательство, и понижать его только за то, что состояние названо
точно, запрещено: иначе S5 наказывал бы именно за ту точность, которой
требует методология.

Понижение до `PARTIALLY_SUPPORTED` + `TOKEN_STATE_UNQUALIFIED` ставится,
только если выполнены **все три** условия:

1. компонент объявлен **чувствительным к состоянию токена** — `RECIPIENT`,
   `DESTINATION`, `NET_EFFECT` либо иной компонент, явно помеченный
   таковым в требованиях Pattern (D-095); **и**
2. устанавливающее Evidence ссылается на квалифицированное состояние
   токена; **и**
3. требование компонента (`ComponentRequirements` / `ComponentWorkItem`)
   **не устанавливает**, что это квалифицированное состояние совпадает с
   тем состоянием токена, которое компонент требует.

Следствия, каждое из которых обязано быть покрыто тестом:

- **Требуемое состояние явно то же самое → понижения нет.** Компонент,
  чьё требование прямо названо `veCRV`, при Evidence про `veCRV`
  остаётся `SUPPORTED`.
- **Совпадение состояний требует семантического вывода → S5 не выводит.**
  Догадка «staked X, вероятно, тот же поток, что X» в S5 не делается ни в
  какую сторону: квалификация переносится вперёд как
  `tokenStateMentions`, компонент понижается до
  `PARTIALLY_SUPPORTED`, окончательное суждение — за S6.
- **Требование Pattern о состоянии токена отсутствует → условие 3
  выполнено** (равенство не установлено), понижение применяется.

**Идентичность экономического пути остаётся задачей S6.** S5 даёт ему
факт квалификации и повод не считать состояния равными молча.

Цепочка собирается в S6; S5 не имеет структурного признака потока и обязан
этого не изображать. Изоляция, которую S5 действительно обеспечивает:
компонент (проверяется), проект (уже обеспечен S4 лексическим
содержанием), состояние токена (обнаруживается, при трёх условиях
понижает, всегда переносится вперёд). **Заполнение `value_source` при
извлечении — работа S6**, а не повод трогать замороженный S4.

## 10. Исключения — решение о пригодности, не мутация

S5 **никогда** не изменяет и не удаляет Evidence. Он лишь помечает, что
элемент не участвует в этой реконсиляции, и почему.

```
WRONG_COMPONENT · WRONG_PROJECT · LEGACY_CONTRACT_VERSION
CLASS_NOT_ADMISSIBLE · DIRECTNESS_INSUFFICIENT · RELATIONSHIP_NOT_SUPPORTING
NOT_CURRENT_STATE_BEARING · MISSING_PUBLICATION_DATE · STALE_FOR_CURRENT_STATE
SUPERSEDED_BY_NEWER · DUPLICATE_UNIT
```

Коды результата (для контроллера и для Proof):

```
NO_EVIDENCE_FOUND · ALL_EVIDENCE_EXCLUDED · MISSING_EXECUTION_EVIDENCE
MISSING_CURRENT_STATE · STALE_CURRENT_STATE · INSUFFICIENT_AUTHORITY
INDIRECT_ONLY · STATE_NOT_FULLY_LIVE · CONFLICTING_STATE
TOKEN_STATE_UNQUALIFIED
```

Оба множества закрыты; произвольных строк в них не появляется.

## 11. Контракт данных

### 11.1 Вход

```ts
interface ComponentReconciliationInput {
  item: ComponentWorkItem;            // из ContractView, не копия
  requirements: ComponentRequirements; // из активного Pattern (D-095)
  evidence: EvidenceRow[];            // все строки job'а по (step, component)
  now: Date;                          // передаётся, не читается из часов
  freshnessPolicyDays: Record<"LOW_CHANGE"|"MEDIUM_CHANGE"|"HIGH_CHANGE", number>;
}

interface ComponentRequirements {     // данные Pattern/CORE, не код (D-095)
  component: string;
  establishingClasses: SourceClass[]; // §5; пусто ⇒ компонент не устанавливается
  requiresCurrentState: boolean;      // §6.2
  freshnessClass: "LOW_CHANGE" | "MEDIUM_CHANGE" | "HIGH_CHANGE";
  tokenStateSensitive: boolean;       // §9.1 условие 1
  requiredTokenState: string | null;  // §9.1 условие 3; null ⇒ равенство не установлено
}
```

`establishingClasses` — единственный источник авторитета в срезе: по нему
считаются §4 (установление), §7 (порог противоречия) и §8.1a (вытеснение).
Глобального рейтинга классов рядом с ним не существует (D-093).

`requiredTokenState` сравнивается **точным нормализованным совпадением**
строки квалификатора. Отсутствие ключа = `null` = равенство не
установлено; выводить равенство S5 не имеет права (§9.1).

Ни `ContractView` целиком, ни бюджет, ни контроллер сюда не входят: у
реконсилятора не должно быть доступа к тому, чем он не имеет права
управлять.

### 11.2 Выход

```ts
interface ComponentReconciliationResult {
  step: number;
  component: string;
  status: "SUPPORTED" | "PARTIALLY_SUPPORTED" | "CONTRADICTED" | "INSUFFICIENT_EVIDENCE";
  reasonCodes: ResultReasonCode[];          // закрытый словарь §10; для
                                            // PARTIALLY_SUPPORTED непуст всегда
  supportingEvidenceIds: string[];          // отсортированы детерминированно
  contradictingEvidenceIds: string[];
  excludedEvidence: { evidenceId: string; reason: ExclusionReason }[];
  currentState: MechanismState | null;      // нормализованное, если компонент его несёт
  temporalBasis: { basisField: "published_at" | "fetched_at"; at: string } | null;
  tokenStateMentions: string[];             // обнаружено, не осуждено (§9)
  requiresFreshEvidence: boolean;           // производное: CONTRADICTED | INSUFFICIENT
}
```

Каждое поле обосновано: `supporting`/`contradicting`/`excluded` отвечают
на «какое Evidence дало это состояние» (§17 задачи); `currentState` и
`temporalBasis` нужны S6 и слою «Что может изменить вывод»;
`tokenStateMentions` переносит наблюдение в S6 без суждения;
`requiresFreshEvidence` — единственное, что читает контроллер.
**Числового confidence здесь нет** (D-081, считается в S7).

### 11.3 Персистенция

`research_component_results`: одна строка на `(research_job_id,
pattern_step, component)`, уникальный индекс по этой тройке, upsert.
Имя уже зарезервировано комментарием схемы S3.

Строка объявляется **производной проекцией, а не вторым хранилищем
истины**: удаление всех строк и повторный прогон обязаны дать побайтово
тот же результат из того же Evidence. Персистенция нужна для аудита
(«какое Evidence дало состояние»), для потребления S6 без пересчёта и
для гейтящих метрик §14.1 плана — но истина остаётся в `evidence`.

## 12. Детерминизм, идемпотентность, продолжение исследования

**Детерминизм.** Порядок сортировки фиксирован и полон:
`published_at DESC NULLS LAST` → ранг класса → ранг официальности → ранг
прямоты → `content_hash` → `evidence.id`. Последние два гарантируют
полный порядок при полностью одинаковых элементах, поэтому порядок строк
из БД, порядок вставки и порядок источников на результат не влияют.

**Модель в S5 не используется вовсе.** Каждое правило выше структурно:
enum, дата, класс, нормализованный словарь, лексический детектор по
закрытому списку. Точка, где семантическое суждение действительно
понадобится, известна и названа: сопоставление свободного текста двух
утверждений — это Critic-слой, отложенный планом §10.4, а не S5. Раз
модели нет — нет и поверхности prompt-инъекции: содержимое `fragment`
используется как данные (лексический поиск, сравнение), никогда как
инструкция.

**Идемпотентность.** Функция чистая; повторный прогон при том же Evidence
даёт тот же результат, upsert не плодит строк. Падение между S5 и S6
безопасно: S6 читает строки, а не «состояние вычисления».

**Продолжение исследования S5 не запускает** (§22 задачи): он возвращает
состояние и коды. Решение «делать ли ещё попытку» принимает контроллер по
`requiresFreshEvidence` + кодам, в пределах уже замороженного бюджета и
области контракта. Реконсилятор не имеет доступа ни к бюджету, ни к
очереди — по конструкции, а не по договорённости.

**Успешная недостаточность ≠ сбой** (D-084). Системный сбой — только:
невалидный контракт/Pattern, несовпадение `patternVersion`, нарушение
инварианта (v2-строка без обязательных полей классификации — то, что
запрещает CHECK в БД), ошибка БД. Отсутствие Evidence — успешный
результат `INSUFFICIENT_EVIDENCE` с кодом `NO_EVIDENCE_FOUND`.

## 13. Алгоритм по шагам

```
1. Загрузить Evidence job'а по (step, component). Пусто → INSUFFICIENT_EVIDENCE
   (NO_EVIDENCE_FOUND). Успех, не ошибка.
2. Отбросить непригодные: версия контракта, чужой компонент, чужой проект,
   дубли по extraction_unit_key. Каждому — код исключения.
3. Нормализовать mechanism_state по словарю CORE; неопознанное → UNKNOWN.
4. Применить временные правила: вычислить основу текущести, отметить
   вытесненные (SUPERSEDED_BY_NEWER).
5. Отобрать устанавливающие элементы по §4 + матрице §5 (+ §6.2 для
   компонентов, требующих текущего состояния). Неподходящим — код.
6. Обнаружить противоречие по §7 среди элементов, способных устанавливать.
   Есть → CONTRADICTED, стоп.
7. Устанавливающих нет → INSUFFICIENT_EVIDENCE с наиболее специфичным кодом
   (MISSING_EXECUTION_EVIDENCE / MISSING_CURRENT_STATE / STALE_CURRENT_STATE /
   ALL_EVIDENCE_EXCLUDED).
8. Есть → проверить основания §8.2. Есть хоть одно → PARTIALLY_SUPPORTED
   с кодами; нет ни одного → SUPPORTED.
9. Собрать результат в детерминированном порядке, сделать upsert.
```

Шаг 6 стоит **до** шага 8 намеренно: конфликт важнее оговорки, и
компонент с конфликтом не может «частично поддерживаться».

## 17. Передача в разработку и гейт приёмки

**Разработка получает:** §11 (схемы), §13 (алгоритм), §5–§9 (правила),
§14–§15 (тесты). Порядок: требования Pattern (D-095) → чистая функция
реконсиляции + юнит-тесты → персистенция и upsert → интеграция с
контроллером → мутационные тесты.

### 17.1 Граница S5 (нормативно)

S5 **остаётся**: детерминированным, без модели, без сети,
ограниченным компонентом, связанным с provenance.

S5 **не имеет права**: искать; загружать; вызывать LLM; пересчитывать
`sourceClass`; пересчитывать `officiality`; изменять Evidence; повышать
память; расширять область Boundary Contract; собирать экономическую
цепочку; выдавать финальный вердикт; назначать числовой confidence.

### 17.2 Гейт приёмки

**S5 принят, когда:**

- все сценарии §14 (A–Y) зелёные;
- все 29 мутаций §15 роняют тесты;
- в пути реконсиляции нет ни одного вызова модели, поиска или загрузки;
- `sourceClass`, `officiality` и строки `evidence` не изменяются
  (доказывается тестом, а не обещанием);
- память не пишется ни в каком виде (D-021, D-025, D-075);
- в коде нет глобального рейтинга классов, применяемого к вытеснению,
  противоречию или установлению (D-093);
- требования компонента читаются из Pattern, отсутствующий ключ не
  подменяется значением по умолчанию (D-095);
- понижение по состоянию токена ставится только по трём условиям §9.1,
  а `tokenStateMentions` заполняется независимо от понижения (D-096);
- регрессия Фаз 1–5 зелёная, `npm run eval:memory` **побайтово не
  изменился**, семантика памяти Фазы 5 не тронута;
- S6-логики (цепочка, destination/recipient, вердикт, confidence) в
  срезе нет.

**S4 остаётся замороженным** — ни один пункт этой стратегии не требует
его изменения; `value_source` заполняется в S6, а не ретроспективно в S4.
**S6 не начат.**
