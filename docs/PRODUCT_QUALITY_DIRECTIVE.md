# ATLAS PROOF — Product Quality Directive

Статус: утверждена владельцем 2026-08-20. Действует на все фазы реализации.
Не отменяет LOCKED decisions и не разрешает самостоятельно менять продуктовую
стратегию. Настоящий стратегический конфликт → STRATEGY REVIEW REQUIRED.

Главный приоритет ATLAS PROOF — не количество функций и не визуальные
эффекты сами по себе. Продукт должен создавать ощущение:

> **мощный интеллект внутри → предельно простой опыт снаружи.**

Пользователь не должен видеть сложность архитектуры, исследовательского ядра,
состояний, очередей, Evidence-механики или внутренних процессов. Он должен
задать понятный вопрос и чувствовать, что ATLAS понимает его намерение,
аккуратно обрабатывает запрос и ведёт к результату.

## 1. CORE FIRST

Самое важное — качество ядра. Архитектура, state management, auth, research
pipeline, persistence, error handling и будущая ARI-логика должны быть
надёжнее визуальной оболочки.

Нельзя улучшать внешний UX ценой: нестабильного состояния; потерянных данных;
race conditions; ложного состояния успеха; фейковой загрузки; скрытой ошибки;
непредсказуемого поведения.

Приоритет при конфликте:

```
correctness → reliability → performance → simplicity → visual polish
```

Но пользователь не должен ощущать эту сложность.

## 2. INVISIBLE COMPLEXITY

Ориентир — лучшие современные AI-продукты: очень простой интерфейс поверх
сложной системы. Внутренняя архитектура ATLAS не переносится в UI.

Пользователь не должен разбираться: что такое worker; какие существуют
состояния research job; как устроена очередь; какие внутренние слои ARI
отработали; как устроена БД; какие технические операции происходят.

Интерфейс переводит сложность в простые человеческие состояния:

```
Задал вопрос → Atlas понял → исследует → показывает результат
```

## 3. MOBILE-FIRST

ATLAS PROOF в первую очередь проектируется для телефона. Любое решение
сначала оценивается на мобильном экране.

Интерфейс должен: быстро считываться; хорошо работать одной рукой; иметь
понятную визуальную иерархию; не заставлять думать, куда нажимать;
не перегружать экран; сохранять главное действие очевидным; избегать мелких
touch targets; не превращать Proof в тяжёлый технический отчёт.

Desktop — адаптация продукта, а не исходная точка дизайна.

## 4. SOFT MOTION

Анимация не должна превращать ATLAS PROOF в демонстрацию motion-design.

Характер движения: **soft · calm · intelligent · premium · responsive**.

Утверждённая Motion System: micro ≈ 140ms; transition ≈ 200ms; large ≈ 280ms;
преимущественно transform + opacity; никаких тяжёлых 500ms+ переходов;
обязательный prefers-reduced-motion.

Анимация помогает понять: что элемент отреагировал; куда перешёл
пользователь; что процесс начался; что состояние изменилось; что появилось
новое содержимое. Не использовать движение только ради красоты.

Избегать: bouncing UI; чрезмерного glow; постоянных фоновых движений; длинных
cinematic transitions; анимаций, мешающих быстро пользоваться приложением.

Правильное ощущение: интерфейс не прыгает — он мягко отвечает пользователю.

## 5. IMMEDIATE FEEDBACK

Приложение никогда не должно казаться зависшим. После действия пользователя
интерфейс реагирует практически сразу:

```
user action → immediate visual acknowledgement → async work
→ meaningful progress/state → result
```

Не имитировать готовый результат. Не использовать fake completion. Если
работа действительно продолжается — честно показывать это простым языком.

## 6. PERFORMANCE IS PART OF DESIGN

Плавность — не декоративная задача. Следить за: unnecessary re-renders;
layout shifts; тяжёлыми зависимостями; большим JS bundle; лишними network
requests; блокировкой main thread; медленной первой отрисовкой;
неоптимальными изображениями; лишним polling; memory leaks.

Не добавлять библиотеку, если задача нормально решается существующим стеком.
ATLAS должен ощущаться быстрым даже тогда, когда само исследование занимает
время.

## 7. SIMPLE LANGUAGE

Пользовательский текст значительно проще внутренней системы. Не писать
техническими терминами там, где можно сказать человеческим языком.

Внутренние состояния (QUEUED / RUNNING / AWAITING_CLARIFICATION) пользователь
не видит — он видит естественные формулировки вида «Atlas начинает проверку»,
«Изучаю источники», «Нужно уточнение», «Proof готов».

Конкретный copy утверждается отдельно — это принцип, а не разрешение
самостоятельно менять продуктовый язык.

## 8. QUALITY BAR

Постоянный вопрос при реализации:

> «Можно ли сделать внутреннюю систему надёжнее, а пользовательский путь — проще?»

Если ответ «да» — предпочитать это решение. Не путать простоту
с примитивностью. ATLAS PROOF должен выполнять сложную интеллектуальную
работу, при этом пользователь должен чувствовать:

> **«Я просто спросил — Atlas разобрался.»**

Это целевое ощущение продукта.
