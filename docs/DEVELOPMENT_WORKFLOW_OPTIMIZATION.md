## 1. Анализ текущего процесса

### 1.1 Как принимаются решения сейчас

Цикл фазы работает и дал результат: Фазы 1–4 закрыты, дефекты ловятся
до владельца, а не после. Последовательность (по утверждённому workflow):

```
план → ревью владельца → реализация → тесты → adversarial review
→ разбор находок → отчёт
```

Что реально удерживает качество: план пишется до кода; ревьюер приходит
со свежим контекстом; каждая находка требует сценария отказа; спорные
продуктовые развилки уходят владельцу, а не решаются молча.

Это менять не нужно. Оптимизировать нужно **стоимость входа в контекст**,
а не сам цикл.

### 1.2 Где на самом деле уходят токены

Измерено на этом проекте (символы ÷ 4 ≈ токены):

| Что | Объём | ≈ токенов |
|---|---|---|
| `docs/handoff/canonical/` (4 документа) | 253 894 симв. | **~63 000** |
| `docs/implementation/` (планы фаз) | 220 518 симв. | ~55 000 |
| `.claude/skills/` (5 skills) | 66 474 симв. | ~16 600 |
| **`01_LOCKED_DECISIONS.md`** | 18 756 симв. | **~4 700** |
| Весь `docs/` целиком | 584 160 симв. | ~146 000 |

Разовые расходы, зафиксированные в этой сессии:

| Операция | Стоимость |
|---|---|
| Adversarial review Фазы 4 (1 агент) | ~151 000 токенов |
| Исследование под план Фазы 5 (10 агентов) | **~865 000 токенов** |
| Живой прогон Interpreter, 20 вопросов | ~25 000 токенов ≈ $0.035 |

**Вывод, который важнее выбора модели.** Один веерный запуск агентов стоит
дороже, чем вся реализация средней фазы. А `LOCKED` в 13 раз компактнее
canonical и по правилу A2 **имеет приоритет над ним**. Значит два главных
рычага экономии — это не «модель подешевле», а:

1. не поднимать canonical там, где отвечает LOCKED;
2. не запускать веерные исследования вне границ «план новой фазы».

### 1.3 Где сейчас используется слишком сильная модель

- рутинная реализация по уже утверждённому плану;
- написание тестов по готовому DoD-списку;
- миграции по описанной в плане схеме;
- правки UI и i18n;
- отчёты и сводки для владельца;
- разбор мелких дефектов с известной причиной.

### 1.4 Что можно удешевить без потери качества

- генерация вариаций пользовательских формулировок для тестов (опечатки,
  сленг, раскладка) — но **не** ожидаемых результатов;
- черновики продуктовых текстов (финал — за владельцем);
- простая классификация и разметка;
- runtime-задачи внутри продукта (Interpreter уже на Haiku).

### 1.5 Что удешевлять нельзя

Архитектура, security, CORE-методология, Learning Loop, инварианты БД,
финальное ревью фазы. Здесь ошибка стоит дороже сэкономленных токенов:
дефект уровня HIGH-1 в Фазе 4 (гейт проверял одну сущность из двух)
пропустил бы любой поверхностный проход.

## 2. Стратегия распределения моделей

### Claude Opus

Только там, где решение трудно откатить:

- архитектурные решения и их обоснование;
- планы новых фаз (`docs/implementation/phase-N-plan.md`);
- любой конфликт с LOCKED → `STRATEGY REVIEW REQUIRED`;
- security-решения (границы доверия, инъекции, приватность, entitlement);
- **adversarial review в конце фазы** и финальный отчёт;
- разбор находок ревью (принять/отклонить с обоснованием).

### Claude Sonnet

Основная рабочая модель:

- реализация утверждённого плана;
- тесты по DoD-списку;
- миграции по описанной схеме;
- UI, i18n, вёрстка, motion;
- рефакторинг без смены поведения;
- отчёты и сводки по готовым фактам;
- починка дефектов с уже установленной причиной.

### Claude Haiku

- простая классификация и разметка;
- вариации входных данных для тестов;
- черновики копирайта;
- **runtime внутри продукта** — Question Interpreter (уже так работает,
  решение владельца зафиксировано в `phase-4-freeze.md`).

## 3. Правила маршрутизации задач

| Задача | Модель | Почему |
|---|---|---|
| План новой фазы | **Opus** | Определяет всё, что будет построено; ошибка проявится через недели |
| Конфликт с LOCKED | **Opus** | Требуется `STRATEGY REVIEW REQUIRED`, а не самостоятельное решение |
| Security-решение | **Opus** | Инъекции, приватность, entitlement — цена ошибки не измеряется токенами |
| Схема БД и инварианты | **Opus** | Констрейнты живут дольше кода; миграция назад дороже |
| Adversarial review фазы | **Opus** | Единственный барьер перед владельцем |
| Разбор находок ревью | **Opus** | Решение «отклоняю находку» требует того же уровня, что и находка |
| Реализация по плану | **Sonnet** | Решения уже приняты; задача — точное исполнение |
| Тесты по DoD | **Sonnet** | Список проверок задан планом |
| Миграция по плану | **Sonnet** | Схема описана; работа механическая |
| Изменение UI / i18n | **Sonnet** | Продуктовые решения приняты, вопрос исполнения |
| Bug fix с известной причиной | **Sonnet** | Диагноз готов |
| Bug fix с неизвестной причиной | **Opus → Sonnet** | Opus ставит диагноз, Sonnet чинит |
| Документация-отчёт | **Sonnet** | Пересказ уже установленных фактов |
| Документация-архитектура | **Opus** | План фазы — это решение, а не описание |
| Вариации входов для тестов | **Haiku** | Механическая генерация формулировок |
| Ожидаемые результаты тестов | **Opus/Sonnet** | Это и есть определение правильности — не отдавать дешёвой модели |
| Черновик копирайта | **Haiku → владелец** | Финал за владельцем (директива качества) |
| Interpreter внутри продукта | **Haiku** | Решение владельца; понимание, а не исследование |
| Research Engine внутри продукта | **решается в Фазе 6** | Не предрешать здесь |

**Правило смены модели.** Переключение модели в уже длинном чате
экономит только стоимость вывода: загруженный контекст никуда не
девается. Настоящая экономия — новый чат с коротким handoff (§4).

## 4. Управление контекстом

### 4.1 Иерархия источников (по A2, уже действует)

```
01_LOCKED_DECISIONS.md   приоритет над всем остальным   ~4 700 токенов
план текущей фазы        что именно строим              ~5 000–9 000
нужный skill             канон конкретного слоя         ~3 000
canonical                ТОЛЬКО при пробеле в LOCKED    ~63 000
```

Правило: **canonical поднимается точечно** — grep по разделу, а не файл
целиком. Все четыре документа canonical сразу не загружаются никогда.

### 4.2 Что прикладывать по типу задачи

| Задача | Достаточный контекст |
|---|---|
| Реализация фазы | план фазы + затрагиваемые файлы + `DECISIONS.md` |
| Тесты | DoD-раздел плана + тестируемые модули |
| UI | `atlas-product-ui` + директива качества + экран |
| Interpreter/Memory/Proof | соответствующий skill + план фазы |
| Новый план фазы | LOCKED + `02_ARCHITECTURE_AND_PHASES` + предыдущий план + точечно canonical |
| Отчёт владельцу | результаты проверок; ничего больше |

### 4.3 Что не нужно каждый раз

- полные canonical-документы;
- планы уже закрытых фаз (для них есть freeze-документы);
- история чата предыдущей фазы;
- `ARI_LEARNING_LOOP_DIRECTIVE_SECTIONS_4_34.md` (1 292 строки) — нужен
  только при работе над самим Learning Loop.

### 4.4 Формат короткого handoff

Открывая новый чат, вставить это и ничего больше:

```
Context:      ATLAS PROOF — Research Intelligence for Digital Assets,
              Telegram Mini App. Репозиторий подключён.
Current phase: Фаза N — <название>. План: docs/implementation/phase-N-plan.md
              (УТВЕРЖДЁН владельцем).
Goal:         <одно предложение: что должно существовать в конце>
Constraints:  Работать строго по утверждённому плану. Архитектуру не
              менять. LOCKED-решения не пересматривать. При конфликте —
              вывести STRATEGY REVIEW REQUIRED и остановиться.
              Прочитать перед началом: docs/DECISIONS.md,
              docs/implementation/phase-N-plan.md.
Task:         <конкретное действие>
```

Handoff умышленно **не пересказывает** решения — он указывает, где они
лежат. Пересказ решений в чате и есть главный источник их искажения.

## 5. Разделение чатов

Причина не в удобстве, а в арифметике: длинный чат несёт всю свою историю
в каждый следующий запрос. Чат, проживший целую фазу, стоит дороже с
каждым сообщением, даже если задача стала проще.

| Чат | Модель | Содержание | Когда открывается |
|---|---|---|---|
| **1. Архитектура и стратегия** | Opus | планы фаз, LOCKED-конфликты, Learning Loop, разбор находок | долгоживущий, но используется редко |
| **2. Реализация** | Sonnet | код, миграции, тесты, UI одной фазы | новый на каждую фазу, закрывается с ней |
| **3. Проверка** | Opus | adversarial review со свежим контекстом | новый на каждую фазу, обязательно чистый |
| **4. Продукт и UX** | Sonnet/Haiku | копирайт, состояния экранов, тексты ошибок | по мере надобности |

**Жёсткое ограничение, снимающее конфликт с утверждённым workflow:**
одновременно писать в код имеет право **только чат 2**. Остальные —
читают. Это сохраняет правило «Main Claude — единственный владелец
реализации» и исключает два параллельных редактора одного файла.

Чат 3 обязан быть чистым: ревьюер, видевший, как писался код, уже не
независим. Это требование существующего мандата, а не новое.

## 6. Механизм против повторного обсуждения решений

### 6.1 Проблема

Продуктовые решения лежат в `01_LOCKED_DECISIONS.md`. А вот
**реализационные** решения рассыпаны по планам фаз: вариант A для
`CANCEL_AT_PERIOD_END`, bootstrap-исключение для `/api/auth/telegram`,
принцип «PostgreSQL — source of truth, SSE — транспорт», structured-first
retrieval. Чтобы их не пересматривать заново, нужно уметь прочитать их
за секунды, а не искать по 220 000 символов планов.

### 6.2 Решение: `docs/DECISIONS.md`

Единый append-only реестр, компактный по построению: одна строка на
решение плюс ссылка на место, где оно обосновано.

```
ID:        D-014
Decision:  CORE не обновляется автоматически. Переход CANDIDATE → ACTIVE
           выполняет человек.
Status:    LOCKED
Where:     docs/ARI_LEARNING_LOOP.md §11
Date:      2026-08-20
Revisit:   только через STRATEGY REVIEW REQUIRED
```

Статусы: `LOCKED` (не пересматривать), `OPEN` (ждёт владельца),
`SUPERSEDED` (заменено — с указанием, чем).

### 6.3 Правило работы

- любое решение владельца в чате → строка в `DECISIONS.md` в том же коммите;
- начало любой задачи → сначала `DECISIONS.md`, потом всё остальное;
- решение со статусом `LOCKED` не обсуждается: если работа требует его
  изменить — `STRATEGY REVIEW REQUIRED` и остановка.

### 6.4 Открытые решения на сегодня

Их нужно внести в реестр как `OPEN`, иначе они потеряются:

| Вопрос | Где описан |
|---|---|
| Глубина уточнения Interpreter: вариант 1 или 2 | `phase-4-freeze.md` §5 |
| Повтор при пропуске `understood_summary` | предложено после живого прогона |
| Retrieval Фазы 5: structured-first без pgvector | `phase-5-plan.md` §11.1 |
| `proofs.verification_status` и кто ставит VERIFIED | `phase-5-plan.md` §11.2 |
| Запрет кросс-проектного обобщения в v1 | `phase-5-plan.md` §11.3 |
| Ключ `memory_enabled` | `phase-5-plan.md` §11.4 |
| Приведение словаря `freshness_class` | `phase-5-plan.md` §11.5 |
| Финальный copy пользовательских текстов | `phase-3-plan.md` §6, `phase-4-freeze.md` |

## 7. Цикл разработки

### 7.1 Владелец — отдельный слой решений (дополнение владельца)

Opus **готовит варианты**, владелец **утверждает**, Sonnet **строит**:

```
Opus     →  варианты и обоснование, без самостоятельного выбора
             там, где выбор продуктовый
Владелец →  решение
Sonnet   →  исполнение принятого решения
```

Это не формальность цикла, а отражение того, где на самом деле находится
источник истины в ATLAS. Продуктовых развилок здесь больше, чем
технических: глубина уточнения Interpreter, показывать ли короткий ответ
без Proof, что считать «половиной сравнения», допускать ли эмбеддинги —
ни одна из них не выводится из кода.

Практические следствия:

- Opus, дойдя до продуктовой развилки, **останавливается и предъявляет
  варианты с рекомендацией**, а не выбирает молча;
- Sonnet не начинает реализацию, пока решение не записано в
  `docs/DECISIONS.md` со статусом, отличным от `OPEN`;
- решение, принятое владельцем в чате, попадает в реестр в том же
  коммите — иначе оно существует только в переписке и будет
  переспрошено.

### 7.2 Цикл

```
Opus (чат 1)      План фазы + варианты по развилкам
                        ↓
                  РЕШЕНИЕ ВЛАДЕЛЬЦА  ← код не пишется до «подтверждаю»
                  → запись в DECISIONS.md
                        ↓
Sonnet (чат 2)    Реализация строго по плану
                        ↓
Sonnet (чат 2)    Тесты DoD + build + tsc + eslint
                        ↓
Opus (чат 3)      Adversarial review, свежий контекст
                        ↓
Opus (чат 1)      Разбор находок: принято / отклонено с обоснованием
                        ↓
Sonnet (чат 2)    Починка принятых находок
                        ↓
Opus (чат 1)      Отчёт владельцу + freeze-документ + DECISIONS.md
```

Эскалация: Sonnet, встретив расхождение с планом, конфликт с LOCKED или
неочевидное security-следствие, **останавливается** и передаёт вопрос в
чат 1. Он не принимает архитектурных решений сам — это и есть граница,
делающая удешевление безопасным. Если развилка продуктовая, чат 1 не
решает её сам, а выносит владельцу (§7.1).

## 8. Как двигаться дальше в ATLAS

**Текущий статус:**

```
Фазы 1–3   закрыты
Фаза 4     заморожена (phase-4-freeze.md), Interpreter v1 принят
Фаза 5     план написан, ждёт ревью владельца
```

**Ближайшие шаги в предлагаемом процессе:**

1. **Чат 1 (Opus).** Владелец разбирает пять решений из `phase-5-plan.md`
   §11 и открытые пункты Фазы 4. Результат → `DECISIONS.md`.
2. **Чат 2 (Sonnet), отдельная короткая задача.** Открытые дефекты Фазы 4:
   повтор при пропуске понимания; вариант 2 глубины уточнения; строка про
   грамотность в промпте. Причины установлены — это исполнение, не анализ.
3. **Чат 2 (Sonnet), новый чат на фазу.** Реализация Фазы 5 после
   утверждения плана: миграция, retrieval, планировщик, контракт, тесты.
4. **Чат 3 (Opus), чистый.** Adversarial review Фазы 5. Здесь экономить
   нельзя: фаза вводит память, а отравленная память портит все будущие
   исследования.
5. **Чат 1 (Opus).** Разбор находок, отчёт, freeze Фазы 5.

**Особенность Фазы 5.** Она вводит `Blind Evaluator` (по утверждённому
workflow — с Фаз 5–6). Он оценивает план исследования, **не зная**, была
ли включена память. Слепота — часть методики, а не организационная
формальность: оценщик, знающий ответ, перестаёт быть оценщиком.

## 9. Экономия

### 9.1 Где экономить

| Рычаг | Как | Порядок эффекта |
|---|---|---|
| Веерные исследования агентами | только на плане новой фазы, не в реализации | до ~865k токенов за запуск |
| canonical | точечный grep вместо полной загрузки | ~63k → ~2–3k |
| Длина чата | новый чат на фазу + короткий handoff | история перестаёт умножаться |
| Модель на исполнении | Sonnet вместо Opus | кратно на объёме реализации |
| Повторные объяснения | `DECISIONS.md` вместо пересказа | устраняет целый класс диалогов |
| Живые прогоны модели | fake gateway в CI, живой — по решению | $0.035 за прогон против нуля |

### 9.2 Где экономить нельзя

- **Архитектура.** Ошибка проявляется через недели и стоит миграции.
- **Security.** Дефект HIGH-1 Фазы 4 (гейт проверял одну сущность из
  двух) выглядел как рабочий код и был зелёным в тестах.
- **CORE и Pattern.** Методология исследования — это и есть продукт.
- **Learning Loop.** Отравленная память портит не один ответ, а все
  последующие.
- **Adversarial review.** Единственный барьер перед владельцем.
- **Ожидаемые результаты тестов.** Тест, написанный дёшево и «под ответ»,
  создаёт ложную уверенность — это уже случалось: тест на сравнение
  проектов был зелёным при полностью нереализованном инварианте.

### 9.3 Чего этот документ не обещает

Точную цифру экономии назвать нельзя: стоимость фазы зависит от числа
найденных дефектов, а не от плана. Разумное ожидание — заметное снижение
на реализации и на входе в контекст при неизменной стоимости
проектирования и проверки. Проверяется это фактом, а не обещанием:
стоимость Фазы 5 в новом процессе против стоимости Фазы 4 в старом.

## 10. Итоговый регламент

> **How ATLAS PROOF should be developed from now on**

1. Решения принимаются один раз и записываются в `docs/DECISIONS.md`.
   `LOCKED` не пересматривается; конфликт → `STRATEGY REVIEW REQUIRED`
   и остановка.
2. Каждая фаза начинается с плана (**Opus**) и не начинается с кода.
   Код не пишется до слова владельца.
3. Реализация идёт по утверждённому плану (**Sonnet**) в отдельном чате,
   создаваемом на фазу. Право записи в код — только у этого чата.
4. Тесты пишутся по DoD плана. Ожидаемые результаты определяет тот, кто
   отвечает за правильность, а не самая дешёвая модель.
5. Каждая фаза заканчивается adversarial review со свежим контекстом
   (**Opus**), разбором находок и отчётом владельцу.
6. Контекст загружается по иерархии: `DECISIONS` → LOCKED → план фазы →
   нужный skill. canonical — точечно и только при пробеле.
7. Веерные запуски агентов допустимы на плане новой фазы; в реализации —
   нет.
8. Продуктовые тексты, показываемые пользователю, утверждает владелец.
9. Никогда не имитируется то, чего не произошло: ни прогресс
   исследования, ни пройденный тест, ни выполненная проверка.
10. Новая роль появляется только после измеренной проблемы — правило
    расширения ролей из `DEVELOPMENT_WORKFLOW.md` остаётся в силе.
11. Продуктовые развилки решает владелец. Opus предъявляет варианты,
    Sonnet исполняет принятое. Решение живёт в `docs/DECISIONS.md`,
    а не в переписке.

## 11. Конфликты с действующими решениями

Проверено против `01_LOCKED_DECISIONS.md`, `DEVELOPMENT_WORKFLOW.md`,
`PRODUCT_QUALITY_DIRECTIVE.md`, `ARI_LEARNING_LOOP.md`.

**Прямых противоречий LOCKED нет.** Документ описывает процесс, а не
продукт. Четыре места требуют явной оговорки — без неё они превратились
бы в конфликт:

| Риск | В чём конфликт | Как снят |
|---|---|---|
| Четыре чата против «Main Claude — единственный владелец реализации» | Параллельные чаты = параллельные редакторы кода, что прямо запрещено | Право записи в код — только у чата реализации. Остальные читают. Чаты разделены по стадиям, а не работают одновременно |
| Haiku на «тестовых сценариях» | Blind-кейсы и регрессия — часть CORE-методологии (`atlas-core`), они определяют, что считается правильным | Haiku генерирует только вариации формулировок на входе. Ожидаемые результаты и критерии вердикта — Opus/Sonnet |
| Haiku на копирайте | Директива качества и решение владельца: финальные тексты утверждает владелец | Haiku даёт черновик. Утверждение остаётся за владельцем, статус copy — `OPEN` |
| Sonnet на «документации» | План фазы формально документ, но фактически архитектурное решение | Документация разделена: отчёт — Sonnet, план фазы — Opus |

**Ещё одна граница.** Правило расширения ролей («проблема → измерили →
узкая роль → проверили») не отменяется. Этот документ не вводит новых
ролей: Main Claude, Adversarial Reviewer и Blind Evaluator остаются
закрытым списком. Меняется только то, **какая модель** исполняет уже
существующую роль и **в каком чате** это происходит.

**Статус пунктов, требовавших решения владельца:**

| Пункт | Статус |
|---|---|
| Распределение моделей (§2–3) | утверждено |
| Разделение чатов + право записи (§5) | утверждено |
| `docs/DECISIONS.md` (§6) | утверждено, реестр заведён |
| Иерархия контекста (§4) | утверждено |
| Владелец как слой approval (§7.1) | добавлено по требованию владельца |
| Восемь открытых решений (§6.4) | **ждут владельца** — перенесены в реестр со статусом `OPEN` |

Последний пункт остаётся единственным незакрытым. Пока эти решения
открыты, они будут всплывать в каждом новом чате и расходовать ровно то,
что регламент экономит.
