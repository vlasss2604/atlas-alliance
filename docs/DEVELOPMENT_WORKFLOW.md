# ATLAS PROOF — Development Workflow

Статус: утверждён владельцем 2026-08-20. Действует с Фазы 3.

## Цикл фазы

```
1. ПЛАН        Main Claude пишет docs/implementation/phase-N-plan.md
2. РЕВЬЮ       владелец проверяет план; код до утверждения не пишется
3. РЕАЛИЗАЦИЯ  Main Claude — единственный владелец реализации
4. ПРОВЕРКИ    все DoD-тесты + next build + tsc + eslint
5. ADVERSARIAL REVIEW
               один независимый reviewer со СВЕЖИМ контекстом
6. РАЗБОР      Main Claude проверяет каждую находку:
               accepted (чинит) / rejected (обосновывает)
7. ОТЧЁТ       владельцу, с секцией «находки ревью: принято/отклонено»
```

## Мандат reviewer'а (шаг 5)

Reviewer получает ТОЛЬКО: утверждённый phase plan, релевантные
LOCKED-решения, Product Quality Directive, дифф/изменённые файлы фазы.

Ищет исключительно:
- correctness;
- security;
- concurrency / race conditions;
- нарушение инвариантов (БД и продуктовых);
- несоответствие утверждённому плану.

**Каждая находка обязана иметь severity + конкретный сценарий отказа
+ нарушенный инвариант.** Формат:

```
HIGH — Cancel race: если worker переходит RUNNING → SUCCEEDED
одновременно с cancel request, возможно X.
Scenario: ...
Violated invariant: ...
```

Запрещено предлагать: рефакторинг «покрасивее», дополнительные
abstraction layers, подготовку к гипотетическому масштабу — всё,
у чего нет конкретного failure scenario. Reviewer ничего не
перепроектирует; его задача — попытаться сломать готовую работу.

## Роли (закрытый список)

| Участник | Что делает | С какой фазы |
|---|---|---|
| Main Claude | планы, вся реализация, тесты, арбитраж находок | всегда |
| Adversarial Reviewer | независимый поиск дефектов по мандату выше | 3 |
| Blind Evaluator | оценивает результаты Research Engine, НЕ видя внутренней реализации ARI: правильный ли Verdict, не пропущен ли механизм, не выдуман ли вывод, есть ли доказательства, признано ли неизвестное. Кейсы — atlas-core/canonical (TAO, SUI, TIA, robustness) | 5–6 |

## Чего НЕ делаем

- Параллельная реализация несколькими subagents — не используется.
- Новые агентные роли не добавляются, пока реальные данные не покажут
  конкретную проблему, которую отдельный специалист способен решить.
- Не смешивать Claude Code subagents (инструмент разработки) с возможными
  будущими агентами внутри самого ARI (часть продукта) — это разные слои
  (см. 02_ARCHITECTURE_AND_PHASES, Часть 5: «MCP — важное разделение»).
