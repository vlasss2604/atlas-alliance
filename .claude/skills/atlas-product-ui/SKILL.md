# ATLAS PRODUCT & UI

## Ключевое правило

> **Concept defines the screen. Reference defines the style.**

Сгенерированный UI-макет задаёт визуальное направление. **Элемент, появившийся на макете, не становится продуктовым требованием автоматически.** Новая функция становится канонической только после отдельного подтверждения.

---

## Что это за продукт

ATLAS PROOF — **Research Intelligence for Digital Assets**, Telegram Mini App.

Это **не**:
```
generic AI assistant     "ask anything" chatbot
энциклопедия             crypto learning app
trading app              dashboard
```

---

## Два уровня доступа

| | DEMO | ARI • CORE |
|---|---|---|
| Смысл | настоящий ATLAS в миниатюре | развивающийся Research Intelligence |
| Проекты | 3 (конфигурируемо) | динамический roster |
| Тема | Token Value Capture | Token Value Capture |
| Proof | 3 lifetime | по подписке |
| Research capability | до `TARGETED_REFRESH` | до `FRESH_RESEARCH` |
| Recovery | 1 шаг | full within budget |

**CORE не позиционируется как «доступ к N проектам».** Формулировка: «Помогайте ARI исследовать новые проекты» — пользователь участвует в растущей системе, а не листает статичный каталог.

**DEMO не должен ощущаться урезанным по качеству.** Ограничение — в охвате и объёме работы, не в правдивости результата.

**Не показывать в UI:** FREE, START, PLUS, PRO, Pattern v1/v2, training batch, Intelligence Version, Research Mode, model selector, topic selector, mechanism selector.

## Навигация

Единственная навигация — bottom nav. **Гамбургер-меню не нужен.**

| Элемент | Назначение |
|---|---|
| Главная | основной экран / вход |
| Исследования | история пользовательских Proof, private by default |
| **центральная ARI-кнопка** | глобальное «начать новое исследование», доступно из любого места, мягкий переход в question-first flow |
| Проекты | проекты, доступные/исследованные ARI |
| Профиль | аккаунт, подписка, язык, настройки, приватность, помощь, удаление аккаунта |

Всё, что обычно прячут в гамбургер (язык, подписка, аккаунт, privacy, помощь, удаление), живёт в Профиле.

**Не добавлять вкладки:** Intelligence, History, Admin, Patterns, Memory, Topics, Links.

## Input — question-first

```
Заголовок:     Что вы хотите понять?
Placeholder:   Задайте вопрос о проекте, токене или рыночном механизме…
Helper:        Можно писать простыми словами.
```

Рядом компактный круглый `?` — открывает glass-tooltip с кликабельными примерами. Клик по примеру заполняет input, пользователь может отредактировать.

Примеры (без профессиональных терминов):
```
За счёт чего этот токен может становиться ценнее?
Проект много зарабатывает. Получают ли от этого пользу владельцы токена?
Что в этом проекте выглядит сильным, а что может быть слабым местом?
Что важного я могу не учитывать?
```

Не возвращаться к обязательному «Вставьте утверждение». Термин `claim` может существовать на сервере.

## Research progress — 5 стадий

```
1. Понимаю задачу
2. Проверяю накопленный опыт
3. Ищу недостающие доказательства
4. Сопоставляю доказательства
5. Формирую Proof
```

**Показывать только реально происходящие стадии.** Если Research Memory не использовалась — не держать пользователя на фиктивном этапе №2 ради красивой последовательности.

`memoryStatus`: `NOT_USED` / `USED` / `USED_AND_REVERIFIED`

При использовании памяти должно быть понятно одновременно: ATLAS применяет накопленный опыт **и** свежие данные перепроверяются сейчас. Нельзя создавать впечатление, что ATLAS просто повторяет старый Proof.

**Persistent job — продуктовый контракт.** Если UI говорит «Вы можете вернуться позже — ARI продолжит работу», сервер обязан это гарантировать. Закрытие Mini App не прерывает research. Возврат восстанавливает состояние.

**Завершение research:** unread-состояние проявляется индикатором на ARI-кнопке и новым Proof во вкладке «Исследования». **Отдельного notification center и колокольчика нет.**

## Onboarding

3 экрана перед первым входом. Один вторичный action — «Пропустить», не главный визуально. Pagination минимальная (точки).

```
Screen 1 — Что такое ATLAS PROOF / что такое ARI / кому полезен
Screen 2 — Как пользоваться: вопрос → ARI исследует → Proof (Verdict, Confidence, Evidence, Sources, Gaps)
Screen 3 — Как развивается ARI: Проекты → Темы → Связи → Сценарии
```

Состояние на сервере (`onboardingCompleted`, `completedAt`, `version`), привязано к ATLAS User ID, не к localStorage. Endpoint идемпотентен — двойной тап по «Начать» не должен ломаться.

**Семантические запреты:**
```
✗ «ATLAS самостоятельно обучает себя»
✓ «ATLAS развивается через проверенный исследовательский опыт»

✗ «ATLAS знает всю крипту»
✓ «ATLAS постепенно расширяет обученные области исследования»

✗ «каждый Proof автоматически делает ATLAS умнее»
✓ «полезные проверенные Proof помогают развивать Research Intelligence»
```

Не упоминать: human approval, training batches, Pattern версии, manual curation.

Не добавлять: 4-й экран, видео, аудио, wallet connection, pricing, запрос разрешений/уведомлений, выбор языка, tutorial-задания, награды, XP.

## Entitlement в UI

**UI lock недостаточен.** Каждый research-запрос проходит серверную проверку:
```
request → resolve ATLAS User ID → resolve entitlement
→ resolve project scope → resolve topic scope
→ resolve research capability → execute
```

Locked-проекты остаются **видимыми** (логотип, название, бейдж/замок) — пользователь должен понимать ценность CORE. Но исследовать их через DEMO backend нельзя.

**DEMO после исчерпания лимита:** read-only доступ сохраняется — история, готовые Proof, Proof Map, проекты, профиль. Блокируется только запуск нового исследования.
> «Лимит DEMO использован. Вы можете продолжать изучать свои исследования или открыть ARI • CORE.»

Заблокированный запрос **не списывает** Proof-квоту.

**Подписка:** цена берётся из product config (сейчас 2 999 Stars/месяц), не хардкодится. Только Telegram Stars. Экран подписки учитывает состояние: активна → показывать статус, не «Оформить».

## Motion & Performance

> Простo снаружи. Умно внутри. Непрерывно в движении.

**State transitions, not page jumps.** Приложение должно ощущаться как одна непрерывная исследовательская среда, а не набор отдельных страниц.

```
Хорошо: interaction → немедленный UI-отклик → research асинхронно → UI наблюдает состояние
Плохо:  interaction → ждём API → разблокируем UI
```

**Анимация никогда не блокирует взаимодействие.** Пользователь не должен ждать окончания анимации, чтобы нажать доступный контрол.

Тайминги (продуктовые ориентиры):
```
отклик кнопки/инпута     — практически мгновенно
микровзаимодействия      — ~100–180 ms
обычные переходы         — ~150–250 ms
крупные трансформации    — ~200–350 ms
```
Избегать обычных навигационных анимаций 500ms+.

**Производительность:**
- предпочитать `transform` и `opacity`
- осторожно с непрерывной анимацией `width/height/top/left`, больших blur, box-shadow, backdrop-filter, сложных SVG-фильтров
- не строить сотни независимо анимируемых DOM-узлов ради воспроизведения статичного макета
- не добавлять WebGL/Framer Motion/GSAP только потому, что «звучит продвинуто» — сначала аудит зависимостей и обоснование
- тестировать в реальных мобильных WebView (Telegram Android/iOS), не только в desktop Chrome
- на слабых устройствах снижать декорации, **не** снижая качество исследования, навигацию, функциональность Proof или доступную информацию
- уважать `prefers-reduced-motion` — reduced motion не значит уродливо

Создать небольшую переиспользуемую **Motion System** (durations, easing, enter/exit, fade/slide/scale, sheet-поведение, reduced-motion), а не произвольные значения на каждом экране.

**Производительность не откладывается на конец:**
```
FEATURE → MOTION → MOBILE PERFORMANCE CHECK → TEST
```

## Визуальный язык

```
near-black / navy-black фон
cyan / teal неон
subtle neural mesh
translucent / glass панели
очень большие радиусы скругления
pill-кнопки
тонкие светящиеся borders
контролируемое свечение
premium research-intelligence атмосфера
```

Избегать: white UI, flat SaaS dashboard, purple gradient SaaS, cartoon UI, перегруженный киберпанк, острые прямоугольные карточки, крупную декоративную анимацию, обилие бейджей и цветов.

Cyan использовать только для: активного элемента, primary CTA, важных связей сети, заголовков. Не заливать свечением весь экран.

Не воспроизводить буквально каждое свечение с концепт-арта — статичный макет может содержать эффекты, дорогие для реального мобильного UI. Реализовывать **восприятие** глубины эффективно.

---

## Mobile-first

```
основной viewport: 360–430 px
Telegram viewport, safe areas, dynamic viewport height
bottom navigation, открытие клавиатуры
```
Claim textarea не должна уходить под клавиатуру. Каждый onboarding-экран помещается в один viewport без обязательного скролла.

---

## Один primary action на состояние

```
Input       → Начать Proof
Proof       → открыть Proof Map
Proof Map   → Evidence / Sources / Gaps
Подписка    → Открыть ARI • CORE
```
Вторичные функции остаются визуально вторичными.

## Тест качества экрана

1. Очевидно ли главное действие?
2. Мгновенный ли отклик на взаимодействие?
3. Сохраняет ли переход контекст?
4. Двигается ли что-то без причины?
5. Задерживает ли motion пользователя?
6. Хорошо ли на среднем телефоне?
7. Понятно ли при reduced motion?
8. Не протекает ли внутренняя сложность в UI?
9. Ощущается ли это как один непрерывный ATLAS?
10. Можно ли что-то убрать без потери пользы?
